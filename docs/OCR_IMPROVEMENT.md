# OCR改善記録

縦書き小説OCR（yomitoku）の品質改善に関する調査・作業記録。

---

## 現状の問題（当初認識）

### 1. テキストフラグメントの断片化
- **症状**: 縦書き小説で単語が断片化（例: 「シルク」→「シル」+「ク」）
- **原因（当初推測）**: `_merge_text_fragments()` のアルゴリズム不良

### 2. フリガナ除去の精度
- **症状**: フリガナが残る・本文の細字が誤除去される
- **原因（当初推測）**: `median * 0.88` という固定比率では対応不可

---

## 実データ調査結果（2026-04-13）

**対象画像**: `おこぼれ姫と円卓の騎士 1 (ビーズログ文庫)/008.png` (1554×2160px)

`debug_yomitoku.py` による調査で根本原因が判明した。

### yomitokuが返す構造

```
paragraphs: 0件  ← paragraphsは一切返らない
lines:      0件  ← linesも一切返らない
words:     52件  ← wordsのみ返る
```

### wordsの内容分析

| 種別 | width | height | aspect | 件数 | 例 |
|------|-------|--------|--------|------|-----|
| 本文列 | 38-48px | 数百〜2000px超 | >10 | 約30件 | 「レティは礼を言い捨て...」（1列全体） |
| ルビ/ふりがな | 18-33px | 27-152px | <6 | 約22件 | 「ぬし」「おおまた」「ほお」等 |

**重要な発見:**
- 本文の各列は**1つのwordとして丸ごと認識**されていた → 断片化は起きていなかった
- ルビ(18-33px)と本文(38-48px)の間に**明確なギャップ（34-37px）**が存在
- ルビには `direction="horizontal"` と `direction="vertical"` が混在している

### 旧実装の実際の問題

1. **フリガナフィルタの境界不安定**: `median * 0.88 = 33px` がルビ/本文の境界と一致しており、
   確実に除去できていなかった（幅33pxのルビが残る場合あり）
2. **_merge_text_fragments は不要だった**: 本文は既に1列1wordで完結しており、
   マージ処理が逆に本文列どうしを誤結合させるリスクがあった

### 優先度 高-2: `_process_words` を実データに即した内容に修正

**ファイル**: `D:\61.tool\common\ocr\ocr_engine.py`

#### 変更内容

**thicknessの計算を direction 問わず width に統一（縦書き前提）**

```python
# 旧: direction に応じて thickness を切り替え（horizontalなルビがwidth/heightで混在）
# 新: 縦書きドキュメント前提で全ワードのthicknessをwidthで計算
box_info = processor.calculate_box_info(pts, 'vertical')
item['thickness'] = box_info['width']
```

**aspect比によるマージ条件判定（新規）**

```python
# 本文列が大半（aspect>10が多い）→ マージ不要
# フラグメントが多い（aspect<8が多数）→ マージ実行
long_col_count = sum(1 for w in filtered if w['aspect'] > 10)
fragment_count = sum(1 for w in filtered if w['aspect'] < 8)
if fragment_count > long_col_count:
    filtered = self._merge_text_fragments(filtered)
```

### 優先度 高-3: フリガナフィルタの自動閾値化

**ファイル**: `D:\61.tool\common\ocr\ocr_engine.py`

`_detect_valley_threshold()` を新規追加。厚みヒストグラムの「谷（投票数0のビン）」を
自動検出して閾値に使用。谷が検出できない場合は `median * 0.88` にフォールバック。

**実データでの効果**:
- ルビ(18-33px)と本文(38-48px)の間のギャップ(34-37px)を自動検出
- 谷(≈35px)を閾値として採用 → ルビが確実に除去される

---

### 優先度 高-4: `_merge_text_fragments` をXビン分割方式に変更

**ファイル**: `D:\61.tool\common\ocr\ocr_engine.py`

フラグメントが実際に発生するケースに備えた改善（断片化が起きている場合のフォールバック）。

旧アルゴリズム（貪欲展開・y_gap=avg*50）→ Xヒストグラムビン分割 + y_gap=avg*1.5

### 下部読み取り不能の調査

**結論: 読み取り不能ではなく仕様通りの動作**

wordsのy座標分布を確認した結果:

| 種別 | y範囲 | カバー率 |
|------|-------|---------|
| 全ページ列（長い列） | y=66〜2128 | 約95% |
| 途中終わり列（短い列） | y=66〜1177 など | 55〜77% |

- **短い列は実際にそこでテキストが終わっている**（会話文など）→ 読み取り不能ではない
- ただし `score=0.02〜0.07` の低信頼度wordは **認識精度が低く文字化けしている列**が存在
  → OCRモデルの限界であり後処理では解決不可

## 残課題

### 認識精度起因の問題（後処理では解決困難）

- `score=0.00〜0.07` の低信頼度列：「 ........ これは、王女殿下」「青く感じるほどの純白な箱...」等
  → yomitokuモデル自体の認識限界。GPU環境での再処理で改善する可能性あり
- `( ····· 王立騎士団...` のような心内語（イタリック体等）の認識精度が低い

### 未確認: 他の画像でのルビ除去精度

他の書籍・ページでも同様にルビが除去できるか確認が必要。
特に以下のケースは要注意:
- ルビと本文の幅差が小さい書籍
- ルビなしのページ（全件が本文 → フィルタで誤除去されないか）

### 対応済み: PDF縦書きテキスト配置（2026-04-13）

**根本原因**: `searchable_pdf.py` の旧実装が `-90°` 回転後に `textOut(全文)` を呼んでいたため、
長い列（50文字超）でテキストがPDFの描画領域外にはみ出し、後半が切れていた。

**修正**: `_draw_vertical_text()` を新規実装。1文字ずつ個別の `beginText/drawText` で縦に配置。
- `font_size = rect_w * 0.9`（列幅に合わせる）
- `char_step = rect_h / n`（文字数でbboxを等分）
- 各文字のy座標を `y1 + i * char_step + step*0.8` で計算
- 横書き（ルビ等）は `_draw_horizontal_text()` で別処理

**確認**: 008.png の `ソルヴェール国には...他の貴族からも一目置かれていた。` が
末尾まで正しくPDFに埋め込まれることをデバッグPDFで確認済み。
