# 小説テキスト検索・RAG 機能 要件定義（ドラフト）

最終更新: 2026-05-10（実装反映: LLM を Qwen3.6:35b-a3b に切替、主要登場人物抽出・検索フィルタを追加）

novel タブ（Kindle スクショ → Searchable PDF）を、**OCR テキスト DB を主軸とした検索・質問応答ビューア** に作り変えるための要件定義。

関連: [要件定義書 §5 保留領域](要件定義書.md) / [機能追加候補.md「Kindle 連携 / OCR」](機能追加候補.md) — 本書はその保留領域を具体化する位置づけ。

---

## 1. 概要

### 1.1 目的

- Kindle からスクショで取り込んだ小説（Searchable PDF）の **OCR テキストを SQLite に取り込み、検索・質問応答できる UI** を提供する
- ハイブリッド検索（FTS5 + ベクトル `bge-m3`）+ ローカル LLM（`qwen3.6:35b-a3b`）でページ番号付きの引用回答を返す
- 読書自体は Kindle 本体で行う想定。本機能は **解析・横断検索・キャラ要約・場面特定** 用途

### 1.2 背景

- 当初は「OCR して PDF 化」が主目的だったが、ユーザー要望のコアは「**OCR テキストの解析と質問応答**」（読むのは Kindle）
- 既存の Searchable PDF（11 冊）には OCR 結果が透明テキスト層として埋め込まれており、PyMuPDF の `get_text("blocks")` で**ページ単位に高品質な再構成が可能**（PoC で検証済み）
- 元画像（連番 PNG, `images/{書籍名}/*.png`）も全冊残っているため、再 OCR や画像表示も可能

### 1.3 対象ユーザー / 利用前提

- 単一ユーザー、LAN 内利用、認証なし（既存方針 [要件定義書 §1.1](要件定義書.md) 継承）
- **ローカル完結**: ChatGPT / NotebookLM などクラウド AI は使用しない（小説に性的描写を含む可能性があるため）
- 既存環境: `qwen3.6:35b-a3b` / `gemma4:e4b` / `bge-m3` / `nomic-embed-text` が Ollama にインストール済み

## 2. スコープ

### 2.1 対象

- **novel タブ**（`source=novel`）のみを「テキスト DB ビューア」に作り変える

### 2.2 非対象

- main / kindle / generated タブは現状維持
- 横断検索（main + novel + kindle）は本フェーズでは対応せず、将来検討（§9 参照）
- OCR エンジンの差し替え（現状 yomitoku のまま）

## 3. ユースケース

| # | ユースケース | 主操作 |
|---|---|---|
| UC-1 | 「キャラ A の正体は？」のような複雑な質問に、ページ番号付きで回答を得たい | 質問セクションに自然文を入力 → Gemma が引用付きで回答 |
| UC-2 | 「○○というセリフ」を検索して該当ページを特定したい | 検索ボックスにキーワード入力 → ヒットページ一覧 + 画像モーダル |

| UC-4 | 新規取り込んだ書籍を DB に組み入れたい | ライブラリ画面で「再構築」ボタン（個別 / シリーズ / 全件） |
| UC-5 | ヒットしたページの内容を画像で確認したい | 結果リストの小サムネイルをクリック → モーダル拡大 |

## 4. 機能要件

### F-1. ライブラリ表示

- novel タブのトップに、登録済み書籍の一覧を表示（書名・サムネイル・ページ数・DB 状態）
- DB 状態: 「未構築 / 構築済み（最終更新日時）/ 構築中」を示す
- 既存のシリーズ機能（`series.router`）と連動し、書籍をシリーズ単位でグルーピング表示
- 各書籍 / シリーズに「再構築」「DB 削除」ボタンを配置
- **サムネイル**: `data/kindle_novel/images/{書籍名}/{連番}.png` の **先頭画像をそのまま縮小表示**（事前生成しない）

### F-2. DB 構築・更新

- ライブラリ画面の「再構築」ボタンで以下 3 粒度のジョブを起動可能：
    1. **この本だけ**: 1 冊の PDF からテキスト抽出 → ベクトル化 → DB 反映
    2. **このシリーズ**: シリーズ内の全書籍を順次再構築
    3. **全件**: 登録済み全書籍を順次再構築
- 既存 DB レコードは再構築前に削除し、新規生成で置換
- 進行状況はバックグラウンドジョブで処理し、UI に「構築中」表示 + 完了後にトースト通知
- 取り込み元: 既存の `data/kindle_novel/pdfs/{書籍名}.pdf` をデフォルトソースとし、画像パスは `data/kindle_novel/images/{書籍名}/` を参照
- CLI からも実行可能（バッチ処理用）
- **再構築中のロック**: **全体ロック + ジョブキュー方式**
  - 再構築ジョブが走っている間、検索 / 質問 API は全体ロックされ、クライアント側でスピナー / 「再構築中」表示
  - 別の再構築リクエストが来た場合は **ジョブキューに積み**、現在のジョブ完了後に順次実行（同時に走るジョブは常に 1 つ）
  - キューの状態（待機中ジョブ件数 / 実行中ジョブの進捗）は UI に表示

### F-3. 全文検索（FTS5 + ベクトル）

- 検索セクションに**検索ボックス + スコープ切替ドロップダウン**を配置
- 即時検索（数百 ms）。FTS5（pages 単位の OR フレーズ検索）+ ベクトル（chunks 単位、bge-m3）+ RRF（Reciprocal Rank Fusion）で結果をマージ
- 表示順: 関連度（RRF スコア）降順、**無限スクロール（初期 20 件、スクロール末端到達で追加 20 件読み込み）**
- 各結果項目: 書名 / page 番号 / テキストスニペット / 小サムネイル
- **スニペット**: FTS5 の `snippet()` 関数でクエリ語前後を切り出し + マッチ箇所を `<mark>` 等でハイライト。長さ 200 字程度
  - ベクトル検索のみでヒットしたチャンク（FTS5 のクエリ語が無い）はチャンク先頭 200 字をそのまま表示（ハイライトなし）
- 「該当なし」時は単にメッセージ表示のみ（クエリサジェストなし）

### F-4. 質問応答（RAG, Gemma）— 1 問 1 答 + 履歴

- 質問セクションに**質問入力欄 + 送信ボタン + 履歴リスト**を配置
- 動作:
    1. 入力された質問でハイブリッド検索（top 16 件、`min_chars` / `body_page_margin` / `max_per_book` でノイズ除外）
    2. 上位ページのテキストをコンテキストとしてプロンプト構築（各 page に主要登場人物ヒントを付与してキャラ帰属の誤統合を抑制）
    3. `qwen3.6:35b-a3b` にストリーミングリクエスト（`stream=True` / `think=False` / temperature=0.2 / repeat_penalty=1.2 / num_predict=4096 / num_ctx=8192）
    4. 回答を表示しつつ、引用ページ番号（クリックで該当ページ画像モーダル）も表示
    5. 完了したら履歴リストに追加
- **質問入力の制約**:
    - 最大 **500 文字**。500 文字制限が運用上問題（要件「複雑な質問でキャラ要約」に支障）と判断したら制限を緩和（または撤廃）
    - **直前の質問と完全一致した場合は確認ダイアログを表示**（誤クリック・連投防止）。確認後は実行
- **履歴の保存範囲**: 容量上限は設けず、**将来のチューニング材料として全項目を残す**:
    - 質問テキスト
    - 回答テキスト（生成完了時のもの）
    - プロンプト全文（指示文 + コンテキスト + 質問）
    - コンテキストの内訳（書名 / pageNo / chunk 番号 / RRF スコア / 各チャンクテキスト）
    - スコープ（全件 / シリーズ ID / 書籍 ID）
    - 使用モデル名（qwen3.6:35b-a3b 等）と LLM パラメータ（temperature / think 等）
    - タイムスタンプ（送信日時 / 応答完了日時）
    - 応答メタ（eval_count / done_reason 等）
- **履歴 UI**: 質問セクション内に **時系列降順の展開可能リスト**として表示
  - 各履歴行は質問テキスト（先頭部）+ タイムスタンプ + スコープを 1 行で表示
  - クリックで展開し、回答全文 + 引用ページ番号 + コンテキスト概要を表示
  - 展開状態でも各履歴行は独立に折りたためる（複数同時展開可）
  - 各履歴に「削除」ボタン
- 「該当箇所が見つかりません」時は単にメッセージ表示のみ（クエリサジェストなし）

> **チャット形式について（決定事項）**: 過去 Q&A をコンテキストに引き継いで「それより前のシーンは？」のように追加質問できるチャット形式は **技術的に実装可能** だが、本フェーズでは以下の理由から **対応しない**：
> - 1 問 1 答で要件「ページ番号付き回答」「複雑な質問への対応」は満たせる
> - チャット形式はコンテキスト長管理 / 検索範囲の参照解決 / UI 状態管理など、要件未確定の論点が多い
> - 利用感を見てから本当に必要かを判断する方が筋が良い
>
> 利用後にチャット形式が必要と判断した場合、§9「将来検討事項」として再検討する。

### F-5. ページ画像表示（モーダル）

- 検索結果 / 質問の引用ページ番号 / 履歴の引用ページ番号 — いずれもクリックすると **画像モーダル** が開く
- モーダル内容: ページ画像（`data/kindle_novel/images/{書籍名}/{連番}.png`）+ 書名 + page 番号
- **操作**:
    - **前後ページ送り**: 左右キー / 前後ボタンで同一書籍の前後ページに移動（ヒットページの前後文脈確認用）
    - **閉じる**: × ボタン / ESC キー / 背景クリック
- 既存リーダー（読み上げモード等）の機能は載せない（読書は Kindle 本体で行う前提）
- 元画像が無い書籍（万一の場合）は「画像なし」表示

### F-6. スコープ切替

- ヘッダーのドロップダウンで **全件 / シリーズ / 単冊** を切替
- 検索 / 質問の両方に同じスコープが適用される
- スコープ状態は URL パラメータ（例: `?scope=series&series_id=42`）で持つ。ブラウザ「戻る / 進む」で履歴可能（既存方針継承）
- **シリーズ未所属の書籍は「シリーズ」スコープの選択肢に含めない**（除外）。「全件」「単冊」スコープでは検索 / 質問対象に含まれる

## 5. 非機能要件

### 5.1 性能

| 操作 | 目標 |
|---|---|
| FTS5 + ベクトル検索（11 冊全件） | < 1 秒 |
| LLM 1 問の応答（生成完了まで） | 80〜130 秒（qwen3.6:35b-a3b の素の応答時間。Gemma 4:26b 時代は 30〜100 秒） |
| DB 1 冊構築（PDF 抽出 + ベクトル化） | < 5 分（PoC で 3 分） |
| 主要登場人物抽出（11 冊一括） | 約 30〜60 分（gemma4:e4b、1359 ページ × 1〜3 秒） |
| DB 全件構築（11 冊） | < 1 時間（主要登場人物抽出を含めると 1.5〜2 時間） |

### 5.2 データ量見積もり

- **DB 本体（書籍データ）**: 1 冊あたり約 200 チャンク × 1024 次元 = 約 800KB（vec 部）+ FTS5 + テキスト本体。11 冊で **約 10MB 程度**（軽い）
- **質問履歴**: 1 件あたり質問 + 回答 + プロンプト全文 + コンテキスト全テキストで **約 15KB**。10,000 件保存しても約 150MB
  - 容量上限は設けず、肥大化が問題化したら閾値（例: 1 年以上 + 1 万件超）でアーカイブする運用を別途検討

### 5.3 セキュリティ・公開範囲

- LAN 内のみ。LAN 外公開は対象外（[セキュリティ設計書 §1](../03_詳細設計/セキュリティ設計書.md) 継承）

## 6. 採用技術（PoC で確定）

| 層 | 技術 | 理由 |
|---|---|---|
| OCR データ取得 | 既存 Searchable PDF を `PyMuPDF.get_text("blocks")` で抽出 | 再 OCR 不要、数分で全 11 冊 DB 化可能 |
| DB | **SQLite + FTS5 + sqlite-vec**（単一ファイル） | ページ番号 / 画像パス / ベクトルを 1 ファイルで管理。pyproject に sqlite-vec 追加済み |
| Embedding | **`bge-m3`**（1024 次元、Ollama） | 日本語意味検索精度が `nomic-embed-text` より明確に高い（PoC で検証）。OCR ミスを意味距離で吸収 |
| 質問応答 LLM | **`qwen3.6:35b-a3b`**（Ollama、thinking モデル / 35B 総・活性 3B MoE） | 概括的な質問への踏み込みが Gemma 4:26b より大幅に深い。`stream=True` / `think=False` を共通モジュール側で必須化（[ADR-0007](../02_基本設計/ADR/0007_llm-extraction-qwen-adoption.md)） |
| 主要登場人物抽出 | **`gemma4:e4b`**（Ollama） | 短答型タスクは軽量モデルで十分。1300 ページの一括抽出を現実的な時間で回せる |
| 検索 | FTS5 OR フレーズ + ベクトル + RRF + フィルタ（`min_chars` / `body_page_margin` / `max_per_book`）| 単純キーワードは FTS5、意味検索は bge-m3 が分担。フィルタで章扉・付録ページを除外し書籍偏りを抑制 |
| LLM クライアント | **`D:\61.tool\common\llm`** 共通モジュール経由（A-0 リネーム前は `Qwen/`） | thinking モデル特有の地雷（`response` 空 / `num_predict` 食い潰し）を踏み抜く呼び出しを集約 |

PoC 検証結果: [docs/05_記録/](../05_記録/) で別途記録予定（任意）

## 8. 制約・前提

- ローカル完結。Ollama サーバー（`localhost:11434`）が起動している前提
- 質問応答 LLM（qwen3.6:35b-a3b）は応答時間が長い（80〜130 秒）。UI で「生成中」スピナー / プログレス表示が必要
- 環境: RTX 5070 **VRAM 12GB** + システム RAM 32GB。qwen3.6:35b-a3b（27GB / Q4_K_M）は VRAM に収まり切らず、Ollama が自動で約 61% を CPU 側にオフロードしている（システム RAM 使用）。それでも MoE 活性 3B のため動作するが、生成速度は ~5〜6 t/s 程度になる
- LLM クライアントは共通 LLM モジュール（`D:\61.tool\common\llm`）に依存。共通モジュールが破損 / 移動するとビルド不可

## 9. 将来検討事項

| TBD-7 | スコープ「未割当書籍」の扱い | **「シリーズ」スコープの選択肢から除外**。「全件」「単冊」では含む |
| TBD-8 | 質問入力の最大文字数 | **500 文字**（運用で問題が出れば緩和） |
| TBD-9 | 同一質問の連投防止 | **直前と完全一致なら確認ダイアログを表示** |
| TBD-10 | 「該当箇所が見つかりません」時の UI | **単にメッセージ表示**（サジェストなし） |
| TBD-A | DB 再構築のロック粒度・並行制御 | **全体ロック + ジョブキュー**（同時 1 ジョブ、別リクエストはキューイング） |
| TBD-B | 履歴 UI の表示形式 | **質問セクション内に時系列降順の展開可能リスト**（クリックで個別展開、複数同時展開可） |
| TBD-C | 画像モーダルの操作仕様 | **前後ページ送りあり**（左右キー / ボタン）+ × / ESC / 背景クリックで閉じる |
