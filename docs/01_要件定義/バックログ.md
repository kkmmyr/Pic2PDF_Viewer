# バックログ（機能追加候補）

最終更新: 2026-05-12（B-15 キャラクター辞典 + B-16 マルチターン会話 QA 実装完了 → 実装済み履歴へ）

将来の機能追加候補を整理した棚卸しリスト。**個人 LAN ソロツール / 同人誌特化** という制約下で何を作り、何を作らないかを明示する。

優先度の判断基準:
- **A（高）**: 新方針の核機能。すぐに着手する
- **B（中）**: 工数中〜大、設計の見直しが必要、一定の利得あり
- **C（低）**: 工数大、利得が中程度、要望が出てから検討
- **対象外**: 信頼モデル / 同人誌特化方針と整合しない、または重複機能で意図的に排除

小説 RAG 関連の検討時は実機ベンチマーク・モデル選定の知見を [小説RAG_技術知見.md](../05_記録/小説RAG_技術知見.md) に蓄積している。判断材料として参照する。

## B. 中規模の機能追加（中優先・中工数）

### B-1. PDF 分割

**動機**: PDF 結合（merge）は実装済みだが、分割（split）は無い。長大な合本を巻ごとに分けたい

**案**: 編集モードで「ここから新 PDF」マーカーを置き、保存時に 2 つ以上の PDF に分割

**工数**: 中。merge の逆処理 + UI 設計

### B-2. メタデータの一括インポート（CSV / JSON）

**動機**: 現在エクスポートは `/api/meta/export` で実装済みだが、インポートが無い。他環境から移行する手段が無い

**案**: `/api/meta/import` を新設し、JSON ファイルアップロード → 既存メタとマージ（衝突解決ポリシーは upsert / overwrite / skip 選択）

**工数**: 中。バリデーション + マージロジック + UI

### B-4. キーボードショートカット カスタマイズ

**動機**: 現在のショートカットは固定。利用頻度や好みに応じてカスタマイズできない

**案**: localStorage に key-action マップを保存。設定画面で編集

**工数**: 中。useReaderShortcuts の汎化が必要

### B-7. 小説 RAG: クラウド LLM 移行の再検討（要件見直し含む / 検証段階）

**動機**: ローカルでは context window の制約で「部分読み」になる構造的課題がある。DeepSeek V3.x / V4 等のクラウド API は **入力 ~$0.30/M token / 出力 ~$1.20/M token** 程度で、全 11 冊フル context を 1-shot で読ませても **月数百〜数千円** で収まる試算。応答時間も短縮される。

**前提変更**: 移行する場合は [要件定義書 §1.3](小説テキスト検索・RAG機能.md) 「ローカル完結（性的描写を含む可能性があるためクラウド AI を使用しない）」の前提を見直す必要がある。

**判断材料**:
- DeepSeek の content policy は西側より緩めだが、明示的な性的描写は refuse される可能性あり
- Kindle 購入小説の全文を中国側クラウドに送信することの是非
- B-6（ローカル num_ctx 拡大）で同等の品質改善が得られるなら不要
- ハイブリッド構成（ローカル: 性的内容の可能性あり / クラウド: 一般 SF・ファンタジー等）も選択肢

**工数**: 中〜大。`qwen_client` 互換のクラウドクライアント実装 + 環境変数でモデル切替 + content policy エラーハンドリング + コスト監視。要件定義書 §1.3 の更新

**着手判断**: B-6 完了後の品質体感を見て判断。B-13 段階 C + B-14 で十分なら本項目は対象外候補へ移動

### B-10. 小説 RAG: ページ単位シーン要約（B-9 の中間版・実質不要）

**現状**: B-9（Contextual Retrieval）が gemma4:e4b への切替で当初 19 時間想定 → **実機 100 分** に短縮されたため、本項目の存在意義（B-9 を待てない場合の安価な代替）は薄れた。B-9 で十分な品質改善が得られているなら **対象外候補へ移動** を検討。

### B-17. 漫画ソースへの画像キャプション検索（パイロット先行）

**動機**: Gemma4:e4b の `analyze_image` を活かして、絵の内容を自然言語で検索できるようにする。同人誌特化ツールの目玉機能候補。クラウドを使わずローカル完結で性的内容を扱える点が方針と整合（旧「AI タグ自動生成」とは異なり、自由文クエリ前提）。

**案**:
- **Step 1 パイロット**: 1 冊（20〜30 頁）を Gemma4:e4b で全頁キャプション → 品質判定。検索クエリ 10 件想定でヒット精度確認
- **Step 2 比較**（任意）: Qwen2.5-VL-7B Q4 を追加導入して品質比較。Qwen3.6:35B-A3B（現運用 LLM）は **vision 非対応** のため、別系列の VL モデルが必要
- **Step 3 本実装**: `pages.caption TEXT` + `pages_caption_vec USING vec0(embedding FLOAT[1024])`（bge-m3 で再利用）+ バッチ CLI + 検索エンドポイント + 検索 UI

**規模試算**: `main/complete/` に 484 ZIP、1 冊平均 25 頁仮定で約 12,100 頁。Gemma4:e4b で 1 頁 5〜8 秒なら **17〜27 時間（1〜2 晩）**。許容できなければサンプル頁（表紙 + 中扉 + 数頁）モードに切替

**前提制約**:
- Gemma `analyze_image` は **日本語テキスト OCR 精度低** とガイドに明記。台詞・効果音は拾えない可能性が高いが、絵の描写用途は問題なし
- 同人誌は 1 冊 30 頁未満が多いとの user 仮定。実態は実機計測で確認
- ライブラリ全体（hitomi 等も含む）に拡張する場合は更にバッチ時間が伸びる

**工数**: パイロット 半日 / 本実装 中

**判断**: Step 1 のヒット精度と所要時間を見てから Step 3 へ進む

### B-18. 小説 RAG: リーダー統合「ここまでのあらすじ」生成（優先度低）

**動機**: 続巻を読み始める前や、間が空いたときに「ここまで何があったっけ」を即座に思い出したい。Qwen 131k ctx で 1 冊丸ごと読めるので、任意ページまでの本文を input に「現時点までのあらすじ」を生成できる。

**案**:
- 小説リーダーに「ここまでのあらすじを生成」ボタン
- `GET /api/novel_db/books/{name}/recap?up_to_page=N` 新設、1〜N ページの本文を Qwen に投入し 800〜1500 字で要約
- 結果は `book_recaps(book_id, up_to_page, text, generated_at)` にキャッシュ（同じ `up_to_page` での再要求はキャッシュ返却）
- 既存 `summarizer.py`（B-5）が骨格としてほぼ流用可能

**工数**: 小〜中

### B-19. 小説 RAG: 書籍類似度推薦（"if you liked X..."）（優先度低）

**動機**: B-8 で `book_summaries_vec`（全冊サマリの embedding）が既に存在。これを使えば「今読んでいる本に似た本」がライブラリから即座に提示できる。

**案**:
- `GET /api/novel_db/books/{name}/similar?top=5` 新設、その本のサマリ embedding から KNN（同書籍は除外）
- リーダーの関連書籍ページ（A-2 で実装済）に「似ているテーマの本」セクションを追加
- 既存 `book_summaries_vec` をそのまま読むだけ。新規モデル呼び出し不要

**工数**: 小

### B-20. 読書会ディスカッション生成（優先度低）

**動機**: 1 冊の小説を Qwen に読み込ませ、2 人のキャラクター（ペルソナ）がリアルタイムに語り合う「読書会」形式の対話を生成する。内容把握補助とエンタメの両立。

**要件詳細**: [B-20_読書会ディスカッション生成_要件.md](B-20_読書会ディスカッション生成_要件.md) を参照。

**概要**:
- 専用ページ `/novel/discussion`（小説ソースのみ対応）
- ペルソナ: プリセット 3 軸（読書スタイル / 口調 / 視点）+ カスタム自由入力
- 入力: 本文全体を Qwen 131k ctx へ投入（超過時はエラー）
- 発話数: UI スライダーでユーザー指定
- ストリーミング: SSE で 1 発言ずつリアルタイム表示
- 保存: `kindle_novel/discussions/<bookName>/<timestamp>.json`（キャンセル時は保存なし）
- スコープ外: 漫画・同人誌対応、3 人以上、ユーザー介入、生成後編集

**依存**: 4.5 完了済み（`a9aa914`）につき即着手可能

**工数**: 中〜大

## C. 大規模 / 要望待ち（低優先・大工数）

### C-1. 表紙ザッピングモード

**動機**: 「今日は何を読もう」状態を解消したい。表紙だけを次々送って気分の本を探すモード

**案**: フルスクリーンで表紙のみを表示し、左右キーでザッピング → クリックで開く

**工数**: 中〜大。新しい閲覧モードの追加

**判断**: 現状のサムネイル一覧で実質的にザッピングできているため、優先度低のまま保留

### C-2. DLsite 作品名検索によるキーワードタグ取得

**動機**: 作品 ID は基本的に取れないが、作品名で公開ページを検索できればキーワードタグを取得できる可能性がある

**案**: タイトル → DLsite / Fanza の公開検索ページ → 候補提示 → ユーザー確認 → タグ反映

**工数**: 中〜大。スクレイピング + 候補提示 UI + 精度評価

**判断**: 実用精度が出る見込みが立った時点で着手判断。タグ機能は撤去済みのため、復活時に併せて検討

### C-3. PWA 対応 / オフライン閲覧

**動機**: PC を移動する際にライブラリをローカルにキャッシュしたい

**案**: Service Worker でメタデータと一部 PDF をオフラインキャッシュ

**工数**: 大

### C-4. モバイル UI 最適化

**動機**: 現在は PC 想定の UI、スマホでは閲覧に耐えるが操作性が低い

**案**: ブレイクポイント別レイアウト、タッチジェスチャー（スワイプでページ送り）

**工数**: 大

### C-5. 読書統計ダッシュボード

**動機**: 「今月何冊読んだ」「どの作者を多く読んでいるか」のサマリ画面がない

**案**: `/api/stats` エンドポイント + ダッシュボードページ

**工数**: 中

### C-6. アクセシビリティ（a11y）強化

**動機**: アイコンのみのボタンが `title=` 属性のみで運用されており、`aria-label` 併用なし。スクリーンリーダー対応が弱い。

**案**:
1. `eslint-plugin-jsx-a11y` 導入で機械的検出
2. アイコンのみボタンに `aria-label` 付与
3. ランドマーク `role`（main / navigation / complementary）設定
4. フォーカストラップ（Dialog 内 Tab 巡回の閉じ込め）

**工数**: 大。

**着手判断（gate 条件）**: 個人 LAN ソロツールである限り**着手しない**。LAN 外公開する場合にのみ再検討する。本項目は TODO リスト上で「条件付保留」として扱い、通常の優先度比較からは除外する。

### C-8. E2E テスト導入（Playwright）

**動機**: フロントは vitest 単体テストで担保しているが、`pages/*` と大規模 Panel は意図的にスコープ外で 0% カバレッジ。ユーザー操作の golden path 自動検証が無い

**案**: Playwright で 5〜10 件のシナリオ構築

**工数**: 大。導入判断は別途

## 対象外（信頼モデル / 同人誌特化方針との非整合）

以下は **個人 LAN シングルユーザー × 同人誌特化** の前提と整合しないため意図的に作らない。

| 項目 | 理由 |
|---|---|
| ユーザーアカウント / 認証 / 認可 | LAN 内シングルユーザー前提 |
| マルチテナント・データ分離 | 同上 |
| API レート制限 | 単一クライアント前提 |
| WebSocket / SSE による進捗通知 | ポーリングで十分 |
| GraphQL API | REST で要件を満たす |
| API バージョニング | クライアント単一 |
| マイクロサービス分割 | 規模に対し過剰 |
| Kubernetes / Docker Compose 化 | LAN ローカル起動で十分 |
| 公開 PR テンプレート / Issue テンプレート | ソロ開発 |
| Storybook | コンポーネント数が爆発しない範囲 |
| サークル名 Web 検索による自動取得 | 撤去済み（精度が実用に達しない） |
| シリーズの自動発見（新規シリーズ生成） | 撤去済み（命名揺れに対し精度不足）。代替: AI による既存シリーズへの紐付け提案（A-1） |
| 多言語 OCR 対応 | OCR 機能自体が保留領域。現状日本語のみで十分 |
| ePub サポート | スコープ外（同人誌は ZIP / 画像が主） |
| AI タグ自動生成（表紙画像 + LLM） | タグ機能自体を撤去。復活時に再検討 |
| レーティング（★1〜5） | 旧バックログで実装候補だったがコード化されたことはなく、利用習慣もないため恒久的に対象外 |
| 大規模 Panel の presentation/container 分割 | hook 抽出済みで本体ロジック層は既に薄く、JSX 主体の分割では行数は減っても認知負荷は下がらない。テスト容易性の利得は hook 単体テスト（744 件）と将来の E2E（C-8）で充足見込みのため対応しない |
| 小説 RAG: LLM 補助チャンキング（Qwen でシーン境界検出 → 再チャンク） | 文献的に確定的な評価が薄く、B-9（Contextual Retrieval）のほうが ROI 高い。再チャンク + 再 embedding のコストも大きい。B-9 で十分な改善が得られると見込み、本項目は対応しない |

## 運用方針

- 候補が **A-N → 対応決定** になったら新機能として `feat:` プレフィックスのコミットで実装
- 実装後は本ファイルから対応済み項目を削除し、上部「実装済み機能の履歴」テーブルに 1 行追加 + 詳細は変更履歴 / 設計書側に記録
- 棚上げ判断（C → 対象外）になった項目は対象外テーブルに移動

候補追加時のフォーマット:

````markdown
### {Tier}-{N}. {タイトル}

**動機**: {現在の不便 / 欲しい価値}
**案**: {具体的な実装方針}
**工数**: 小 / 中 / 大
````
