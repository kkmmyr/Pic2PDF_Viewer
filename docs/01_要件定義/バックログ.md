# バックログ（機能追加候補）

最終更新: 2026-06-16（B-27 追加: Kindle 新アプリキャプチャ完全対応）

将来の機能追加候補を整理した棚卸しリスト。**個人 LAN ソロツール / 同人誌特化** という制約下で何を作り、何を作らないかを明示する。

> 内部構造改善・依存更新・DB/インフラ移行は本ファイルではなく [リファクタリング計画書](../06_リファクタリング/リファクタリング計画書.md) へ。

優先度の判断基準:
- **A（高）**: 新方針の核機能。すぐに着手する
- **B（中）**: 工数中〜大、設計の見直しが必要、一定の利得あり
- **C（低）**: 工数大、利得が中程度、要望が出てから検討
- **対象外**: 信頼モデル / 同人誌特化方針と整合しない、または重複機能で意図的に排除

小説 RAG 関連の検討時は実機ベンチマーク・モデル選定の知見を [小説RAG_技術知見.md](../05_記録/小説RAG_技術知見.md) に蓄積している。判断材料として参照する。

## B. 中規模の機能追加（中優先・中工数）

### B-26. 書籍類似度推薦（novel 専用）

**動機**: 読書会で「この本に似ている」という表現を自然に使えるようにしたい。書籍詳細ページから直接「次に読む本」を探せる体験を作る。

**詳細要件**: [書籍類似度推薦_要件.md](書籍類似度推薦_要件.md)

**概要**:
- 類似度: bge-m3 全文 embedding + サマリ embedding + タグ/著者メタ情報の 3 軸ハイブリッド（均等重み、調整可）
- 表示: 書籍詳細ページ下部パネル、閾値 cos ≥ 0.7 の最大 5 件
- 永続化: `book_similarities` テーブルにプリコンピュート
- トリガー: 管理画面から手動バッチ実行
- 対象: novel のみ（comic / doujin は対象外）

**工数**: 中〜大。DB スキーマ変更・バッチ処理・新規 API 2 本・フロントエンドコンポーネント追加

### B-2. メタデータの一括インポート（CSV / JSON）

**動機**: 現在エクスポートは `/api/meta/export` で実装済みだが、インポートが無い。他環境から移行する手段が無い

**案**: `/api/meta/import` を新設し、JSON ファイルアップロード → 既存メタとマージ（衝突解決ポリシーは upsert / overwrite / skip 選択）

**工数**: 中。バリデーション + マージロジック + UI

### B-4. キーボードショートカット カスタマイズ

**動機**: 現在のショートカットは固定。利用頻度や好みに応じてカスタマイズできない

**案**: localStorage に key-action マップを保存。設定画面で編集

**工数**: 中。useReaderShortcuts の汎化が必要

### B-17. 漫画ソースへの画像キャプション検索（パイロット先行）

**動機**: ローカル VL モデルを活かして、絵の内容を自然言語で検索できるようにする。同人誌特化ツールの目玉機能候補。クラウドを使わずローカル完結で性的内容を扱える点が方針と整合（旧「AI タグ自動生成」とは異なり、自由文クエリ前提）。

**案**:
- ~~**Step 1 パイロット**: 1 冊（20〜30 頁）を Gemma4:e4b で全頁キャプション → 品質判定~~
- ~~**Step 2 比較**（任意）: Qwen-VL 系との比較~~
- **Step 3 本実装**: `pages.caption TEXT` + `pages_caption_vec USING vec0(embedding FLOAT[1024])`（bge-m3 で再利用）+ バッチ CLI + 検索エンドポイント + 検索 UI

**パイロット結果（2026-05-14 完了）**: 詳細 → `docs/05_記録/漫画AI検証.md`

| モデル | T1 シーン | T2 パネル | T3 ストーリー | T4 OCR | T5 キャラ |
|---|:---:|:---:|:---:|:---:|:---:|
| gemma4:e4b | △ | ◯ | × | ×（30%） | △ |
| **qwen3-vl:8b** | **◯** | **◯** | **△** | **◯（4/5）** | **△** |

**採用モデル**: `qwen3-vl:8b`（OCR 精度が 30% → 80%+ に改善）

**技術的注意点**:
- qwen3-vl:8b は Ollama の `images` 配列に複数画像を渡すと **空文字列を返す（サイレント失敗）**
- 複数ページ送信は **PIL 縦連結で 1 枚 PNG にまとめる**回避策で対応済み
- 1 ページあたり処理時間の計測は Step 3 着手時に行う

**規模試算**: 1 冊平均 25 頁仮定で約 12,100 頁。qwen3-vl:8b の速度は実測次第。許容できなければサンプル頁（表紙 + 中扉 + 数頁）モードに切替

**工数**: Step 3 本実装 中

**判断**: **保留**（2026-06-12）: 現状の qwen3-vl:8b の品質が期待を下回るため現状は対応しない。ローカル VLM の精度向上（新モデル等）を確認した段階で再判断する。

### B-18. 小説 RAG: リーダー統合「ここまでのあらすじ」生成（優先度低）

**動機**: 続巻を読み始める前や、間が空いたときに「ここまで何があったっけ」を即座に思い出したい。Qwen 131k ctx で 1 冊丸ごと読めるので、任意ページまでの本文を input に「現時点までのあらすじ」を生成できる。

**案**:
- 小説リーダーに「ここまでのあらすじを生成」ボタン
- `GET /api/novel_db/books/{name}/recap?up_to_page=N` 新設、1〜N ページの本文を Qwen に投入し 800〜1500 字で要約
- 結果は `book_recaps(book_id, up_to_page, text, generated_at)` にキャッシュ（同じ `up_to_page` での再要求はキャッシュ返却）
- 既存 `summarizer.py`（B-5）が骨格としてほぼ流用可能

**工数**: 小〜中

### B-25. meta.db クラウド同期（SQLite Online Backup API + ファイルストレージ）

**動機**: 閲覧回数・ジャンル・シリーズ等の書誌メタを複数端末で共有したい。SQLite は WAL モードで頻繁に書き込みが発生するため、ライブファイルを OneDrive に置くと同期競合でDB破損リスクがある。

**方針**: `sqlite3.backup()`（SQLite Online Backup API）でスナップショットを安全に作成し、そのファイルだけを OneDrive / S3 等に配置する。ライブDB は常にローカルのまま。

**案**:
- `GET /api/meta/backup` — `sqlite3.backup()` でスナップショット（`meta.backup.db`）を作成し、指定ディレクトリに保存
- `POST /api/meta/restore` — 指定パスの `meta.backup.db` を取り込んで現在の DB に upsert マージ（衝突時は `last_viewed_at` が新しい方を優先）
- バックアップ先は env `META_BACKUP_DIR` で設定（OneDrive の共有パスを指定）
- Windows タスクスケジューラで定期実行（例: 1 日 1 回 `POST /api/meta/backup`）

**なぜ DynamoDB でなく SQLite backup か**:
- データモデルの移行が不要（SQLite のままファイルコピー）
- 追加クラウド費用ゼロ（OneDrive / ローカル NAS に置くだけ）
- `sqlite3.backup()` は API 標準なのでロック競合なし

**工数**: 小。`sqlite3.backup()` の呼び出し 1 関数 + API エンドポイント 2 本 + タスクスケジューラ登録手順

### B-19. 小説 RAG: 書籍類似度推薦（"if you liked X..."）（優先度低）

**動機**: B-8 で `book_summaries_vec`（全冊サマリの embedding）が既に存在。これを使えば「今読んでいる本に似た本」がライブラリから即座に提示できる。

**案**:
- `GET /api/novel_db/books/{name}/similar?top=5` 新設、その本のサマリ embedding から KNN（同書籍は除外）
- リーダーの関連書籍ページ（A-2 で実装済）に「似ているテーマの本」セクションを追加
- 既存 `book_summaries_vec` をそのまま読むだけ。新規モデル呼び出し不要

**工数**: 小

### B-27. Kindle 新アプリ（Microsoft Store 版）キャプチャ完全対応

**動機**: 旧 Kindle for PC が 2026-06-30 に廃止され、Microsoft Store 版新アプリへ移行済み。ウィンドウタイトル変更（`'Kindle for PC'` → `'Kindle'`）は TM-1（2026-06-16）で対応済みだが、以下の点が未解決：

1. **ウィンドウ最大化不可**: 新アプリはウィンドウサイズを自由に変更できるが、旧来の F11 フルスクリーンや最大化ボタンの挙動が変わっており、固定クロップ座標（`CROP_X1/Y1/X2/Y2`）がずれる可能性がある
2. **クロップ座標の再キャリブレーション**: `AutoKindleCapturer` の動的検出（黒帯スキャン）は引き続き動くはずだが、新 UI のヘッダー高・余白が変わっているため `Config` のデフォルト固定座標が実態と乖離している
3. **ショートカットキーの変更確認**: ページ送り（左/右矢印）・フルスクリーン（F11）が旧アプリと同じか未確認

**調査 & 対応方針**:
- `capturer.py` を新アプリで実際に動かし、キャプチャ枠のずれを確認
- ずれがあれば `Config` のデフォルト座標を実測値に更新、または `AutoKindleCapturer` を常用モードに昇格（固定座標廃止）
- ショートカットキー変更があれば `Config.PAGE_CHANGE_KEY` / `setup_window()` を修正

**工数**: 小〜中（実機確認がメイン。コード変更は座標更新のみの可能性あり）

## C. 大規模 / 要望待ち（低優先・大工数）

### C-1. 表紙ザッピングモード

**動機**: 「今日は何を読もう」状態を解消したい。表紙だけを次々送って気分の本を探すモード

**案**: フルスクリーンで表紙のみを表示し、左右キーでザッピング → クリックで開く

**工数**: 中〜大。新しい閲覧モードの追加

**判断**: 現状のサムネイル一覧で実質的にザッピングできているため、優先度低のまま保留

### C-2. DLsite 作品名検索によるキーワードタグ取得

**動機**: 作品 ID は基本的に取れないが、作品名で公開ページを検索できればキーワードタグを取得できる可能性がある

**案**: タイトル → DLsite / Fanza の公開検索ページ → 候補提示 → ユーザー確認 → タグ反映

**工数**: 中〜大。スクレイピング + 候補提示 UI + 精度評価

**判断**: 実用精度が出る見込みが立った時点で着手判断。タグ機能は撤去済みのため、復活時に併せて検討

### C-3. PWA 対応 / オフライン閲覧

**動機**: PC を移動する際にライブラリをローカルにキャッシュしたい

**案**: Service Worker でメタデータと一部 PDF をオフラインキャッシュ

**工数**: 大

### C-5. 読書統計ダッシュボード

**動機**: 「今月何冊読んだ」「どの作者を多く読んでいるか」のサマリ画面がない

**案**: `/api/stats` エンドポイント + ダッシュボードページ

**工数**: 中

### C-8. E2E テスト導入（Playwright）

**動機**: フロントは vitest 単体テストで担保しているが、`pages/*` と大規模 Panel は意図的にスコープ外で 0% カバレッジ。ユーザー操作の golden path 自動検証が無い

**案**: Playwright で 5〜10 件のシナリオ構築

**工数**: 大。導入判断は別途

### C-10. 小説 RAG: 新規キャプチャ後の自動 DB 構築

**動機**: 現状は管理画面から手動で OCR → ビルドを投入する必要がある。新しい書籍をキャプチャするたびに手順が発生する。

**案**: キャプチャ完了イベントを hook して job_queue に自動投入

**工数**: 中。イベント連携の設計が必要

### C-11. 小説 RAG: 検索結果エクスポート

**動機**: 良い回答を手元のメモに残したい。コピーボタン以上の構造化エクスポートが欲しい。

**案**: JSON / Markdown 形式でダウンロード（回答 + 引用チャンク + ページ番号）

**工数**: 小

### C-13. 小説 RAG: 複数モデルでの回答比較 UI

**動機**: モデル更新時の品質比較を画面上でできるようにしたい。現状はログを見て判断。

**案**: 同一クエリを複数モデルに投げて並列表示。NOVEL_DB_LLM_MODEL を実行時に切り替え可能にする。

**工数**: 中

## 対象外（信頼モデル / 同人誌特化方針との非整合）

以下は **個人 LAN シングルユーザー × 同人誌特化** の前提と整合しないため意図的に作らない。

| 項目 | 理由 |
|---|---|
| ユーザーアカウント / 認証 / 認可 | LAN 内シングルユーザー前提 |
| マルチテナント・データ分離 | 同上 |
| API レート制限 | 単一クライアント前提 |
| WebSocket / SSE による進捗通知 | ポーリングで十分 |
| GraphQL API | REST で要件を満たす |
| API バージョニング | クライアント単一 |
| マイクロサービス分割 | 規模に対し過剰 |
| Kubernetes / Docker Compose 化 | LAN ローカル起動で十分 |
| 公開 PR テンプレート / Issue テンプレート | ソロ開発 |
| Storybook | コンポーネント数が爆発しない範囲 |
| サークル名 Web 検索による自動取得 | 撤去済み（精度が実用に達しない） |
| シリーズの自動発見（新規シリーズ生成） | 撤去済み（命名揺れに対し精度不足）。代替: AI による既存シリーズへの紐付け提案（A-1） |
| 多言語 OCR 対応 | OCR 機能自体が保留領域。現状日本語のみで十分 |
| ePub サポート | スコープ外（同人誌は ZIP / 画像が主） |
| AI タグ自動生成（表紙画像 + LLM） | タグ機能自体を撤去。復活時に再検討 |
| レーティング（★1〜5） | 旧バックログで実装候補だったがコード化されたことはなく、利用習慣もないため恒久的に対象外 |
| 小説 RAG: クラウド LLM 移行（B-7） | B-13/B-14 完了でローカル QA 品質・速度が要件を充足（llama-server で応答 5× 短縮、全文読み込み実現）。「性的描写を含む可能性があるためクラウド AI を使用しない」方針とも整合するため恒久的に対象外（2026-06-12 判断） |
| 小説 RAG: ページ単位シーン要約（B-10） | B-9（Contextual Retrieval / gemma4:e4b）で当初 19 時間想定 → 実機 100 分に短縮され存在意義消失。B-9 で品質充足（2026-06-12 判断） |
| 大規模 Panel の presentation/container 分割 | hook 抽出済みで本体ロジック層は既に薄く、JSX 主体の分割では行数は減っても認知負荷は下がらない。テスト容易性の利得は hook 単体テスト（744 件）と将来の E2E（C-8）で充足見込みのため対応しない |
| 小説 RAG: LLM 補助チャンキング（Qwen でシーン境界検出 → 再チャンク） | 文献的に確定的な評価が薄く、B-9（Contextual Retrieval）のほうが ROI 高い。再チャンク + 再 embedding のコストも大きい。B-9 で十分な改善が得られると見込み、本項目は対応しない |
| PDF 分割（B-1） | merge の逆処理は工数に対して利用頻度が低く、手動ツールで代替可能 |
| モバイル UI 最適化（C-4） | 個人 LAN PC 専用ツールのためモバイル対応は不要 |
| a11y 強化（C-6） | LAN 内シングルユーザー前提のため不要。LAN 外公開の予定もなし |
| 小説 RAG: 横断検索（C-9） | スキーマ変更コストが大きく、ソース別閲覧で利用実態として不要 |

## 運用方針

- **新規候補の振り分け**: ユーザーから見た新機能・新体験 → 本ファイル（A/B/C 階層）。内部改善・依存更新 → [リファクタリング計画書](../06_リファクタリング/リファクタリング計画書.md)。
- 候補が **A-N → 対応決定** になったら新機能として `feat:` プレフィックスのコミットで実装
- 実装後は本ファイルから対応済み項目を削除し、上部「実装済み機能の履歴」テーブルに 1 行追加 + 詳細は変更履歴 / 設計書側に記録
- 棚上げ判断（C → 対象外）になった項目は対象外テーブルに移動

候補追加時のフォーマット:

````markdown
### {Tier}-{N}. {タイトル}

**動機**: {現在の不便 / 欲しい価値}
**案**: {具体的な実装方針}
**工数**: 小 / 中 / 大
````
