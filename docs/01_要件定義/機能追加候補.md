# 機能追加候補（バックログ）

最終更新: 2026-05-07（A-1 / A-5 / A-6 / A-7 実装済み削除）

将来の機能追加候補を整理した棚卸しリスト。要件定義（[要件定義書.md](要件定義書.md)）に未掲載のアイデアと、既存機能の "あと一歩" 改善をまとめる。**個人 LAN ソロツール**という制約下で意図的に非対応とする項目も明示する。

優先度の判断基準:
- **A（高）**: 既存機能の延長で利得が見込め、工数が中以下。すぐに着手可能
- **B（中）**: 工数中〜大、設計の見直しが必要、一定の利得あり
- **C（低）**: 工数大、利得が中程度、要望が出てから検討
- **対象外**: 信頼モデル（個人 LAN ソロ）と整合しない、または重複機能で意図的に排除

## A. 既存機能の "あと一歩"（高優先・低工数）

### ~~A-1. 読書状態フラグ（未読 / 読書中 / 読了）~~（2026-05-07 実装完了）

`meta.json` に `read_state: 'unread' | 'reading' | 'done'` を追加し、`POST /api/meta/view` で `unread → reading`、Reader の最終ページ到達で `reading → done` を自動遷移する。後方互換のため未設定エントリは `view_count` から派生扱い。詳細は [API 仕様書 §2.6 / §2.7](../03_詳細設計/API仕様書.md) / [詳細設計書_バックエンド編 読書状態](../03_詳細設計/詳細設計書_バックエンド編.md) / [詳細設計書_フロントエンド編](../03_詳細設計/詳細設計書_フロントエンド編.md) 参照。

### A-2. 書籍ノート / 自由テキストメモ

**動機**: 「この巻はラスト 30 ページが面白い」「次回読むときの注意」などの個人メモを書籍に紐付けたい

**案**: `meta.json` に `note: string` を追加。書籍カードまたは編集ダイアログから編集

**工数**: 小。`meta_store.merge_entry_fields` に 1 フィールド追加するだけ

### A-3. PDF のページ並び替え

**動機**: 現在「ページ削除」はあるが「ページ順序変更」がない。スキャン取込でズレた順序の修正に使える

**案**: 編集モードに DnD（dnd-kit）で並び替え、保存時に PDF を再構成

**工数**: 中。既存の編集モードに DnD 拡張

### A-4. 書籍レーティング（★1〜5）

**動機**: 「お気に入り」は 0/1 のトグルのみ。「面白さの度合い」を表現できない

**案**: `meta.json` に `rating: 0..5` を追加。書籍カードに星表示、ソート種別「レーティング順」追加

**工数**: 小。データ追加 + UI 1 箇所

### ~~A-5. 関連書籍の表示~~（2026-05-07 実装完了）

最終ページ到達時に「同シリーズ / 同作者 / 共通タグ」の関連書籍をフローティングパネルで提示。詳細は [詳細設計書_フロントエンド編 関連書籍パネル](../03_詳細設計/詳細設計書_フロントエンド編.md)。

### ~~A-6. シリーズ未分類候補レポート~~（2026-05-07 実装完了）

`GET /api/series/unresolved-candidates` を新設。`SERIES_MIN_PREFIX_LEN=5` 未満のプレフィックスや巻数パース失敗で漏れたペアを `reason` 付きで返す。ToolsMenu の「未分類候補をレビュー」ダイアログから既存 `BulkSeriesAssignDialog` で手動シリーズ化に繋ぐ。詳細は [API 仕様書 §3.6](../03_詳細設計/API仕様書.md) / [詳細設計書_バックエンド編 unresolved_candidates 節](../03_詳細設計/詳細設計書_バックエンド編.md) / [詳細設計書_フロントエンド編 UnresolvedSeries 節](../03_詳細設計/詳細設計書_フロントエンド編.md)。

### ~~A-7. バックエンドログのファイル永続化~~（2026-05-07 実装完了）

`backend/data/logs/app.log` への永続化を [ADR-0006](../02_基本設計/ADR/0006_backend-log-file-persistence.md) で決定し実装済み。詳細は [詳細設計書_バックエンド編 §1.4](../03_詳細設計/詳細設計書_バックエンド編.md) / [運用ガイド §5](../04_環境構築/運用ガイド.md)。

## B. 中規模の機能追加（中優先・中工数）

### B-1. PDF 分割

**動機**: PDF 結合（merge）は実装済みだが、分割（split）は無い。長大な合本を巻ごとに分けたい

**案**: 編集モードで「ここから新 PDF」マーカーを置き、保存時に 2 つ以上の PDF に分割

**工数**: 中。merge の逆処理 + UI 設計

### B-2. メタデータの一括インポート（CSV / JSON）

**動機**: 現在エクスポートは `/api/meta/export` で実装済みだが、インポートが無い。他環境から移行する手段が無い

**案**: `/api/meta/import` を新設し、JSON ファイルアップロード → 既存メタとマージ（衝突解決ポリシーは upsert / overwrite / skip 選択）

**工数**: 中。バリデーション + マージロジック + UI

### B-3. キーボードショートカット カスタマイズ

**動機**: 現在のショートカット（`Ctrl+F`、`f`、`?`、`s`、矢印、↓↑、Esc など）は固定。利用頻度や好みに応じてカスタマイズできない

**案**: localStorage に key-action マップを保存。設定画面で編集

**工数**: 中。useReaderShortcuts の汎化が必要

### B-4. タグの階層化（タクソノミー）

**動機**: 現在タグはフラット。例「ジャンル: ファンタジー」「気分: ライト」のように二次元化したい

**案**: タグを `category:value` 形式（例: `genre:fantasy`）にし、UI 側で category ごとに表示色 / フィルタを分ける。下位互換のため既存タグは `untagged:*` 扱い

**工数**: 中〜大。データ移行 + UI 大幅変更

### B-5. 画像ベース書籍の検索

**動機**: image-only モード（`generated` ソース）で全文検索ができない。novel ソースは Searchable PDF で検索可能だが、image ソースはタイトル・作者・タグのみ

**案**: `generated` ソースにも yomitoku を任意適用するオプションを設ける（同人誌は文字が少ないため取りこぼし許容）

**工数**: 中。OCR バッチ処理を image-only に対応 + 検索 API 拡張

## C. 大規模 / 要望待ち（低優先・大工数）

### C-1. PWA 対応 / オフライン閲覧

**動機**: PC を移動する際にライブラリをローカルにキャッシュしたい

**案**: Service Worker でメタデータと一部 PDF をオフラインキャッシュ

**工数**: 大。バンドル管理・キャッシュ戦略・更新通知が必要

### C-2. モバイル UI 最適化

**動機**: 現在は PC 想定の UI、スマホでは閲覧に耐えるが操作性が低い

**案**: ブレイクポイント別レイアウト、タッチジェスチャー（スワイプでページ送り）

**工数**: 大。デザイン全般の見直し

### C-3. 多言語 OCR 対応

**動機**: yomitoku は日本語縦書き特化。英語マンガなどは OCR できない

**案**: Tesseract / PaddleOCR 等を併用、書籍ごとに OCR エンジン選択

**工数**: 大。OCR エンジン抽象化 + 言語判定

### C-4. ePub サポート

**動機**: Kindle 経由ではなく ePub 直接読み込み

**案**: ePub → 画像変換または ePub Reader 統合

**工数**: 大。新フォーマット対応はパイプライン全体に波及

### C-5. AI タグ自動生成

**動機**: タグ手入力は手間。書籍内容（表紙画像 + メタデータ）から AI 推論で候補提示

**案**: Gemma 4 Vision または OpenAI Vision で表紙画像 + タイトルから候補生成

**工数**: 中〜大。プロンプト調整 + UI 確認フロー

### C-6. 読書統計ダッシュボード

**動機**: 「今月何冊読んだ」「どの作者を多く読んでいるか」のサマリ画面がない

**案**: `/api/stats` エンドポイント + ダッシュボードページ

**工数**: 中。集計ロジック + チャート（Chart.js 等）導入

### C-7. アクセシビリティ（a11y）強化

**動機**: 現状アイコンのみのボタン（80 箇所程度: ReaderHeader / LibraryBulkActionBar / PdfCardActionButtons 等）が `title=` 属性のみで運用されており、`aria-label` 併用なし。スクリーンリーダー対応が弱い。詳細・対応順序は [詳細設計書_フロントエンド編 §改善候補「アクセシビリティ」](../03_詳細設計/詳細設計書_フロントエンド編.md)。

**案**:
1. `eslint-plugin-jsx-a11y` 導入で機械的検出
2. アイコンのみボタンに `aria-label` 付与
3. ランドマーク `role`（main / navigation / complementary）設定
4. フォーカストラップ（Dialog 内 Tab 巡回の閉じ込め）

**工数**: 大。80+ 箇所の改修 + ESLint ルール対応。個人 LAN ソロツール前提では当面受容可、LAN 外公開時に着手判断

### C-8. 大規模 Panel の presentation/container 分割

**動機**: `LibraryPanel.tsx` (417 行) / `ReaderPanel.tsx` (365 行) は Phase 50 / 53 / 54 で hook 抽出を繰り返し**ロジック層は十分薄いが、JSX 部分が支配的**で行数が下がらない。テスト整備計画書 §1 でも「pages / 大規模 Panel は個別 hook + 子コンポーネントで担保、E2E は別途検討」と明記済み。

**案**: presentation コンポーネント (純粋 JSX) と container コンポーネント (state / handler 受け取り + 子へ橋渡し) に分割。例: `LibraryPanel` → `LibraryPanelView` (presentation) + `LibraryPanel` (container)。

**工数**: 中〜大。利得（テスト容易性 / レビュー容易性）が JSX 比重 125 行を分割するコストに見合うかは要検討。**現状は [Phase 50 / 53 のスキップ判断](../06_リファクタリング/リファクタリング履歴.md) で「利得薄」として保留継続**。E2E (C-9) を導入したら相対的に利得が増える可能性あり

### C-9. E2E テスト導入（Playwright）

**動機**: 現状フロントは vitest 単体テスト 744 件で hooks / 子コンポーネントを担保しているが、`pages/*` (GeneratorPage / HitomiPage / OCRPage / ViewerPage) と大規模 Panel (LibraryPanel / ReaderPanel) は**意図的にスコープ外**で 0% カバレッジ（[テスト整備計画書 §9](../06_リファクタリング/テスト整備計画書.md) / [テスト整備計画書_フロントエンド編 §9](../06_リファクタリング/テスト整備計画書_フロントエンド編.md)）。ユーザー操作の golden path 自動検証が無い。

**案**: Playwright で「PDF 生成 → ライブラリ閲覧 → メタ編集 → リーダー → ページめくり」等の E2E シナリオを 5〜10 件構築。`backend/data/` を fixture として用意し localhost:8090（リリース統合）で実行。

**工数**: 大。Playwright 環境構築 + シナリオ設計 + CI（あれば）統合 + flaky test 対策。**現状は判断保留**。導入判断基準は別途。

## 対象外（信頼モデル / 過剰設計の排除）

以下は **個人 LAN シングルユーザーツール** の前提と整合しないため意図的に作らない（[ADR-0001](../02_基本設計/ADR/0001_react-vite-typescript-frontend.md) / [ADR-0002](../02_基本設計/ADR/0002_fastapi-backend.md) / [セキュリティ設計書 §1](../03_詳細設計/セキュリティ設計書.md)）:

| 項目 | 理由 |
|---|---|
| ユーザーアカウント / 認証 / 認可 | LAN 内シングルユーザー前提 |
| マルチテナント・データ分離 | 同上 |
| API レート制限 | 単一クライアント前提 |
| WebSocket / SSE による進捗通知 | ポーリングで十分 |
| GraphQL API | REST で要件を満たす |
| API バージョニング | クライアント単一 |
| マイクロサービス分割 | 規模に対し過剰 |
| Kubernetes / Docker Compose 化 | LAN ローカル起動で十分 |
| 公開 PR テンプレート / Issue テンプレート | ソロ開発 |
| Storybook | コンポーネント数が爆発しない範囲 |

## 運用方針

- 候補が **A-N → 対応決定** になったらリファクタリング計画書ではなく、新機能として `feat:` プレフィックスのコミットで実装
- 実装後は本ファイルから対応済み項目を削除し、[要件定義書.md](要件定義書.md) §3 に追記
- 棚上げ判断（C → 対象外）になった項目は対象外テーブルに移動

候補追加時のフォーマット:

````markdown
### {Tier}-{N}. {タイトル}

**動機**: {現在の不便 / 欲しい価値}
**案**: {具体的な実装方針}
**工数**: 小 / 中 / 大
````
