# 機能追加候補（バックログ）

最終更新: 2026-05-11（B-9 実装完了 + 全件バッチ完了 / B-10 を B-9 で代替されたため折りたたみ / **B-11 Query Expansion 採用**（gemma4:e4b で +2.4 秒、抽象質問の recall 改善）/ **B-12 IQ4_XS 採用完了** / **B-13 段階 A 採用完了** / ADR-0008 設計書 HTML 配信構成 を新設 / VRAM 22GB→12GB 全面訂正）

将来の機能追加候補を整理した棚卸しリスト。**個人 LAN ソロツール / 同人誌特化** という制約下で何を作り、何を作らないかを明示する。

優先度の判断基準:
- **A（高）**: 新方針の核機能。すぐに着手する
- **B（中）**: 工数中〜大、設計の見直しが必要、一定の利得あり
- **C（低）**: 工数大、利得が中程度、要望が出てから検討
- **対象外**: 信頼モデル / 同人誌特化方針と整合しない、または重複機能で意図的に排除

小説 RAG 関連の検討時は実機ベンチマーク・モデル選定の知見を [小説RAG_技術知見.md](../05_記録/小説RAG_技術知見.md) に蓄積している。判断材料として参照する。

### ~~B-6. 小説 RAG: ローカル `num_ctx` 拡大による map-reduce 廃止~~（2026-05-10 検証完了 → 採用）

**結果**: `num_ctx=131072` で **prompt 70k tokens を切り詰めなしで完走、OOM なし、5 分弱**を実機確認。`summarizer.py` を 1-shot 経路をデフォルトに切替（>200,000 字の異常な本文に限り map-reduce にフォールバック）。

**改善幅**: 1 冊あたり 369s → 287s（**~22% 高速化**）かつ **チャンク間の文脈共有が完全** に。実機比較で「父王の奇策 → レティ女王指名 → 派閥構造 → デュークの板挟み → 親友フリートの手切断 → 騎士の誓い」のような **因果連鎖を捉えた要約** が得られるようになり、map-reduce 版より構造把握が大幅に深い。ハルシネーション率は 1-shot 版でも 0%（実機検証）。

**副産物**: B-8〜B-11 の検索品質改善案も同 num_ctx 拡大を前提に成立。

### B-7. 小説 RAG: クラウド LLM 移行の再検討（要件見直し含む / 検証段階）

**動機**: ローカルでは context window の制約で「部分読み」になる構造的課題がある。DeepSeek V3.x / V4 等のクラウド API は **入力 ~$0.30/M token / 出力 ~$1.20/M token** 程度で、全 11 冊フル context を 1-shot で読ませても **月数百〜数千円** で収まる試算。応答時間も短縮される。

**前提変更**: 移行する場合は [要件定義書 §1.3](小説テキスト検索・RAG機能.md) 「ローカル完結（性的描写を含む可能性があるためクラウド AI を使用しない）」の前提を見直す必要がある。

**判断材料**:
- DeepSeek の content policy は西側より緩めだが、明示的な性的描写は refuse される可能性あり
- Kindle 購入小説の全文を中国側クラウドに送信することの是非
- B-6（ローカル num_ctx 拡大）で同等の品質改善が得られるなら不要
- ハイブリッド構成（ローカル: 性的内容の可能性あり / クラウド: 一般 SF・ファンタジー等）も選択肢

**工数**: 中〜大。`qwen_client` 互換のクラウドクライアント実装 + 環境変数でモデル切替 + content policy エラーハンドリング + コスト監視。要件定義書 §1.3 の更新

**着手判断**: B-6 の検証結果を見てから判断。B-6 で十分なら本項目は対象外候補へ移動

### ~~B-9. 小説 RAG: Contextual Retrieval（チャンクごとの文脈付与）~~（2026-05-11 実装完了 + 全件バッチ完了）

Anthropic 2024-09 ブログの Contextual Retrieval 手法を実装。`chunks.contextual_text TEXT` / `chunks.contextual_generated_at TIMESTAMP` を追加し（既存 DB は `_migrate()` で自動 ALTER）、`services/novel_db/contextualizer.py:generate_chunk_context()` で **gemma4:e4b**（軽量モデル、`NOVEL_DB_CONTEXT_MODEL` で切替）にチャンク + 書籍俯瞰サマリを渡して 80 字程度の位置説明を生成。`make_embedding_input()` で `(contextual_text + "\n\n" + chunk_text)` を組み立て、bge-m3 でバッチ 16 で再 embedding して `chunks_vec` を DELETE → INSERT で更新。CLI `backend/scripts/build_chunk_contexts.py --book | --all | --series --redo` で一括実行。

**モデル選定変更**: 当初 Qwen を想定していたが、Anthropic blog の指針「位置説明タスクは軽量モデルで十分」に従い **gemma4:e4b に切替**。実機 2.7〜2.8 秒/チャンクで、Qwen 想定（30 秒/チャンク）の **~10× 高速化** を実現。

**所要時間（実機計測、最終）**:
- パイロット書籍 1 巻 (202 チャンク): 594 秒（~10 分）
- **全件 2,230 チャンクの一括バッチ: 5,916 秒（98.6 分）**、失敗 0 件、当初想定 19 時間から **~12× 短縮**
- **全 11 冊 100% カバレッジ達成**、avg ctx 長 68 字

**動作確認**:
- パイロット: 「父王が次期女王を発表する場面」→ 1 巻 p11 が distance 最良で top 1
- 全件バッチ後の cross-book retrieval（scope=all、max_per_book=2）:
    - 「ベルナードの裁判での弁護士役」→ 9 巻「提督の商談」p91/92 が top 1-2（実際の裁判編）
    - 「メルディが軍師として活躍」→ 10 巻「二人の軍師」p49/92 が top 1-2（タイトル通り）
    - 「シリーズで最も大きな対立は」→ 巻横断で 5 巻分カバー

**テスト**: `test_novel_db_contextualizer.py`（9 件、応答整形・空入力スキップ・LLM エラー時の空文字返却・embedding 入力組立）。backend pytest **695 → 704 件 全 PASS**。

### B-9. 小説 RAG: Contextual Retrieval（チャンクごとの文脈付与）

**動機**: 現状 `chunks.text` は「ページから 800 字を切り出しただけ」で、書籍内での位置づけ（巻 / シーン / 登場キャラ群）が embedding に含まれていない。Anthropic 2024-09 の Contextual Retrieval 手法では、各チャンクに「この場面は ~巻のソレス裁判編で、ベルナードがレティの弁護を準備している場面」のようなナラティブ位置説明を Qwen で生成し、`位置説明 + chunk_text` を再 embedding することで **検索 recall が 35〜49% 改善** することが報告されている（[出典](https://www.anthropic.com/news/contextual-retrieval)）。

**案**:
- スキーマ: `chunks.contextual_text TEXT` を ALTER ADD
- 新規 `services/novel_db/contextualizer.py`（Qwen で 1 チャンクあたり 50〜100 字の位置説明を生成。プロンプトには `book.summary` をコンテキストとして渡す）
- 全 2,230 チャンク × ~30 秒 = **約 19 時間**（夜間バッチ 1〜2 晩。GPU 占有）
- `bge-m3` で `contextual_text + text` を再 embedding（既存の `chunks_vec` を更新）
- 失敗時は `chunks.contextual_text IS NULL` の chunk を従前の embedding のまま使う（後方互換）

**工数**: 中。実装 1〜2 日 + バッチ 1〜2 晩。B-6 の num_ctx 拡大が前提（`book.summary` をコンテキストに渡せる）

**期待利得**: **検索品質の最大インパクト施策**。RAG 全体の recall・precision を底上げできる。B-5（書籍サマリ）/ B-8（サマリ検索インデックス）と直交（補完関係）

**着手順**: B-8 → B-9 が安全。B-8 で検索強化の効果を体感してから、19 時間バッチを投じる判断

</details>

### ~~B-11. 小説 RAG: Query Expansion（質問前処理）~~（2026-05-11 採用、gemma4:e4b 使用、デフォルト ON）

**動機**: ユーザーの短い質問（例: 「ベルナードの裁判での役割は？」）を、軽量 LLM で「9 巻ソレス王子裁判編 / ベルナード弁護士役 / レティとの連携 / 真犯人特定 …」のような検索クエリ群に展開してから FTS5 / ベクトル検索する。

**狙い**: 抽象質問・関係的質問で **「クエリ ↔ チャンク」の両端から retrieval 堅牢性を強化**:
- B-9（Contextual Retrieval）: chunk 側を強化（embedding に位置説明を含める）
- B-11（Query Expansion）: query 側を強化（複数の検索角度を生成）
- 両方適用で直交効果が累積する

**実装方針**:
- 新規 `services/novel_db/query_expander.py` で gemma4:e4b にプロンプトを投げて拡張クエリを 3 個生成
    - Qwen 想定だと +30〜60 秒だが、短答タスクなので軽量モデルで十分 → **+3〜5 秒** に圧縮
- 元の質問 + 拡張クエリ 3 個 = 計 4 つで `hybrid_search` を実行
- 結果は `(book_name, page_no)` でデデュープ、スコア最大値で並べ替え → `NOVEL_DB_QA_TOP_K` 件に絞り込み
- 設定（環境変数で切替可）:
    - `NOVEL_DB_QA_EXPAND_ENABLED`（デフォルト `true`、品質優先）
    - `NOVEL_DB_QA_EXPAND_N`（デフォルト 3、生成する拡張クエリ数）
    - `NOVEL_DB_QA_EXPAND_MODEL`（デフォルト `gemma4:e4b`）

**プロンプト設計**:
```
次の質問に対し、小説の本文を全文検索 / 意味検索するための短い検索クエリを N 個生成。
- 各クエリは異なる切り口（場面 / キャラ / 行動 / 関係性 / 時期 など）
- 各クエリは 10〜20 字程度のキーワード列
- 元のキーワードを含めても可

質問: {question}
検索クエリ（1 行 1 クエリ、N 行）:
```

**応答時間ペナルティ**: 当初 Qwen 想定で +30〜60 秒と書いていたが、**gemma4:e4b 採用で +3〜5 秒** に圧縮。書籍サマリ生成（4〜6 分）に比べれば誤差レベル。

**フォールバック**: gemma4:e4b 呼び出しが失敗した場合は元の質問だけで通常検索（後方互換）。`NOVEL_DB_QA_EXPAND_ENABLED=false` で完全に無効化可能。

**期待利得**:
- 「主人公の成長」「キャラ A と B の関係性」のような **抽象質問・関係質問** で retrieval recall が改善
- 「page 50 で誰が言った？」のような **具体質問** には影響なし（既存検索で十分）

### ~~B-13 段階 A. 小説 RAG: QA の大量コンテキスト読み込み~~（2026-05-11 採用完了 / B / C は未着手）

**進行状況**:
- **段階 A**（2026-05-11 採用完了）: `NOVEL_DB_QA_NUM_CTX = 16384` / `NOVEL_DB_QA_TOP_K = 32` に切替。**scope=all で発生していたプロンプト切り詰めを解消**（ベースラインの `prompt_eval` が ctx 上限 8,192 にぴったり張り付いていたのを実機計測で確認）。応答時間ペナルティはほぼなし
- 段階 B / C: 必要性を見て後日検討

**実機ベンチマーク**（段階 A 採用前 vs 後）:

| クエリ | Before（top_k=16/ctx=8k）| After（top_k=32/ctx=16k）| 変化 |
|---|---|---|---|
| scope=all 概括（「シリーズ全体を通したレティーツィアの成長」）| prompt_eval=**8,192**（切詰）/ 135s / 2,556 chars | prompt_eval=**10,833**（完全）/ **131s** / 2,274 chars | ✅ 切詰解消、時間 -3% |
| scope=all 特定キャラ（「デュークが忠誠を誓うまでの心情変化」）| prompt_eval=**8,192**（切詰）/ 136s / 2,634 chars | prompt_eval=**10,915**（完全）/ 153s / 2,760 chars | ✅ 切詰解消、+12% で詳細回答 |
| scope=book 単冊（「アストリッドが救われる過程」）| 2,960 / 98s / 1,871 chars | 3,592 / **74s** / 1,301 chars | ✅ ctx 余裕、時間 -24% |

**重要な気づき**: ベースラインの scope=all で `prompt_eval` が num_ctx 上限の **8,192 にぴったり** 張り付いていた事実から、**従来は QA プロンプトの 16,676/16,809 文字（推定 ~10k〜15k tokens）が入力時点で切り詰めされていた** ことが判明。段階 A はそれを解消した（切り詰めバグ修正に近い改善）。

**動機**: B-6 で **Qwen が num_ctx=131,072 で 1 冊丸ごと（実測 70k tokens）を 1-shot で完走できる** ことを実機検証済み。一方、従来の QA エンドポイントは:
- `num_ctx=8,192`（控えめ、切り詰めリスクあり）
- `top_k=16` ページ抜粋
- ヒット書籍のサマリのみ

つまり Qwen の context 容量にはまだ **10 倍以上の余裕がある**。検索ヒットだけに依存せず、もっと大量のページ・サマリを読ませることで、特に概括質問・巻横断質問の回答品質が更に上がるはず。

**現状の context 内訳（推定）**:
- top_k=16 ページ抜粋: ~10,000 字 ≒ ~6,500 tokens
- 書籍俯瞰サマリ（ヒット書籍のみ、5〜8 冊分）: ~8,000〜12,000 字 ≒ ~5,000〜8,000 tokens
- システムプロンプト + 質問: ~1,000 tokens
- 合計: **~12,500〜15,500 tokens / num_ctx=8,192 を超えるため切り詰めされている可能性**

**3 つの段階的拡張案**:

| 段階 | 設定 | 想定 context | 応答時間 | 期待効果 |
|---|---|---|---|---|
| **A（小幅、即効）** | `num_ctx=16,384` / `top_k=32` / 全 11 冊サマリ常時挿入 | ~25k tokens | +20〜30% | 切り詰めの解消 + 全書籍俯瞰の網羅 |
| **B（中規模）** | `num_ctx=32,768` / `top_k=64` / 全サマリ + 同書籍内 top 5 ページ | ~50k tokens | +50〜80% | 概括質問の深さ向上 |
| **C（大規模）** | `num_ctx=131,072` / `top_k=200` / 全サマリ + ヒット書籍は **全 page 読み込み** | ~100k tokens | **+150〜250%**（80 秒 → 200〜300 秒）| 「この書籍について詳しく」レベルで本文丸読み |

**実装方針**:
- `NOVEL_DB_QA_NUM_CTX` / `NOVEL_DB_QA_TOP_K` を環境変数で切替可能に
- 段階 C は scope=book のとき特に効く（1 冊 = ~70k tokens、num_ctx=131k に余裕で収まる）
- 段階 A から実装・検証し、品質改善が見えれば段階 B / C に進む
- 「該当書籍の全 page を context に入れる」モードを scope=book でオプション提供
- 応答時間が許容できるかは user 判断（QA は対話的なので応答時間とのトレードオフ）

**実装時の検証項目**:
- 同じ質問を A / B / C で投げて回答品質を比較（特に概括質問）
- ハルシネーション率の変動（context を増やしすぎると逆効果のケースもある）
- VRAM 使用量（num_ctx を上げると線形に増える）
- 応答時間の体感影響

**期待利得**:
- 「シリーズ全体のキャラクター関係性の変遷」のような **複数書籍にまたがる巨視的な質問** の回答品質向上
- 「この書籍の主人公の心情の変化を詳しく」のような **1 冊内の深掘り質問** で本文丸読みによる精緻な回答
- B-9（Contextual Retrieval）と並ぶ、retrieval ではなく **生成側** の品質強化施策

**工数**: 小〜中。実装は config 変数追加 + LLM_OPTIONS 切替 + プロンプト構築の調整。検証に時間を要する（質問パターンごとに A/B/C を試す）

**着手判断**: B-12（Qwen 高速化）と組合せれば応答時間ペナルティを相殺できるため、B-12 完了後に B-13 を試すのが筋良い
