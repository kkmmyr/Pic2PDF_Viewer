## 2026-05-17: change — タイムスタンプ全面 JST 化

### 変更内容

- **バックエンド**: DB 書き込み時刻をすべて JST に統一
  - SQLite: `datetime('now')` → `datetime('now', '+9 hours')`、`CURRENT_TIMESTAMP` → `(datetime('now', '+9 hours'))`
  - Python: `datetime.now(UTC)` / `datetime.now()` → `datetime.now(JST)` （`utils/dt.py` の `JST`/`jst_now()` 経由）
  - 対象ファイル: `schema.py`, `qa_history.py`, `builder.py`, `full_builder.py`, `qa_sessions.py`, `job_queue.py`, `job_worker.py`, `summarizer.py`, `character_summarizer.py`, `scripts/build_chunk_contexts.py`, `discussion_service.py`, `relation_extractor.py`, `meta_db_backup.py`, `routers/meta.py`
- **フロントエンド**: `parseSqliteUtc` がタイムゾーン情報なし文字列に `+09:00` を付与（従来は `Z`）
  - `FinishedJobCard`, `RunningJobCard`, `NovelManagePage` の raw `new Date()` を `formatSqliteUtcAsJst` に統一
- **新規**: `backend/utils/dt.py` — `JST = ZoneInfo("Asia/Tokyo")` と `jst_now()` ラッパー
- **設計書更新**: API仕様書に「共通仕様 > タイムスタンプ形式」節を追加

### 注意事項

移行前（UTC 保存）の既存 DB レコードはタイムゾーン接尾辞がないため、JST として解釈され 9 時間早い表示になる。rebuild 後のデータから正しい JST 時刻に切り替わる。

## 2026-05-15: refactor(backend) — Phase 66 Alembic 導入（novel.db マイグレーション管理）

### 変更内容

- `backend/alembic.ini` / `backend/alembic/env.py` / `backend/alembic/script.py.mako` 新規作成（Alembic 設定）
- `backend/alembic/versions/0001_initial.py` 新規作成: 旧 `_migrate()` 相当の操作を idempotent revision として実装
- `backend/services/novel_db/migrations.py` 新規作成: `upgrade_head()` ヘルパー（起動時呼び出し）
- `backend/services/novel_db/schema.py`: `_ddl()` を全カラム含む最新スキーマに更新、`_migrate()` を削除（Alembic に移管）
- `backend/main.py` lifespan: `init_db()` → `upgrade_head()` → `job_queue.start()` の順序に更新
- `backend/pyproject.toml`: `alembic==1.18.4`（+ `sqlalchemy==2.0.49`）を依存に追加

### 設計方針

- **sqlite3 runtime 維持**: アプリケーションコードは引き続き sqlite3 を使用。Alembic + SQLAlchemy はマイグレーション実行のみに利用
- **新規 DB**: `init_schema()` の `_ddl()` が全カラムを含む最新スキーマで CREATE TABLE → Alembic revision は PRAGMA で存在確認し no-op でスタンプ
- **既存 DB**: `_ddl()` は no-op（IF NOT EXISTS）→ Alembic revision が不足カラムを idempotent に ALTER TABLE ADD COLUMN
- **起動中断**: `upgrade_head()` 失敗（DB 破損等）は例外を送出し FastAPI 起動を中断する
- downgrade は pass（intentionally no-op）
- autogenerate 不使用・手書き revision のみ

### 影響範囲

- HTTP エンドポイント変更なし
- テスト: pytest 819 passed（変更なし）
- production DB: `alembic_version` テーブルが追加、revision 0001 がスタンプ済み

## 2026-05-12: perf — B-9 Contextual Retrieval 改良（プロンプト拡張 + skip 判定 + 1 冊 redo 検証）

### 背景

2026-05-11 のデータ層品質チェックで、`chunks.contextual_text` が物語的要約に流れ本文の固有名詞・引用句が落ちる事例が頻発することが判明。実例として Vol 9 p113 の「ベルナードの教え 国民への義務」を含む本命チャンクで、ctx に「ソレスが自由な未来を選ぶ決意を固める場面」のみが入り「ベルナード」「教え」「義務」が一切記録されず、クエリでの検索で 6 位まで沈降していた。さらに Vol 1 p1/p2 の表紙・タイトルページに対し本筋を捏造した ctx が `min_chars=300` フィルタを通過して embedding に残る現象も。

### 変更

#### 1. プロンプト改善（`backend/services/novel_db/contextualizer.py`）

`_CONTEXT_PROMPT` の冒頭に **「必ず含めるべきこと（最重要）」** セクションを追加し、以下を明示指示:
- チャンク本文に登場する **固有名詞**（人名・組織名・地名・役職）を可能な限り入れる

## 2026-05-11: feat(novel_db) — Query Expansion で抽象質問の recall 改善（B-11 採用）

### 内容

QA エンドポイントでハイブリッド検索を実行する前に、軽量 LLM（gemma4:e4b）で
ユーザーの質問から **追加の検索クエリを 3 個生成** し、元の質問と合わせて
合計 4 つのクエリで検索する。結果は `(book_name, page_no)` でデデュープ、
RRF スコアの最大値で並べ替えて `NOVEL_DB_QA_TOP_K` 件に絞る。

抽象質問（「主人公の成長」「キャラの関係性変化」など）では、ユーザーの 1 つの
クエリだけだと semantic 距離が遠い page を取り逃すことがある。複数の角度
（場面 / キャラ / 行動 / 関係性 / 時期）から検索することで recall が改善する。

### 新規 / 変更

- 新規 `services/novel_db/query_expander.py`
- `routers/novel_db.py` qa_endpoint で `NOVEL_DB_QA_EXPAND_ENABLED` 時に展開実行
- `backend/config.py` に 3 つの設定追加:
    - `NOVEL_DB_QA_EXPAND_ENABLED`（デフォルト true、品質優先）
    - `NOVEL_DB_QA_EXPAND_N`（デフォルト 3）
    - `NOVEL_DB_QA_EXPAND_MODEL`（デフォルト gemma4:e4b）

### 応答時間ペナルティ（実測）

候補時点では Qwen で +30〜60 秒を想定していたが、Query Expansion は短答型
タスクなので gemma4:e4b で十分と判断 → 実測 **+2.4 秒/回**（想定 3〜5 秒よりも速い）。

### 動作例（実機）

| 元の質問 | 展開クエリ 1 | 展開クエリ 2 |
|---|---|---|
| シリーズ全体のテーマ | 運命と選択のテーマ | 過去の因縁と和解 |
| ベルナードの裁判での役割 | ベルナード 裁判 証言 | ベルナード 役割 裁判 |
| デュークがレティに忠誠を誓う場面 | デューク レティ 忠誠 誓う | デューク レティ 関係性 場面 |

抽象的な「シリーズ全体のテーマ」では意味的な角度に展開、具体的な「ベルナードの裁判での役割」ではキーワード分解で FTS5 向けに展開、と質問の性格に応じて使い分けが動作している。

### テスト

- 新規 `test_novel_db_query_expander.py` 15 件追加（応答整形 / 空入力 / LLM エラー時の後方互換フォールバック / 元質問が先頭にくる / n 件への制限）
- backend pytest **704 → 719 件 全 PASS**

### B-9 との直交関係

- B-9（Contextual Retrieval）: chunk 側 embedding を強化
- B-11（Query Expansion）: query 側を強化

両方適用で「クエリ ↔ チャンク」の両端から retrieval 堅牢性が累積。

### フォールバック

- LLM 呼び出し失敗時は元の質問だけで検索（後方互換）
- `NOVEL_DB_QA_EXPAND_ENABLED=false` で完全無効化

## 2026-05-11: perf(novel_db) — QA の num_ctx を 8192 → 16384 に拡大 + top_k を 16 → 32 に（B-13 段階 A 採用完了）

### 内容

B-12 で Qwen IQ4_XS に切り替わったタイミングで余裕が出た VRAM / CPU 帯域を、QA 品質向上に投資する。

| 項目 | 旧 | 新 |
|---|---|---|
| `NOVEL_DB_QA_NUM_CTX` | （`llm.py:LLM_OPTIONS` で 8192 ハードコード）| **16384**（config 化、`os.environ.get` で上書き可）|
| `NOVEL_DB_QA_TOP_K` | 16 | **32**（環境変数で上書き可）|

### 実機ベンチマーク（同一クエリで Before / After 比較）

| クエリ | Before（top_k=16/ctx=8k）| After（top_k=32/ctx=16k）|
|---|---|---|
| scope=all 概括 | prompt_eval=**8,192**（**切詰**）/ 135s | prompt_eval=**10,833**（完全）/ 131s |
| scope=all 特定キャラ | prompt_eval=**8,192**（**切詰**）/ 136s | prompt_eval=**10,915**（完全）/ 153s |
| scope=book 単冊 | 2,960 / 98s | 3,592 / **74s** |

**重要な発見**: ベースラインの scope=all クエリで **prompt_eval が num_ctx 上限の 8,192 token にぴったり張り付いていた** = QA プロンプト（実プロンプト 16,676〜16,809 chars）が入力時点で **切り詰めされていた事実が判明**。段階 A はそれを解消する変更（切り詰めバグ修正に近い改善）。

### 評価

- ✅ **切り詰めの解消**: scope=all で 8,192 → 10,833+ tokens（32% 多くのトークンを取り込めるように）
- ✅ **応答時間ペナルティほぼなし**: -3% 〜 +12% の範囲（誤差レベル、想定の +20〜30% より良好）
- ✅ scope=book は速くなった（-24%、GPU キャッシュ温まりの影響）
- 既存サマリ・キャラ・コンテキスト各種は影響なし（生成側だけの変更）

### 段階 B / C（未着手）

- 段階 B: `num_ctx=32768` / `top_k=64` / 全サマリ + 同書籍内 top 5 ページ
- 段階 C: `num_ctx=131072` / `top_k=200` / scope=book で **全 page 読み込み**

段階 A の効果と応答時間を見て、必要なら後日検討。

### ロールバック

```powershell
$env:NOVEL_DB_QA_NUM_CTX = "8192"
$env:NOVEL_DB_QA_TOP_K = "16"
```

を起動時に設定すれば旧設定で動作（backend 再起動必要）。

## 2026-05-11: perf(novel_db) — Qwen LLM を IQ4_XS 量子化に切替（B-12 採用）+ VRAM 認識訂正

### 内容

`bartowski/Qwen_Qwen3.6-35B-A3B-GGUF` から IQ4_XS（18.81 GB）を取得し、Ollama に `qwen3.6-iq4xs` として登録。`backend/config.py` の `NOVEL_DB_LLM_MODEL` 既定値を `qwen3.6:35b-a3b`（Q4_K_M、27GB）→ `qwen3.6-iq4xs`（21GB）に変更。

**速度改善（実機計測）**:
- 書籍サマリ 1 冊（ctx=131k）: 287 秒 → **229 秒**（**-20%**）
- QA 応答（ctx=8k）: 93 秒 → **80 秒**（**-14%**）
- 生成 t/s: 5.4 → 6.2（ctx=131k、+15%）/ 13.8 → 14.6（ctx=8k、+6%）
- プロンプト処理 t/s: 453〜483 → **567〜600**（**+24〜25%**）
- CPU/GPU 比（`ollama ps`）: 61%/39% → **49%/51%**（GPU 比率 +12pt）

**品質確認**:
- 書籍 1 巻サマリを IQ4_XS で再生成（902 chars）し、Q4_K_M 版（1125 chars）と比較
- 主張 8 項目（紫電 / ソルヴェール国 / 毒殺 / ゴズ=エナージー宿主の完全同化 / 騎士の叙任 等）すべて DB ヒット
- **ハルシネーション 0 件**

**運用方針**:
- 既存 11 冊サマリ（Q4_K_M 製）は再生成せず維持（品質体感差ほぼなし）
- 旧 `qwen3.6:35b-a3b` は削除せずロールバック保険として残す
- ロールバックは `NOVEL_DB_LLM_MODEL=qwen3.6:35b-a3b` 環境変数で即時切替可能

- **Step 1（`OLLAMA_FLASH_ATTENTION=1` + `OLLAMA_KV_CACHE_TYPE=q8_0`）**: ベースライン比 ±誤差範囲で効果ゼロ。本機は CPU offload 律速のため GPU 内 attention 最適化は効かない。env var は削除済み

当初 ADR-0007 / 設計書 / 機能追加候補で「VRAM ~22GB」と書いていた箇所が複数あったが、**実態は RTX 5070 で VRAM 12GB のみ**。Ollama が自動で約 61%（旧 Q4_K_M 時）→ 49%（IQ4_XS 後）を CPU 側にオフロードしていた。今回の B-12 検証で正確な状況が判明したため、全箇所を訂正:

- 一方で **Claude が最も頻繁にアクセスする読者** であり、HTML 直書きは Claude の Read/Edit/Grep 効率を落とす（token 膨張・edit 失敗率増・cross-doc 整合チェック精度劣化）
- 「MD ソース + ビルド時 HTML 化」のハイブリッドが両者のメリットを取れる

### 影響

- Markdown 編集後に `mkdocs build` を実行することで HTML が最新化される（リリースビルドの `build_release.bat` 等への組み込みは将来検討）
- 開発者は初回 `uv tool install mkdocs --with mkdocs-material --with mkdocs-mermaid2-plugin` + `uv tool update-shell` のセットアップが必要
- `~/.local/bin` が PATH に通っていないと `mkdocs` コマンドが見つからないため、Windows ではユーザー PATH への手動追加または `uv tool update-shell` 後 PowerShell 再起動が必要

## 2026-05-11: feat(novel_db) — Contextual Retrieval（B-9）を実装

### 内容

Anthropic 2024-09 ブログの Contextual Retrieval 手法を踏襲。各チャンクに書籍俯瞰サマリ（B-5）をコンテキストとして与え、LLM に 80 字程度の位置説明を生成させ、`(contextual_text + chunk_text)` を bge-m3 で再 embedding することで検索 recall を底上げする。

- **スキーマ**（[schema.py](../../backend/services/novel_db/schema.py)）
    - `chunks.contextual_text TEXT` / `chunks.contextual_generated_at TIMESTAMP` 追加。既存 DB は `_migrate()` で自動 ALTER
- **新規モジュール**: [services/novel_db/contextualizer.py](../../backend/services/novel_db/contextualizer.py)
    - `generate_chunk_context(book_name, book_summary, chunk_text, model)`: LLM で位置説明を生成
    - `make_embedding_input(contextual_text, chunk_text)`: `(ctx + "\n\n" + text)` 組立てヘルパ。ctx 欠落時は text のみで後方互換
    - `_clean_response()`: 「位置説明:」「場面:」「出力:」等の前置きを除去 + 1 行目のみ採用
- **新規 CLI**: [scripts/build_chunk_contexts.py](../../backend/scripts/build_chunk_contexts.py)
    - `--all` / `--book` / `--series` / `--redo`、書籍ごとにコンテキスト生成 + バッチ 16 で再 embedding
    - 進捗表示（ctx 進捗 / embedding 完了時間）
- **設定**: [config.py](../../backend/config.py) に `NOVEL_DB_CONTEXT_MODEL = "gemma4:e4b"` 追加。`qwen3.6:35b-a3b` 等への切替可能
- **テスト**: 9 件追加、backend pytest **695 → 704 件 全 PASS**
    - `test_novel_db_contextualizer.py`: 応答整形 / 空入力スキップ / LLM エラー時の空文字返却 / embedding 入力組立
- **設計書反映**: [バックエンド設計 §2.1 / §3 / §4 / §5.8 / §5.9 / §6.1 / §14](../03_詳細設計/小説テキスト検索・RAG機能_バックエンド設計.md) / [機能追加候補 B-9](../01_要件定義/機能追加候補.md) を実装完了に / [小説RAG_技術知見.md](../05_記録/小説RAG_技術知見.md) に手法とベンチマークを追記済

### モデル選定の判断変更

当初は Qwen3.6:35b-a3b を想定していたが、Anthropic blog の指針「位置説明タスクは軽量モデルで十分」に従い **gemma4:e4b に切替**。実機計測で:
- 1 チャンクあたり **2.7〜2.8 秒**（Qwen 想定 30 秒の **~10× 高速化**）
- 全件 2,230 チャンクで **98.6 分**（当初 19 時間想定から **~12× 短縮**）
- 失敗 0 件、全 11 冊 100% カバレッジ、avg ctx 長 68 字

### 動作確認

**パイロット（書籍 1 巻）**:
- avg 63 字 / min 29 字 / max 88 字 の位置説明（target ~80 字）
- 「父王が次期女王を発表する場面」のクエリ → 該当 p11 が distance 最良で top 1
- ランダムサンプル 5 件の `contextual_text` を本文と照合 → 全て整合

**全件バッチ完了後の cross-book retrieval**（scope=all、max_per_book=2）:
- 「ベルナードの裁判での弁護士役」→ 9 巻「提督の商談」p91/92 が top 1-2（実際の裁判編シーン）
- 「メルディが軍師として活躍」→ 10 巻「二人の軍師」p49/92 が top 1-2（タイトル通り）
- 「シリーズで最も大きな対立は」→ 巻横断で 5 巻分カバー
- 意味的に妥当な順位を返す

### 影響

- ベクトル検索の embedding 入力に位置情報が含まれるため、抽象的なクエリ（直接の語彙的一致が無いケース）で該当 page が top に来やすくなる
- `contextual_text` が NULL の chunk は text のみで embedding（後方互換）
- 既存 DB は `_migrate()` で自動的にカラム追加、CLI 実行で順次有効化
- `builder.rebuild_book` で書籍を再構築すると、`pages.main_characters` と並んで `chunks.contextual_text` も道連れで消える。再構築後は CLI で再実行が必要（バックエンド設計 §5.4 にコメント追記済）

  - 選択モード時はカード左上にチェックボックス表示（チェック済み/部分選択=青塗り + 白アイコン、未選択=空枠）
- `docs/03_詳細設計/小説テキスト検索・RAG機能_フロントエンド設計.md` §5.3 を更新

### 影響

- API 変更なし
- 選択機能（作者設定 / シリーズ登録）は全グループモードおよびドリルダウンで利用可能に
