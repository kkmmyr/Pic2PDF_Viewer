## 4. 小説（主戦場）

### 4.0 画面構成

旧 Novel 画面は廃止し、以下の構造に再編する。

```
小説（サイドバートップ）
├ 小説ライブラリ           ← 旧「小説テキスト検索画面」を改名・拡張
│   ├ OCR 全文の検索
│   ├ AI 質問（4.4 でブラッシュアップ）
│   ├ 作者・シリーズの登録／編集（4.3）
│   └ ─[遷移]─→ 閲覧画面（4.1）
│                ├ 表紙クリックからの通常閲覧
│                └ AI 根拠ページからのジャンプ閲覧
│                   （画像見開きビューワー、ジャンプ後は自由めくり）
└ OCR 画面
    └ OCR 実行 / 棚卸し対象（4.2）
```

### 4.1 閲覧機能

| 用途 | 内容 |
|---|---|
| 通常閲覧 | 小説ライブラリで表紙をクリックして本文を見る |
| AI 根拠ページのジャンプ閲覧 | AI が「このページを参照しました」と返したとき、そのページへ飛んでから **自由に前後をめくれる** |

- 表示は **画像見開きビューワー**（同人誌と同じ感覚）
- 「周辺 N ページに固定」ではなく、ジャンプ後は本一冊を自由に閲覧できる動線

### 4.2 インポート / OCR の棚卸し（作業中）

- 技術検証を重ねた結果、OCR が **何をどう動かしているか不明瞭** な状態
- やること:
  1. **現状把握**（何が動いて何が死んでいるか）
  2. **理想形に向けた再設計案** が書けるまで整理する（C1）

**2026-05-12 作業中（未コミット）**: `builder.py` を `ocr_book()` + `rebuild_from_pages()` の 2 ステップに分離。
- `ocr_book()`: images/*.png → OCR → `pages.full_text` を更新。`ocr_done_at` カラム新設。
- `rebuild_from_pages()`: `pages.full_text` → chunk → embed → `chunks/chunks_vec` を再構築。
- `RebuildJobMode` に `'rebuild'` / `'ocr'` を追加（旧 `'pdf_text'` / `'reocr'` は後方互換で残置）。
- 13 ファイル変更中。テスト通過確認後にコミット予定。

### 4.4 AI 分析のブラッシュアップ

| 観点 | 内容 |
|---|---|
| 現状 | ページ単位 RAG。効率が悪そう |
| 方針 | 全文 OCR がある前提で、より適切な単位にする |
| 制約 | 「根拠ページ特定」は必ず残す（4.1 の閲覧機能とつながる） |
| 評価軸 | **回答精度 + 主観的な使い心地** が主。速度は致命的でない限り許容（E1） |
| 移行 | 新方式に移ったら、現状のページ単位 RAG は **撤去**（E2） |

#### 単位の候補（実験して決める）

| 方針 | 概要 |
|---|---|
| (a) Qwen に分割判断を任せる | 「章 / シーン / 場面の切れ目を見つけて返して」と Qwen に問う |
| (b) Qwen は別用途、分割は決定論的に | 固定文字数 / sentence-splitter / 章タグ検出 等 |

ユーザーの当初イメージは (a) だが、決定ではない。**(b) の方が品質が高ければ (b) を採用**（E3）。

「1 冊全文を Qwen に読み込ませた上で、RAG に適した文字数で分ける」やり方が成立するかを実機検証する。

### 4.5 本構築処理の統合

#### 現状（バラバラに走っている処理）

backend/scripts/ に **個別の CLI バッチ** として並んでいる:

| スクリプト | 役割 | LLM |
|---|---|---|
| `build_novel_db.py` | novel.db 基礎構築（チャンク化 / OCR 取込） | - |
| `build_novel_summaries.py` | 書籍サマリ（あらすじ）生成 | Qwen |
| `extract_characters.py` | ページごとの登場人物抽出 | gemma4:26b |
| `build_character_summaries.py` | キャラごとの人物サマリ (B-15) | Qwen |
| `build_chunk_contexts.py` | チャンク位置説明 (B-9) | gemma4:e4b |

→ それぞれが別プロセスで本を読み直して LLM に投げており、効率が悪い。検証時に作っただけで現状正しく動いていない可能性もあるため、**この整理の中で確認する**（F2）。

#### 統合後の姿

- **1 冊 = 1 Qwen セッション** で読み込み → 要約 / 人物 / RAG 用文脈をまとめて処理
- 現状の **gemma 系処理（人物抽出 / チャンク文脈）も Qwen 側に寄せる**（速度が極端に遅くならない範囲、F1-a）
- 統合処理は **UI から起動できるジョブキュー** にする（バックエンド設計書の Phase D3-2 と合流、F1-b）

#### セッションの開閉タイミング = パターン A（F3）

```
本をインポート
  ↓ Qwen セッション開く（本一冊を prefill）
  ↓ 要約 + 人物 + RAG 用文脈をまとめて生成
  ↓ DB に保存
  ↓ セッション閉じる
それ以降の質問は別途新セッション（DB を参照しつつ Qwen に問う）
```

→ 同一セッション内では、**ベース状態を共有して分岐質問** を投げる使い方をする（rewind 的活用）。

#### KV cache の永続化はしない（2026-05-12 結論）

「本ごとに KV cache を SSD 保存して、次回質問時に読み込めば prefill をスキップできるのでは」というアイデアは検討したが **採用しない**:

- 想定蔵書数は **数百冊** スケール（現状 11 冊は検証用）
- 1 冊あたり KV cache は数 GB（`-ctk q8_0 -ctv q8_0` 適用済みでも） → **TB 級ストレージ** が必要で非現実的
- モデル / 量子化 / context パラメータの変更で cache 無効化されるので保守コストも重い

代わりに採用する方針:

- **都度 prefill** が前提（prefill 速度は B-14 / `-ncmoe` 等で既に最適化済み）
- rewind = **同一セッション内のベース状態分岐** に限定して使う
- セッションを閉じたら KV cache は捨てる、開けば再 prefill する

llama.cpp 側の関連機能（参考）:

| 機能 | 用途 |
|---|---|
| `--prompt-cache <file>` | prompt 処理後の KV cache をファイル保存（CLI） |
| `llama_state_save_file` / `llama_state_load_file` (API) | プログラムから状態を保存・復元 |
| `llama_kv_cache_seq_cp` (API) | sequence 単位で cache をコピー（= 分岐） |

llama-server (HTTP API) でこれをどう扱うかは別調査が必要（`cache_prompt: true` で同セッション内の連続リクエスト間の cache 再利用は可能）。

## 5. 進める順序

全体は **整理した時点で見えてくるのを待つ** スタンス。ただし以下の **最低限の依存関係** だけ確定している:

```
4.4 AI 分析の単位を決める（実験して (a) / (b) を比較）
        ↓
4.5 統合処理を実装（決まった単位で「インポート時 1 回きり」の中身を作る）
```

4.5 は「インポート時 1 回きりで要約 + 人物 + RAG 用文脈をまとめて生成」する設計なので、**生成する単位（4.4）が決まらないと中身が固められない**。
