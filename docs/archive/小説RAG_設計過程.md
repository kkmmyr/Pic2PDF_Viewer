## 1. 当初の設計判断（Why）

### 1.1 全体アーキテクチャの選択理由

- **既存 FastAPI に組み込む理由**: hitomi 監視は単発タスクなので別プロセスにしたが、本機能は対話型 API（検索・質問）が主で、リクエスト都度の応答が必須。組み込みが自然。
- **SQLite + FTS5 + ベクトルを選んだ理由**: PoC で SQLite + FTS5 + sqlite-vec を検証し十分な性能（11 冊で約 10MB、検索 < 1 秒）を確認。後に §5 の通り LanceDB へ移行。
- **bge-m3 を採用した理由**: PoC で `nomic-embed-text` と比較し、日本語意味検索精度が明確に高い（OCR ミスを意味距離で吸収可能）。
- **質問応答に Qwen3.6:35b-a3b を採用した理由**: 当初 PoC で gemma4:26b を採用したが、シリーズ全体の概括質問（「テーマ」「主人公の成長」等）への回答が浅かった。Qwen3.6:35b-a3b（35B 総 / 活性 3B MoE）に切替えたところ `done_reason='stop'` で完走し、章ごとの対比・具体例引用を含む構造的回答が得られた。応答時間は 30〜100 秒 → 80〜130 秒に伸びたが品質向上が上回った（[ADR-0007](../design/基本設計/ADR/0007_llm-extraction-qwen-adoption.md)）。
- **主要登場人物抽出に軽量 Gemma を採用した理由**: 短答型タスク（人名リスト出力）で重量モデルは過剰。1300 ページ超の一括抽出を現実的時間で回すため軽量モデルが必須。
- **LLM クライアントを共通モジュールに切り出した理由**: Qwen3.x は thinking モデルで `stream=True` / `think=False` の併用が必須。`num_predict` を thinking ブロックに食い潰される事故が起きやすく、地雷を踏む呼び出しを各プロジェクトで再実装したくなかった（[ADR-0007](../design/基本設計/ADR/0007_llm-extraction-qwen-adoption.md)）。
- **全体ロック + ジョブキューを選んだ理由**: SQLite WAL でもベクトル更新の書き込みは GPU/CPU を高負荷で消費するため並列は逆効果。ロック粒度を書籍単位にする利得は薄く、クライアントに「再構築中」を示せば UX は十分。

### 1.2 sqlite-vec → LanceDB 移行（Phase 62、2026-05-14）

当初はベクトルも SQLite 内の sqlite-vec（`chunks_vec` / `book_summaries_vec` の vec0 仮想テーブル）に格納していた。Phase 62 でベクトル部分のみ LanceDB（`novel.lancedb` の `chunks` / `summaries` テーブル）へ分離。FTS5・メタデータは SQLite に残した。

- **移行理由**: sqlite-vec の vec0 は線形スキャン O(n) で ANN インデックスを追加できない。LanceDB は 50,000 チャンク超で IVF_PQ が自動ビルドされ ANN 検索が有効化される。
- 移行に伴い `serialize_f32` 手動シリアライズが不要になり、`get_chunks_table().add([...])` / `delete(...)` で扱えるようになった。現行スキーマは [データ設計 §1.2](../design/詳細設計/機能別/小説RAG_データ.md)。

## 2. チャンク戦略の実験（§5.2、2026-05-12）

現行の本番方式はページ単位 `chunk_page`（800 字 / overlap 50）。これに対しクロスページ方式 `chunk_book`（1200 字 / overlap 120、bisect で page_id 解決）と、Qwen 意味セグメンテーション `chunk_qwen`（1 冊全文を Qwen に送り章・場面の境界ページを JSON で返させ、境界ごとに `chunk_book` でサブ分割）を比較した。

比較スクリプト: `backend/scripts/eval_chunk_strategy.py --qwen`。

**実験結果**: 書籍「おこぼれ姫と円卓の騎士 1」(118 ページ / 115,256 字) で 3 方式を比較（クエリ: 「父王が次期女王を発表する場面」）。

| 方式 | チャンク数 | avg文字数 | top1 スコア |
|---|---|---|---|
| 現状 `chunk_page` | 202 | 594字 | **0.5824** (p11) |
| 実験B `chunk_book` | 109 | 1176字 | 0.5558 (p11) |
| 実験A `chunk_qwen` | 109 | 1172字 | 0.5558 (p11) |

Qwen が識別した境界: `[13, 41, 74, 107]`（p74 = 「第三章 騎士と暗殺者」の実際の章頭）。

**考察**:
- この書籍はページあたり平均 ~980 字と密度が高く、ページ単位でも十分なコンテキストが得られるため `chunk_page` が最高スコアを維持。
- `chunk_qwen` は境界識別精度は高い（章頭と一致）が、セグメント数が少ない（4 点）ためチャンク数・avg 字数が `chunk_book` とほぼ同一に収束した。
- ページ密度が低い書籍（挿絵多め・会話主体、平均 300〜500 字/ページ）では `chunk_book` / `chunk_qwen` の優位性が出る可能性あり。

**決定**: `chunk_page` を本番方式として維持。`chunk_book` / `chunk_qwen` は実験コードとして `chunker.py` に残し、必要時に再検証できるようにする（現行コードでも `chunk_book` は残置）。

## 3. 俯瞰質問の天井 — B-5 → B-8 → B-9 の三段改善史

`scope=all` / `scope=series` での「シリーズ全体のテーマ」のような概括質問は、ハイブリッド検索が拾える少数のページ抜粋に依存するため、全 11 冊・1359 ページを俯瞰しきれない構造だった。これを 3 段階で改善した。

### 3.1 B-5（2026-05-10）書籍俯瞰サマリの事前生成

**なぜ必要か**: `top_k` 件のページ抜粋では全冊を俯瞰しきれない。Qwen 切替で踏み込みは改善したが、検索コンテキスト依存である限りシリーズ全体を網羅した回答は本質的に難しい。事前に各冊の要約を作れば、scope=all/series で「全冊あらすじ + ヒットページ抜粋」を渡せる。

各冊を 1500 字程度に要約して `books.summary` に保存し、QA プロンプト先頭に `【書籍俯瞰サマリ】` ブロックとして埋め込む。**B-6 検証（2026-05-10）で 1-shot 経路に切替**（全文を `num_ctx=131072` で丸ごと Qwen に渡す。>200,000 字のみ map-reduce フォールバック）。`num_ctx=131072` が VRAM 12GB + RAM 32GB で OOM なく動作することを確認（[技術知見 §0](../log/技術知見/小説RAG_技術知見.md)）。

### 3.2 B-8（2026-05-10）書籍サマリ自体のベクトル検索

**なぜ必要か**: ページレベルの検索に引っかからなかった書籍は、たとえ質問に強く関連していてもサマリが QA に渡らない。サマリ自体を retrieval 候補にすれば、ページヒットの無い書籍も俯瞰情報として Qwen に伝わる。

`book_summaries_vec`（当時、後に LanceDB `summaries` へ移行）にサマリの bge-m3 ベクトルを格納し、`search_book_summaries` でサマリ自体を検索。ページヒット書籍とサマリヒット書籍の和集合をプロンプトに載せる。**FTS5 を使わない理由**: サマリは抽象表現中心でユーザー質問語との keyword 一致が起きにくく、意味類似度の方が効く。

**動作確認**: 「メルディの軍師としての活躍」→「10 二人の軍師」が distance 0.97 で 1 位、と意味的に妥当な順位を確認。

### 3.3 B-9（2026-05-11）Contextual Retrieval（チャンク位置説明）

**なぜ必要か**: `chunks.text` は「ページから 800 字を切り出しただけ」で、書籍内での位置づけ（巻 / シーン / 登場キャラ群）が embedding に含まれない。「父王が次期女王を発表する場面」のような抽象質問が、該当ページに直接の語彙一致が無くても、位置説明込みの embedding なら top に来る。

Anthropic 2024-09 の Contextual Retrieval を踏襲。各チャンクに書籍俯瞰サマリ（B-5）をコンテキストとして与え「このチャンクが書籍内のどの場面か」を 1 文（~80 字）生成し、`(contextual_text + chunk_text)` を再 embedding。Anthropic 計測で recall 35〜49% 改善。実機の retrieval 精度は [技術知見 §4.3](../log/技術知見/小説RAG_技術知見.md)。

- **初版（2026-05-11）**: 202 チャンクのパイロットで avg 63 字の位置説明、「父王が次期女王を発表する場面」→ p11 top1 を確認。
- **改良版（2026-05-12）**: 物語要約に流れて固有名詞が落ちる事例が頻発したため、**本文の固有名詞と特徴的フレーズを必ず含める**指示を追加。id=23（おこぼれ姫 1 巻、202 chunks）の `--redo` で ok=174 / skip=28 / ng=0、avg 106 字。「レティーツィア」「我が右手は剣、我が左手は楯」等の固有名詞・フレーズが含まれることを確認。

**B-11 との直交**: B-9 は chunk 側 embedding を強化、B-11（Query Expansion）は query 側を強化。両方適用で「クエリ ↔ チャンク」両端から retrieval 堅牢性が累積する。

## 4. num_ctx / top_k の段階拡大（B-13、2026-05-11）

QA の `num_ctx` は PoC の 8,192 から段階 A → B → C と拡大した。**段階別の数値表（num_ctx / top_k / max_per_book / 実測 in_tok・elapsed）は [技術知見 §2.2](../log/技術知見/小説RAG_技術知見.md) が一次ソース**。ここでは各段の狙いだけ残す。

- **段階 A（16,384 / top_k 32）**: 切り詰めバグ解消（`prompt_eval_count` が 8,192 に張り付いていた問題）。
- **段階 B（32,768 / top_k 64 / max_per_book 5）**: 概括質問の深さ向上。B-14 で応答が 5× 速くなった余裕を使う。`max_per_book=5` で scope=all/series でも同一書籍のページを最大 5 件集め、同書籍に集中する質問に深く答える（11 冊 × 5 = 最大 55 件、top_k=64 の枠内）。
- **段階 C（131,072 / scope=book で全 page 読み、既定）**: `NOVEL_DB_QA_FULL_BOOK_MODE=true`。scope=book では hybrid_search を bypass し全ページを Qwen に投げる。応答時間は段階 B の 4.5× だが本文 9 箇所以上から具体引用付きの深い分析を得る。scope=all/series は段階 B 相当を維持。ロールバックは `NOVEL_DB_QA_FULL_BOOK_MODE=false`。

**-ncmoe 28 の採用**（llama-server の MoE エキスパート CPU オフロード数）は ncmoe スイープの結果 A_short / B_mid / C_long いずれもベストだったため。**スイープ数値表は [技術知見 §9.3](../log/技術知見/小説RAG_技術知見.md)**。llama-server は段階 C 本採用後 `-c 131072 -ncmoe 28` 起動が canonical（Windows タスクスケジューラ `llama-server-qwen` に登録）。

### Phase 2: 旧資産の削除（完了）
- `main.py` の `app.mount("/kindle_novel/pdfs", …)` を削除。
- frontend `config/api.ts` の `source === 'novel'` PDF 分岐を削除。
- `data/kindle_novel/pdfs/` 配下の PDF を削除。
- `kindle-pdf/batch_ocr.py` / `searchable_pdf.py` は kindle 用途で残置（novel 用途のみ撤去）。

### 永続資産（削除しない）
- `data/kindle_novel/images/{書籍名}/*.png`（画像表示・再 OCR 用途）。
- `kindle-pdf/main_novel.py`（novel 画像取り込みツール）。

現行の取込は画像 OCR 経路（subprocess）が主。`extractor.extract_pages`（PyMuPDF）は旧 PDF 書籍との後方互換用として残っている（[パイプライン設計 §2](../design/詳細設計/機能別/小説RAG_パイプライン設計.md)）。

## 6. 質問応答プロンプトの成立経緯（§7.2）

PoC 当初は最小プロンプトだったが、Qwen 切替で「シリーズ全体」スコープの概括質問において**キャラ帰属の誤統合**が観察された（複数ページのキャラを混同し、別キャラの心情を主人公の話として統合する等）。`character_extractor` で抽出したヒントをページごとに `[page N, 主要登場人物: …]` として付与し、明示的な帰属ルール（発言者・行動者を明示、別ページのキャラを安易に統合しない）をプロンプトに追加することで誤統合率を下げた（PoC 計測で ~18% まで低下、許容範囲）。完全防止には書籍ごとの fine-tuning が必要でローカル個人ツールとしてはコスト超過のため、許容範囲として運用する判断とした。現行プロンプトは `prompt_builder.py` の `PROMPT_TEMPLATE`。
