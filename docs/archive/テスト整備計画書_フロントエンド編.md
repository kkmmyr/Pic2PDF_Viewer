## 4. テスト実装ガイドライン

### 4.1 共通フィクスチャ / テストヘルパー

`src/test/setup.ts` は現状 `@testing-library/jest-dom` の import のみ。以下を追加候補とする:

- `src/test/setup.ts`: `ResizeObserver` / `matchMedia` の polyfill 追加（jsdom に存在しないため Dialog / DnD 系で必要）
- `src/test/helpers/apiMock.ts`: `vi.mock('../config/api_client', ...)` の boilerplate を `setupApiMock()` で集約
- `src/test/helpers/factories.ts`: `makePdfFile(name, overrides?)` / `makeMetaEntry(...)` などのテストデータ生成

### 4.2 モック方針

- **API 通信**: `vi.mock('../config/api_client', () => ({ default: { get: vi.fn(), post: vi.fn(), patch: vi.fn(), delete: vi.fn() } }))` の hoist モック（既存テスト踏襲）。`apiClient` メソッドの戻り値は **interceptor 適用済みの `response.data` 相当**を直接返す（既存 `useBookMeta.test.ts` の形式）。
- **localStorage**: jsdom 既定の localStorage を `beforeEach` で `localStorage.clear()`。
- **タイマー**: `vi.useFakeTimers()` + `vi.advanceTimersByTime(ms)` でデバウンス・ポーリングを進める。
- **pdf.js**: `vi.mock('pdfjs-dist', ...)` で `getDocument` を最小実装に差し替え。
- **dnd-kit**: ドラッグ完了は `onDragEnd` を直接 callback 呼び出しで模擬（DnD イベント発火はせず）。
- **fullscreen API**: `Element.prototype.requestFullscreen` / `document.exitFullscreen` を `vi.fn()` で差し替え。
- **ResizeObserver**: jsdom に存在しないため `setup.ts` で `globalThis.ResizeObserver = vi.fn(...)`。

### 4.3 アクセシビリティ前提のクエリ

- 第一選択: `getByRole('button', { name: ... })` / `getByLabelText`
- `getByText` は短文のときのみ
- `getByTestId` は最後の手段（既存テストでも極力避けている）

### 4.4 非同期パターン

- `await waitFor(() => expect(...))` で副作用完了を待つ
- `await act(async () => { ... })` で state 更新をフラッシュ
- ポーリング検証は `vi.useFakeTimers()` + `vi.advanceTimersByTime()` で進める

### 4.5 カバレッジ計測（推奨）

```bash
cd frontend
npx vitest run --coverage
```

`vite.config.ts` に追加:
```ts
test: {
    environment: 'jsdom',
    globals: true,
    setupFiles: './src/test/setup.ts',
    coverage: {
        provider: 'v8',
        reporter: ['text', 'html'],
        include: ['src/**/*.{ts,tsx}'],
        exclude: ['src/test/**', 'src/main.tsx', 'src/vite-env.d.ts', 'src/**/index.ts'],
    },
}
```

`@vitest/coverage-v8` を devDependency に追加。

- **`setup.ts` の拡張**: `@testing-library/jest-dom` の import に加え、`ResizeObserver` / `IntersectionObserver` を class 形式で polyfill。`vi.fn().mockImplementation` で返す関数は `new` で呼べないため、constructor として動作する class 定義が必要だった。
- **`apiClient` モック**: 既存 `useBookMeta.test.ts` の `vi.mock('../config/api_client', () => ({ default: { get: vi.fn(), post: vi.fn(), patch: vi.fn(), delete: vi.fn() } }))` パターンを全 hook テストで踏襲。interceptor 適用済みの `response.data` 相当を mock 戻り値として直接返す。
- **`vi.useFakeTimers` の `toFake` 制御**: デフォルトの `vi.useFakeTimers()` は `waitFor` の内部 `setTimeout` も止めてしまい polling できなくなる。`vi.useFakeTimers({ toFake: ['setInterval', 'clearInterval'] })` で `setInterval` だけ fake にし、`setTimeout` は real のまま保つことで `waitFor` を有効に保ったまま `setInterval` を制御できる（`useGenerateJob` / `useJobPolling` / `useOcrStatus` / `usePdfStatus` で適用）。
- **microtask flush の手法**: `useEffect` 内の async IIFE が `waitFor` のデフォルト 1 秒タイムアウトに間に合わない場面では、`await act(async () => { await Promise.resolve(); await Promise.resolve(); })` で microtask を 2 周明示 flush して同期 `expect` する方式に切り替えた（`useJobPolling` / `useOcrStatus` / `usePdfStatus` の running 状態確認）。
- **react-pdf の barrel import 経由汚染**: `components/reader/index.ts` が `PageRenderer` を export しているため、`AutoFillAuthorsBar` / `SeriesResolveBar` のような hitomi 系コンポーネントが `import { ToastContainer } from '../reader'` するだけで `react-pdf` → `pdfjs-dist` が読み込まれ、jsdom に `DOMMatrix` が無いため evaluation で落ちる。各テスト先頭の `vi.mock('react-pdf', ...)` で回避。`usePdfDocumentState` も同じ理由でモック必要。
- **MemoryRouter wrap**: `useUrlState` / `useUrlFilters` は `react-router` の `useSearchParams` を使うため、`renderHook` の `wrapper` で `<MemoryRouter initialEntries={[...]}>` を渡す形式。
- **`window.matchMedia` / `requestFullscreen` / `fullscreenElement`**: jsdom 不在のため `Object.defineProperty(window, ...)` または `vi.spyOn(...).mockImplementation(...)` で各テスト内に mock を差し込む。
- **`Image()` の捕捉**: `useImagePreloader` のテストで `window.Image` を class で差し替え、src setter を観察して preload 件数を検証。
- **dnd-kit のスキップ**: `PdfGrid` の DnD ドラッグ動作は dnd-kit の Pointer event 連鎖を再現するコストが高いため、`onReorder` 経由の検証は省略し、render と各分岐のスモークに留めた。
- **`ErrorBoundary` のノイズ抑制**: jsdom はエラーバウンダリ内の throw を `window 'error'` イベントで再発火するため、テスト出力に大量のスタックトレースが出る。`addEventListener('error', e => e.preventDefault())` + `vi.spyOn(console, 'error')` で抑制。
- **axios interceptor の写経テスト**: `axios.create` 経由の interceptor 本体を直接テストするのが面倒なため、`config/api_client.ts` の reject ハンドラと同じロジックを写経した別関数を `api_client.test.ts` 内に置き、そちらをユニットテストする手法を採用。実装の `kind` 判定 / `detail` 抽出 / 境界 status の挙動だけ独立に検証できる。
- **useBookMeta 4 分割の検証**: `useBookMetaCore` + 対象 hook（Write / Series / View）を組み合わせる合成ヘルパーを各テストファイル先頭で定義し、実運用と同じ合成形式で検証。`setMeta` / `makeKey` を直接 mock せず、本物の `useState` 経由で観察できる利点がある。

### 7.3 テストを書く中で見つけた潜在課題

詳細は本ファイル末尾のセクション **§8 改善提案** を参照。要点のみ:

## 8. 改善提案（テスト作成中に発見）

優先度は実害ベース:
- 🔴 高 — 実機で再現する可能性のあるバグ
- 🟡 中 — 防御層が弱くセキュリティ・運用上の懸念がある
- 🟢 低 — 設計上の整理（リファクタ範疇）

> **2026-05-06 時点**: テスト作成中に発見した実害（🔴/🟡）はゼロ。Phase 54 までのリファクタリングと既存テストでバグの大半が予防済みだった可能性が高い。以下は構造改善の提案 2 件のみ。

### 8.1 🟢 `components/reader/index.ts` の barrel import が PageRenderer を含む

**該当箇所**: [components/reader/index.ts](../../frontend/src/components/reader/index.ts) が `PageRenderer` も `export` している。

**症状**: `AutoFillAuthorsBar` / `SeriesResolveBar` / `HitomiArrivalCard` 等の reader 配下を一切使わないコンポーネントが、`import { ToastContainer } from '../reader'` するだけで `PageRenderer` → `react-pdf` → `pdfjs-dist` までインポート連鎖する。本番ビルドでは tree-shaking で除去される想定だが、jsdom テストでは全モジュールが評価されるため `DOMMatrix` 不在で落ちる。各テストで `vi.mock('react-pdf', ...)` を要求する原因となっている。

**影響**: 本番ビルドのバンドルサイズには影響なし（tree-shaking 効くと仮定）。テスト時の摩擦のみ。

**対応案**: `components/reader/index.ts` から `PageRenderer` の export を外す（PageRenderer は `ReaderPanel` からのみ直接 import される）。または `components/reader/_internal/index.ts` のような副 barrel に分離。コミット効果: 5 ファイル前後のテストから `vi.mock('react-pdf', ...)` を削除可能。

### 8.2 🟢 `useReaderShortcuts` / `useLibrarySelectionShortcut` の listener アンマウント検証

**該当箇所**: [hooks/useReaderShortcuts.ts](../../frontend/src/hooks/useReaderShortcuts.ts) / [hooks/useLibrarySelectionShortcut.ts](../../frontend/src/hooks/useLibrarySelectionShortcut.ts)

**症状**: どちらも `window.addEventListener('keydown', ...)` を直接登録するため、テストでアンマウント後に listener が残っていないことを直接検証する手段が無い。間接的には「アンマウント後に keyboard event を dispatch してもハンドラが呼ばれない」で確認できるが、テスト間で listener が積み重なるリスクは残る（実害は低い）。

**対応案**: 検証手段の改善のみ。`window.addEventListener` の `vi.spyOn` で `removeEventListener` 呼び出しを観察する手法を採用するか、Hook 設計を `target: HTMLElement` 受け取り型に変えてテスタビリティを上げる。本計画では未対応で OK。
