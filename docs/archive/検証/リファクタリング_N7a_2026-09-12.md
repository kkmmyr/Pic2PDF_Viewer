## 2. 調査方法と範囲

同一参照元ファイルの重複は除き、`backend/tests/`等のtest、`backend/scripts/`・`scripts/`のCLI、

## 3. 移動前に解消すべき検査・台帳の不足

### 3.1 固定パスの依存検査が移動後に省略される

`scripts/maintenance/check_import_boundaries.py`の`_novel_module_violations`は、
`full_build_content` / `full_build_repository` / `search_ranking` / `search_presentation` /
`search_queries` / `ocr_job_application`の6ファイルを直下の固定パスで探し、存在しなければskipする。
一般のservice走査が再帰的でも、この6境界の専用allowlist検査が維持される保証にはならない。

一時ディレクトリで同じ`import sqlite3`を持つファイルを使い、以下を再現した。

| 配置 | 専用検査の結果 |
|---|---|
| `backend/services/novel_db/search_ranking.py` | `Search boundary imports sqlite3`を検出 |
| `backend/services/novel_db/retrieval/search_ranking.py`へ移動 | 違反0件。専用検査から外れる |

実リポジトリのソースは移動していない。この結果は現行コードに違反があるという指摘ではなく、
将来の移動で検査が失われる再現である。N7bでは対象一覧の存在・走査保証を追加し、
未登録の移動・欠落で成功しないこと、登録した新配置でも禁止importを検出することを固定する。
部分fixtureを使う既存testと、実リポジトリ全体の対象存在検査を区別する。

### 3.2 page FTS公開窓口が互換台帳に未登録

`page_fts.py`は後方互換公開窓口と明記され、14個の型・関数・定数・loggerを再公開している。
`build_page_fts_index.py`は関数だけでなく`logger`もimportする。
しかし`maintenance_assets.json`のcompatibility 15件にはこのファイルがない。
台帳検査は登録済み項目を検査するため、この未登録を検出しない。

N7bで`page_fts.py`を維持する入口として登録し、利用元・owner・再評価条件・復旧方法を記録する。
機械台帳と[保守資産・互換層台帳](../../design/環境構築/保守資産・互換層台帳.md)を同期する。
N7aでは台帳の状態変更や入口削除は行っていない。
