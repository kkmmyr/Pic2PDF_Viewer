# リファクタリング N5a 実施・検証記録

> status: archived | last-verified: 2026-09-08 | owner: project owner

N3・N4をそれぞれ`4bdb9bb`・`f64a3b1`、TM-10を`1b5e893`で区切った後の、
OCR job設定依存分離のローカル受入記録。現在の未完了事項は
[リファクタリング計画書](../../log/計画/リファクタリング計画書.md)を正本とする。

## 1. 完了範囲と所有者

| 所有者 | 分離後の責務 |
|---|---|
| `job_worker.py` | 呼出しごとに既存保存/worker/QA操作と設定resolverを組み立てる |
| `ocr_job_configuration.py` | 設定を実行時に読み、engine/model revisionだけを`OcrRunSpec`として返す |
| `ocr_job_application.py` | 注入された設定resolver・保存・worker・QA操作の実行順と失敗処理 |
| 既存extractor / worker / session | process起動、manifest、server世代、ページ実行とretry |
| 既存run store / QA / publication | 入力・候補SHA、checkpoint、QA待ち、承認と公開の拒否条件 |

`OcrJobDependencies`に内部組立用の`resolve_run_spec`を追加した。
既存の`execute_ocr_job`の引数、queue入口、HTTP、schema/migration、worker JSONL、
設定名・既定engine・model revision・promptは変更していない。
applicationでのページ/入力型参照は`TYPE_CHECKING`内へ移し、型の供給元を再分割しなかった。

## 2. 固定した契約

| 境界 | 維持した内容・確認 |
|---|---|
| 設定選択 | casefoldのみ。Surya設定版・複合固定版・その他engine名の分岐を維持。空白trimや新しい検証を追加しない |
| 参照時点 | 対象解決と初期進捗の後、run準備前に一度。対象0冊でも解決し、他modeでは参照しない。job間で設定をcacheしない |
| 準備失敗 | 入力収集/run準備の途中失敗はそのまま伝播し、先行runを一括failedにしない既存の範囲を保持 |
| worker/保存失敗 | 全準備済みrunをfailedとし、未知書籍の結果を拒否。ページ保存後にdetailを通知 |
| QA準備失敗 | 冊単位でfailedを記録して残りを処理し、最後に失敗を集約 |
| checkpoint再開 | 一時画像・隔離DBとfake workerで1ページ保存後に中断。同じrunを再開し、残りの1ページだけを処理 |
| provenance/公開 | 再開前後で保存済み入力SHA・本文/raw・候補manifest・attempt数とrun manifestが一致。QA待ちでbooks/公開履歴は増えず、未審査の公開を拒否 |
| cancel/retry | queued cancel可・running cancel不可の既存契約、worker server世代・再起動・既存の候補再利用を回帰テストで維持 |
| 依存方向 | config・具体worker・設定adapter等の直接importを静的に拒否。applicationを別名で読み直し、型の供給元を実行時importしないことも検査 |

分離前に設定/失敗時点15ケースとcheckpoint統合1ケースを追加した。既存対象と合わせて
96 passed / 1 skipped。分離後に依存・注入12ケースを追加し、同じ関連群は108 passed / 1 skipped。

旧HEADと新実装のAST比較では、設定選択の分岐、進捗整形・run準備・worker消費・QA準備の
4 helper、準備後の例外処理とQA呼出しが同一だった。
これは固定入力での制御・保存契約の比較であり、実モデル出力品質の同等性評価ではない。

## 3. 構造比較

| 指標 | 分離前 | 分離後 |
|---|---:|---:|
| applicationからconfig/具体workerへの直接import | 2 | 0 |
| applicationからextractor/run storeへの実行時import | 2 | 0（型参照のみ） |
| `ocr_job_application.py`行数 | 150 | 152 |
| 設定adapter行数 | — | 18 |
| `job_worker.py`行数 | 105 | 107 |

行数を減らすための分割ではなく、設定の選択理由を処理順の所有者から分離した。
OCRの設定・保存・process接続を差し替え、注入値でapplicationを検査できる。
package全体の推移importや動的import全般の排除、工数・速度改善率は保証していない。

## 4. 検証結果

Windows / Python 3.12.10 / root uv workspaceで実施した。

| 検査 | 結果 |
|---|---|
| 分離後のOCR/queue/保存/worker/extractor/複合engine/依存テスト | 108 passed、1 skipped |
| backend全体・coverage | 1,768 passed、4 skipped。coverage 73.25%、基準65%を充足 |
| Kindle / common LLM | 130 passed・2 skipped / 76 passed |
| basedpyright / backend Ruff・format | 0 errors / warnings / notes、lint合格、479 files formatted確認 |
| 月次監査 | docs、file map、規模、C901、OpenAPI、依存境界、保守資産、Knip、計画残存検査に合格 |
| 品質基準 | TM-10後の規模12 / 12、C901 35 / 35を維持 |
| OpenAPI | `ed33f214ffed`、109 paths。baseline更新なし |
| 設計書 | リンク・status・nav・file map検査とstrict buildに合格 |

全体検査は`uv run pytest -q --cov --cov-fail-under=65 --cov-report=term:skip-covered`で実行し、
N3の生成/公開・N4の検索回帰を含めた。既存のStarlette/httpx非推奨warningは残る。

UIとfrontend/srcの変更はないため、frontend全test/build・実ブラウザ確認は省略した。
月次Knipは端末既定Node.js 24.13.0 / npm 11.6.2で実行した。
実Surya/Qwen/dots推論、Windows実撮影、Mac MLX、本番配備・本番DB操作は実施していない。
既存adapter自体は今回変更しておらず、その実機品質・稼働環境の受入を本記録で代替しない。
正式OCR holdoutを反復試験に使っていない。

## 5. 後続への反映

次はN5bのCapture→Libraryメタ更新入口の整理とする。
`capture_registration.py`の順序制御と`CapturePublication`の補償を維持し、
置換可否の読取り・ASIN更新・以前のメタ復元を先に固定する。
新しいLibrary adapterから既存`meta_store`へ委譲する場合、現行のLibrary依存禁止規則に
狭い許可が必要になるため、所有ファイルを確定してから規則を変更する。
撮影状態機械統合、画像配置/rollback順の変更は持ち込まない。

N3/N4で確認した通常再実行による索引自動修復の非保証は維持する。
TM-8（Mac実モデル）とTM-9（起動停止時cleanup）は未完了のままとする。
N5aだけをrevertできる構造であり、DB migrationやデータ再作成は不要である。
