比較元は`2c6671d`。以下をmoduleを実行しないAST解析で確認した。

- content、repository、full_builderの3ファイルは、top-level importを除いた構文木がすべて一致した。
- Novel DBのPythonファイルは118から119へ変化。増加は副作用のないpackage初期化ファイル1つ。
- 移動した2moduleの名前を比較元へ対応付けると、直接依存259本は前後で完全一致し、追加・削除は0本。
- 対象3moduleには静的依存グラフで自分へ戻る経路がなく、今回の新規循環はない。
- `generation/__init__.py`の構文木はdocstringだけであり、新たな初期化依存を持たない。

依存比較は絶対・相対importと`from package import module`を扱い、関数内・条件付きimportも含む。
動的importやPythonの暗黙の親package初期化すべてを表現するグラフではないため、次の実読込みも行った。

## 3. 後続の採否

**N7cの次に、追加の物理移動を自動的には採用しない。**
今回、狭い範囲の移動と契約維持を確認できた一方、依存本数や変更範囲の縮小、開発速度の向上を
実測したわけではない。N7の完了条件を全118ファイルの移動に置き換えない。

| 候補 | 判定 | 根拠と再評価条件 |
|---|---|---|
| 検索内部3ファイルの`retrieval/`配置 | 現案を見送り | 現在の`retrieval.py`はQA/chat routerの入口で、testのpatch先でもある。同名packageを作るだけでは入口を隠す。検索機能の変更時に公開入口・配置名・移行契約を先に再設計し、具体的な利点が出た場合だけ再評価 |
| page FTS内部3ファイルの配置 | 今回は見送り | 公開窓口`page_fts.py`とstate/builder/queryの分離は既に成立。追加移動で改善する依存や保守上の問題を示せていない。索引機能を次に拡張するときに再評価 |
| CLI一括rename、OCR worker、frontend全域移動 | 見送りを維持 | ファイル指定実行、公開import、外部利用へ波及する。関係する機能変更で移動が必要となった場合だけ個別に計画 |
| 期限付き互換7件・移行入口4件の撤去 | 外部確認待ち | 既存のowner・再評価日・撤去条件を維持。今回の移動成功を利用終了の根拠にしない |

同名衝突は一時fixtureで実際に確認した。`retrieval.py`と`retrieval/__init__.py`を同時に置くと、
Pythonの探索結果は後者になる。実repositoryには後者を作っていない。
新規設計時の論理境界を、そのまま現行repositoryのdirectory名として採用しない。

次の確定作業はN7c成果のcommit・共有・取り込みである。実装の次候補はTM-9/TM-11等の
失敗時の振る舞い改善を別単位で検討する。これらをN7cの機械的移動へ混在させない。
