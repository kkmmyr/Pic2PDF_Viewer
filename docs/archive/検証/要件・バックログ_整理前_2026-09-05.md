### 5.1. OCR（novel.db 直接格納）

- **現状（2026-07-27 確認）**: backend の job queue から Surya OCR 2 を実行し、ページ単位の品質検査・チェックポイント保存後に run を `awaiting_qa` へ進める。必須ページの画像照合・補正と run 承認が終わるまで公開テーブルは更新せず、承認済みの1冊分だけを `novel.db` の `pages` テーブルへ確定する。`yomitoku` は限定補助・比較・後方互換用に残す。Novel Reader は元PNGを表示し、Searchable PDF は生成しない。
- **Codex管理の正式運用（ADR-0024）**: Qwen3.5-OCR-JP-2Bを主候補、dots.mocrを全ページの独立副候補とし、
  本番engineへは配線しない。CodexがMacの隔離DBで1冊ずつ実行し、risk対象・clean標本・候補差分を原画像で
  監査して、確定できる箇所だけを補正する。通常の利用者QAは不要とし、Codexでも一意に確定できない箇所だけを
  保留する。成果は画像SHA、候補raw、model revision、選択理由、補正文、review根拠、digest付きpackageとして
  Linuxへ渡し、固定provenance・本番画像との再照合、冪等staging、検証済みbackup、原子的公開を通過した
  1冊だけを反映する。package importと公開は別操作とし、importだけでは正本本文・FTSを変更しない。
  Macから本番DBを直接更新せず、自動公開・DB丸ごと置換・手動SQL patchは行わない。
- **スタンドアロン `batch_ocr.py`**: 撤去済み（以前の独立スクリプト方式は廃止）。
- **方針**: 同人誌（doujin ソース）への適用可能性は将来検討。

### 5.2. OCR後のSol主生成・選択的評価（段階導入）

- **目的**: OCR承認済み小説本文から、詳細あらすじ、一覧用短縮要約、人物辞典を品質優先で生成する。
- **主生成**: 1冊のOCR本文をGPT-5.6 Solへ1回だけ渡し、構造化事実と公開候補を同時に生成する。
- **評価**: JSON、SHA、正規名、文字数等はローカルで検査し、否定、最終状態、主体、期間等の
  高リスク主張だけを別の新規Solセッションで原文照合する。
- **公開**: 固定パイロット中は必ず旧版差分と人手確認を行い、未承認・不合格候補を公開しない。
- **外部送信**: 書籍単位の明示的opt-inとし、モデル改善利用オフを運用前提に、OCR本文以外の画像、
  PDF、ASIN、ローカルパス、認証情報を送らない。
- **費用境界**: 初期版はMac上のCodex CLIへChatGPTログインし、サブスクリプション利用上限内で実行する。
  APIキー課金へ自動切替せず、利用上限到達時は安全停止・手動再開する。
- **既存経路**: Qwenは対話QAとオフライン代替として維持し、Sol失敗時に自動公開する代替には使わない。
- **詳細**: [Sol主生成・選択的独立評価設計](../../design/詳細設計/機能別/小説RAG_Sol生成・評価設計.md)を参照。

### B-35. 小説OCRの機械単独自動公開 — 保留

**現在地**: 現在の全機械候補は正式policyに未達。Unlimited-OCR BF16は固定5枚すべての
生成反復、Nemotron Parse 2.0 8bitは固定1枚目の4,096 token反復でそれぞれ
fail-fast不採用とした。Qianfan-OCRの固定MLX 4bit変換も固定1枚目で最大CER gateを超え、
2枚目で生成反復したためfail-fast不採用とした。HunyuanOCR 1.5 BF16 GGUFは固定1枚目を通過したが、
2枚目で段落重複・順序入替により最大CER gateを超えたため不採用とした。Codex画像QA込みの
運用品質と、Codexなしの機械性能を分けたまま評価する。Hayai OCR v2固定revisionも固定1枚目で
8文字しか生成せずCER 99.4932%となったためfail-fast不採用とした。honmono-ocrは縦書き行benchmarkが公開されたが、モデル本体と
参照GitHubを認証なしで取得できず、ページ分割・読順復元も別途必要なため直ちに評価しない。実装済みgateと実測値は
下記正本へ置く。

Qwen3.5-OCR-JP-2B固定revisionは固定5枚中4枚で総合CER 0.2416%だったが、`001751`だけが
8,000 token上限まで反復し、単体5枚総合CER 344.1829%となったため単独候補にはしない。既存の
`has_suspicious_repetition`は固定5枚でこの1枚だけを検出し、同ページだけHTML末尾も切断された。参照正解を使わず、
反復または末尾切断時だけ
dots.mocrへ切り替える複合候補は、過去の同revision・固定5枚実測から総合CER 0.3285%以下、
ページ最大0.6907%以下となるため固定5枚gateを通過した。初期規則の固定79枚screeningは15枚時点で
総合CER 0.5166%、`000260`が3.1042%となりfail-fastしたが、レビュー前提版では全79枚を再開・完走した。

ADR-0022で、Qwenを主候補、dots.mocrを全ページの独立副候補とし、反復・HTML切断・非保持markup・
隣接する狭い縦列bboxの読順違反・副候補の有意な文字量増加をレビュー初期候補の切替signalにする。
ADR-0024により、この版はCodexがMac隔離DBで原画像レビュー・補正し、固定provenance・画像SHA・digest付き
packageとしてLinuxへ渡す運用に限定した。通常の利用者QAは要求しない。機械gate未達なので自動公開には使わない。
修正後本文は運用品質として採用するが、機械CERへ混ぜない。

開封済み79枚ではQwen単体が反復4枚を含み総合CER 104.9354%、dots単体が0.8990%、レビュー用複合版が
0.4091%だった。複合版は79枚中7枚をdotsへ切り替え、最大ページCERは2.8835%で2.0%未満gateだけが残った。
したがってQwen主候補＋dots副候補の構成を維持するが、候補選択だけで公開品質とはみなさない。

**残作業**:

1. 機械総合合格は将来の自動公開条件として継続する。新しい未調整holdoutでpolicy JSONの全gateを満たすまで、
   自動公開とCodex原画像レビュー省略は実装しない。
2. 小書き文字・約物と縦列を保持し、ページ最大CERを下げる独立候補を作る。
3. 候補を固定後、新しい未調整holdoutを候補品質を見ずに封印し、一度だけ評価する。
4. 機械総合合格後だけ、Codex確認縮小の反復・100画面試験へ進む。
5. subprocess、QA DB更新、FTS同期の障害注入で旧公開状態の保持を確認する。
6. Mac版YomiTokuはWindowsと同一version・同一画像SHA・同一設定のmanifestを取得してから、
   CPU/MPSの本文一致率と速度を比較する。Qwen＋Dots＋Codex合成runをMPS性能値に流用しない。

**2026-08-29実装済み**: `ocr_runs.model=unversioned`を新規runで禁止し、YomiToku・PyTorch・
device・wrapper/model/pipeline SHA、dirty状態をrun manifestへ固定した。primary/externalの
非採用側も本文・raw出力・自己SHA付きmanifestとして保持する。OCR初期化・画面処理・QA・
Codex補正の時刻も分離記録し、「公開可能になるまでの時間」を比較できるようにした。

レビュー前提laneの完了条件は[小説OCR品質改善 実装計画](../../log/計画/小説OCR品質改善_実装計画.md)の
複合engine統合、1冊のCodexレビュー、package隔離往復、公開・rollback確認。policy JSONの全gate合格は
自動公開の条件として残す。現行契約は
[OCR設計書](../../design/詳細設計/機能別/OCR設計書.md)、実測は
[OCR品質改善 技術知見](../../log/技術知見/OCR品質改善_技術知見.md)を参照する。
