## 2. 固定した保存・通知契約

分離前に既存対象22件を実行し、公開境界16ケースを追加した38件で同じ期待値が通ることを確認した。
分離後は保存関数の未確定状態1件と、新しい2 moduleの依存境界14ケースも追加した。

| 場面 | 維持した結果・テスト |
|---|---|
| 書籍なし・既存公開版あり・redo | 既存skip条件・通知、redoでの再生成を維持。詳細/一覧は非空、人物説明は1行以上非NULLでskip |
| 生成・検査失敗 | 旧公開版を保持。本文根拠なし・根拠のある既存人物の消失は公開へ進まない。`finished`を通知しない |
| UPDATE / DELETE / INSERT / commit失敗 | 隔離SQLiteへ障害注入し、公開文・全人物行・生成時刻のsnapshotが旧版と一致。rollback後はtransactionが閉じ、索引へ進まない |
| 保存関数だけを実行 | 呼出し元からは新行が見えるが未commitで、別接続には旧版が見える。呼出し元のrollbackで旧版へ戻る |
| 索引更新開始 | commit済みでtransactionが閉じており、別接続から新しい公開文・人物・生成時刻を参照できる |
| embedding / 索引delete / add失敗 | 既存`summary_index`を通し、外部embedding・tableだけを差し替えて障害注入。warningを記録してdoneとなり、SQLite公開行を戻さない |
| 索引失敗後の通常再実行 | SQLiteの充足条件でskipし、生成も索引も再実行しない。add失敗では旧索引のdelete後に欠落し得る |
| job通知 | rebuild進捗→生成進捗→検査→done→finishedの順序と、生成・検査・SQL失敗時の打切りを固定 |

生成途中の事実checkpoint・grounding監査は独立した保存経路を持つ。公開版保持を「DB全体が
未変更」と表現していた設計書を修正した。これら独立保存の方式自体は変更していない。

限定許可する。生成・索引・config・HTTPへの逆依存を拒否し、汎用repository化はしていない。
