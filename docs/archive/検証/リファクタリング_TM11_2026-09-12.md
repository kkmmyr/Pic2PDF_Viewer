# TM-11 撮影補償失敗と復旧再開 検証記録

> status: archived | last-verified: 2026-09-12 | owner: project owner

## 1. 基点と変更範囲

TM-9を`76dc73c`でcommit・pushし、[PR #24](https://github.com/kkmmyr/Pic2PDF_Viewer/pull/24)の
backend・frontend・docs・secrets CI成功後、`6034fcf`でmasterへ取り込んだ。
その基点から`codex/tm11-capture-recovery`でTM-11を実装した。

- publication: 成功flagを消す補償、全失敗の保持、復元先競合・退避資産保護、記録の作成と回収。
- registration: 元の登録失敗と補償失敗の例外group、未復旧記録がある場合の停止、job成功後のmarker削除失敗の区別。
- Library metadata: 更新前・更新後snapshot、競合時の上書き拒否、検証済みsnapshotからの再構成。SQLは引き続きmeta_storeが所有。
- recovery record: JSONの型検証、排他的な開始marker、atomic更新、復旧実行lock。
- recovery / repository: 現行jobと保存先の照合、保存済みflagから残る補償だけを再開。job状態を変更しない。
- `tools.recover_capture`: 既定は表示のみ、`--resume`で明示した復旧。外部公開APIは追加しない。

契約は[Kindle自動撮影ジョブ契約](../../design/詳細設計/機能別/Kindle自動撮影ジョブ契約.md#capture-recovery)、
作業手順は[運用ガイド](../../design/環境構築/運用ガイド.md#capture-recovery)を正本とする。

## 2. 受入条件と失敗注入

| 条件 | 確認した結果 |
|---|---|
| メタ復元失敗 | 元のSQL失敗を保持し、画像の回収を継続。原因解消後に残るメタ復元を再実行 |
| package / staging / target / 旧画像 / 世代削除の各失敗 | 各失敗と未完了flagを保存し、独立した後続処理を継続 |
| 複数失敗 | 全失敗を順番どおり保持。未復元の旧画像・packageを消さない |
| 再試行 | 別のpublication objectを記録から作成して復旧。成功済み画像・メタは再度削除・上書きしない |
| 復元先の既存資産 | `.ready`の既存packageや正式targetの別資産を上書きしない |
| 退避画像の欠落 / 未復元 | エラーとflagを残し、退避世代を保持。空directory以外は自動削除しない |
| メタの後続編集 | 更新前・更新後のどちらとも異なるentryは競合として保持 |
| job失敗と補償失敗 | 両例外のidentityをcauseのgroupに保持し、登録失敗のtype/messageも記録へ保存 |
| 初期marker保存失敗 | 正式画像の変更前に止まり、残存markerで次の登録を止める |
| 補償記録の保存失敗 | 他の補償を続け、例外noteへsnapshotを残す。初期markerで通常登録を止める |
| job成功後のmarker削除失敗 | job、正式画像、processed package、監査の成功状態を維持してログへ通知 |
| 復旧CLI | 既定表示は記録・DB・資産を変更しない。`--resume`成功後もjob状態は維持 |
| 不確定・不一致 | publishing / resuming、破損JSON、path・job同一性・snapshotの不一致、成功済みjobを復旧前に拒否 |
| 重複復旧 | 排他的lockで再開を拒否。残存lockも通常登録を止める |

## 3. 検証結果

- 修正前のSQLite失敗注入で、メタ復元が失敗すると新画像が残ることを再現（1 failed）。
- 最終版の関連4ファイルは58 passed / 1 skipped。DB・画像・packageは一時領域へ隔離し、状態の比較と例外identityを検査。
- Ruff lint・format、basedpyright（0 errors / 0 warnings）に合格。
- 月次品質監査に合格。C901は35件、code sizeは12件の既存基準を維持。OpenAPIは109 paths・hash `ed33f214ffed`で不変。
- 検証用型ライブラリの依存がLibraryメタadapterへ入る問題を境界検査で検出し、JSON検証をrecord境界へ配置。既存の許可依存を緩和せずに解消。
- backend全体は`uv run pytest -q --cov --cov-fail-under=65`で1,887 passed / 4 skipped / 既存warning 1件（454.44秒）。coverage 73.56%で65%基準を充足。warningはStarlette TestClient/httpxの既存非推奨通知。
- 文書検査とMkDocs strict buildに合格。固定anchorの生成HTMLとリンク先を確認した。凍結記録内の既存リンク切れ30件は情報扱いで維持。

## 4. 運用上の限界と引渡し

通常例外からの補償と、保存済みの確定した未完了状態からの再開を対象とする。
process強制終了・任意のクラッシュからの自動修復、分散transaction、稼働中writerとの競合制御は保証しない。
復旧前にbackend・撮影agent等のwriterを停止する。publishing / resumingや残存lockは実資産とDBを手動確認する。
メタ競合の解決方針や復元先の競合資産の採否を自動決定しない。

TM-11はローカル実装・検証完了。この時点でcommit・push・merge・本番配備前。Windows実撮影・本番DBでの破壊的な失敗注入は実施していない。
既存の未追跡`@AutomationLog.txt`と`tmp/`は変更していない。
後続の未完了作業は[リファクタリング計画書](../../log/計画/リファクタリング計画書.md)を参照する。
