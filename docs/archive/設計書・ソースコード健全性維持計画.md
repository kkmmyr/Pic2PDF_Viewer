# 設計書・ソースコード健全性維持計画

作成日: 2026-07-26
最終更新: 2026-07-27

> 状態: 2026-07-28 完了・archive移管

現行ルールは[品質ガードレール](../design/詳細設計/品質ガードレール.md)を参照する。
本書は導入判断と完了実績を保持する凍結記録である。

設計書とソースコードが時間とともに肥大化・陳腐化することを防ぎ、
問題が大きくなる前に検知・是正するための継続方針と導入計画。

構造改善の実施順は
[リファクタリング計画書](../log/計画/リファクタリング計画書.md)、
ユーザー向け機能は[バックログ](../log/計画/バックログ.md)で管理する。

---

## 1. 目的

次の状態を継続的に守る。

1. living設計書が現在の実装を現在形で説明している。
2. 完了計画・検証過程・旧仕様が現行設計へ混入しない。
3. 既存の大きなファイルを直ちに全分割せず、新規の肥大化と複雑度悪化を止める。
4. API、DB、ファイル形式、UI操作などの外部契約を比較可能にする。
5. 例外は理由と期限を持ち、無期限のignoreを作らない。

---

## 2. 基本方針

### 2.1 正本を一つにする

| 情報 | 正本 |
|---|---|
| 現在の要件・設計・運用 | `docs/design/` |
| 進行中の計画・技術知見・既知の問題 | `docs/log/` |
| 完了計画・検証過程・撤去済み仕様 | `docs/archive/` |
| API構造 | FastAPI `/openapi.json` |
| DB構造 | Alembic migration。SQLModelはautogenerate補助 |
| ファイル配置 | 自動生成ファイルマップ |
| 継続必須の開発規約 | `AGENTS.md`とproject skills |

同じ一覧やスキーマを複数文書へ手書きしない。設計書には、OpenAPIやmigrationだけでは
表せない意図、境界、失敗時挙動を記載する。

### 2.2 絶対上限ではなくラチェットで改善する

既存コードには行数・複雑度超過があるため、一度に全違反をエラーにしない。
現在値を基準線として固定し、次を段階的に強制する。

- 新しい違反を増やさない。
- 既存違反を悪化させない。
- 対象を変更するPhaseで違反数または最大値を下げる。
- 改善済み基準線を元へ戻さない。

### 2.3 責務境界で判断する

行数だけで分割しない。次のうち2つ以上を満たす場合を分割候補とする。

- 異なる理由で変更される責務が同居している。
- C901などの複雑度超過がある。
- 直近の変更量が大きく、競合や回帰が繰り返されている。
- テストで外部環境を大量mockしないと検証できない。
- API、DB、ファイルI/O、UI操作など複数の副作用境界をまたぐ。

### 2.4 互換性を比較してから構造を変える

リファクタリング前に対象ごとの不変条件を固定する。

| 対象 | 比較方法 |
|---|---|
| FastAPI | 正規化した`openapi.json`の差分 |
| DB | migration head、schema、主要query結果 |
| Kindle capture | error code、状態遷移、manifest、画像寸法・枚数 |
| OCR | 固定fixture本文、品質flag、CER |
| Reader | RTL/LTRページ遷移表 |
| ファイル公開 | 障害注入によるrollback結果 |

## 3. 設計書ガードレール

### 3.1 機械チェック

必須:

- living文書の相対リンク切れ0件。
- MkDocs navのdead entry / orphan 0件。
- `design/`文書は冒頭に`status`と`last-verified`を持つ。
- ファイルマップを自動生成し、手編集によるドリフトを許さない。
- `docs/log/変更履歴.md`は800行以内で週次ローテーションする。

段階導入:

- `design/`の800行超は現在のwarnから、既存警告解消後にblockingへ変更する。
- 800行を超える必要がある場合は、文書冒頭に理由、分割しない根拠、
  再確認日を記載した例外登録を必須とする。

### 3.2 文書の寿命管理

- 計画完了を記録するコミットで、計画書を`archive/`へ移す。
- living文書へPhase番号や実装経緯を残さず、理由が必要ならADRへ記録する。
- `last-verified`は内容を実装と照合した場合だけ更新する。
- 同一仕様を要件、詳細設計、計画へ重複記載せず、下位文書から正本へリンクする。

### 3.3 レビュー観点

設計書変更時は次を確認する。

- 現在形で読んだときに旧仕様と誤認しないか。
- 実在しないファイル、class、API、設定名がないか。
- API一覧やファイルツリーを手書きで複製していないか。
- 完了後も計画バケットへ残る文書がないか。

## 4. ソースコードガードレール

### 4.1 規模

生成物、migration、凍結スクリプト、テストfixtureを除くproduction codeに適用する。

| 物理行数 | 扱い |
|---:|---|
| 400行以下 | 通常範囲 |
| 401〜500行 | 変更時に責務数を確認 |
| 501〜800行 | 分割要否を計画書へ記録。理由なく増加させない |
| 801行以上 | P1調査対象。変更前にcharacterization testを用意する |

数値は自動分割の命令ではない。単一責務であることを説明できる場合は例外登録できる。

### 4.2 複雑度

- Ruff C901の現在超過28件を基準線として記録する。
- 新規関数のC901超過を禁止する。
- 既存超過関数を変更する場合、原則として複雑度を増やさない。
- Phase完了ごとに基準線を更新し、減った違反をallowlistへ戻さない。
- `scripts/maintenance/c901_baseline.json`は関数単位の現在上限を保持する。
  `check_c901_ratchet.py`は新規違反と上限悪化をblockingにし、閾値以下へ改善した
  entryは専用maintenance変更でbaselineから削除する。

### 4.3 依存方向

原則:

- backend: `router → service → utility/config`。serviceからrouterをimportしない。
- frontend: `page → component/hook/feature → apiClient/config/type`。
- Kindle: `agent → controller/capturer`。controllerとcapturerはLinux APIを知らない。
- DB transaction、ファイルI/O、外部process、UI Automationを同一関数へ集めない。

将来はimport検査をCIへ追加する。導入前に現行違反を列挙し、違反ゼロの境界から
段階的にblocking化する。

### 4.4 重複と共通化

- 2箇所の類似だけでは共通化しない。
- 3箇所以上、または同じ不具合修正が複数箇所へ必要になった時点で検討する。
- 共通化により引数や条件分岐が増え、利用側より抽象層の方が複雑になる場合は行わない。

## 5. テストと契約のガードレール

- 副作用を持つ処理の分割前にcharacterization testを追加する。
- 正常系だけでなく、途中失敗、再試行、二重実行、rollbackを固定する。
- OpenAPI変更を伴わないPhaseでは、正規化したschema差分を0件にする。
- 生成型は手編集せず、OpenAPIから再生成する。
- 実機依存処理はunit testと録画・固定fixtureで大半を検証し、実機操作はPhase末尾に限定する。
- テスト数だけを品質指標にせず、変更対象の失敗境界が固定されているかを確認する。

---

## 6. 例外管理

ガードレールの例外は、対象ファイルと同じリファクタリングPhaseまたは専用allowlistに
次を記録する。

```yaml
path: path/to/file
rule: size-over-800
reason: 分割しない具体的理由
owner: 対象機能名
baseline: 917
expires: 2026-10-31
recheck_when: 次の機能追加または50行超の増加時
```

- `reason`、`expires`、`recheck_when`のない例外は禁止する。
- 行単位の無期限`noqa`やディレクトリ全体の除外は使用しない。
- 期限到来時は「分割」「基準線更新」「例外継続」を再判断する。

## 7. 導入計画

### Guardrail 0 — 基準線確定

- [x] docs、ファイル規模、C901、テスト収集数、Knipの現状を記録。
- [x] 新しいリファクタリングロードマップを確定。

### Guardrail 1 — 文書ラチェット

- [x] Phase 1でフロントエンド詳細設計の800行超を解消。
- [x] 完了済み計画をarchiveへ移す。
- [x] 警告0件を達成。800行超のblocking化はGuardrail 2のラチェット実装と同時に行う。

### Guardrail 2 — ソース規模・複雑度ラチェット

- [x] production codeの物理行数を再現可能に測定するscriptを追加。
- [x] C901既存超過28件のbaselineを機械可読形式で保存する。
- [x] CIとpre-commitで新規超過と関数単位の基準線悪化を検知する。
- [x] 生成物、migration、archive、fixtureの除外規則をテストする。

`check_code_size.py`は`backend`、`kindle-pdf`、`frontend/src`のproduction codeを
物理行数で測定する。400行超の既存ファイルは`code_size_baseline.json`へ固定し、
新規超過と既存baselineからの増加をblockingにする。テスト、migration、fixture、
生成OpenAPI型は明示的に除外する。`design/`文書の800行上限も警告からblockingへ移行する。

### Guardrail 3 — 契約・依存境界

- [x] OpenAPI正規化比較scriptを追加する。
- [x] backend / frontend / Kindleのimport方向を調査する。
- [x] 違反ゼロの境界からCI blockingを有効化する。

`check_openapi_contract.py`はFastAPIアプリから正規化schemaを生成し、
`openapi_baseline.json`との差を検査する。意図したAPI変更では`--update`でbaselineを
更新し、生成型、設計書、差分を同じ変更でレビューする。

`check_import_boundaries.py`は現在違反0件の境界からblockingにする。

- backendのserviceはrouterをimportしない。
- frontendのpage未満の層はpageをimportしない。
- Kindleのcontroller / capturerはagent transport、backend、routerをimportしない。

### Guardrail 4 — 定期監査

- [x] 月1回、肥大化上位、複雑度、未使用依存、docs警告、完了計画残存を確認する。
- [x] 同じ候補を繰り返し検出した場合だけPhaseへ昇格する。
- [x] 結果は変更履歴ではなく、未解決時だけ計画書へ追記する。

月次入口は`uv run python scripts/maintenance/monthly_health_audit.py`とする。
全項目成功時は記録を増やさず、未解決項目が同じ対象で2回連続した場合だけ、
ユーザー挙動を変えないものをリファクタリング計画、依存・インフラ・性能を
技術メンテナンス候補へ起票する。

---

## 8. 完了条件

本計画は次をすべて満たした時点で通常運用へ移し、計画書をarchiveへ移す。

1. docsのリンク、nav、status、サイズにblocking違反がない。
2. 新規production codeの規模・C901悪化をCIで検知できる。
3. OpenAPIの意図しない変更を比較できる。
4. 主要3層の依存方向を少なくとも1つずつ機械検査している。
5. 例外に理由、基準線、期限、再確認条件がある。
6. 月次監査のコマンドと結果の扱いが運用ガイドへ記録されている。
