## 1. 背景・目的

このツールの目的の一つとして「小説（ラノベ中心）について会話する」がある。現状の検証は「読書会ディスカッション」（B-20、2 ペルソナ SSE 対話生成、実装済み）。

最終目標: **特定の本（将来的にはシリーズ）について、10 分程度の動画に相当する分量の会話コンテンツを生成できるようにする。** さらに、その本だけで閉じず、

- 似た別の本を引き合いに出した比較トーク
- その本にまつわる時事ネタ・過去の流行などの小話（脱線）

を自然に織り交ぜられるようにしたい。これを実現するための土台として、本の内容を RAG で即座に引ける状態と、本の内容をタグのように管理する仕組みが要る、というのがユーザーの仮説。

**今回のスコープ**: 実装ではなく、計画書（要件定義）を作るための前段の情報整理。規模が大きいため他の日常作業とは別建てで扱う。

## 3. 今回の対話で確定した方針

| 論点 | 結論 |
|---|---|
| 最終成果物の範囲 | **台本（テキスト）まで**。音声化（TTS）・動画化は将来構想であり今回は対象外。ただし将来の TTS 連携を妨げない設計にする（話者ラベル付きテキストの構造は既に B-20 で担保） |
| 話者形式 | 現行は **2 人**（進行役+専門家等、知識レベルは対等・性格や観点が異なる）。長期的には **3 人以上のパネル形式**も視野に入れるが、今回はまず 2 人構成の拡張から着手 |
| 対象本の粒度 | まず **特定の 1 冊を完成させる**ことを優先。シリーズ・複数巻対応は後続 |
| 類似本の選定範囲 | **ハイブリッド**。RAG 取り込み済みの蔵書内（B-26 の類似度推薦と連携）を優先しつつ、蔵書にない本については LLM の一般知識で補う |
| 時事ネタ・過去の流行の情報源 | **LLM の学習済み知識のみで十分**。リアルタイム Web 検索は今回想定しない（コスト・精度・実装複雑度の観点で見送り） |

## 4. 現行実装とのギャップ（新規に必要になりそうな能力）

### 4.0 面白さの設計原則（2026-07-04 Phase 0a へのユーザーフィードバックから確立）

Phase 0a の出力に対するユーザー評価は「**だらだらと内容について話している感じがして読む気が起きない**」「時事ネタ・過去の流行の小話が一切ない」。これは本機能の品質基準を定義する最重要フィードバック。分析すると Phase 0a 出力がつまらない原因は 4 つ:

1. **対立の不在**: 全ターンが相手への同意（「ええ、本当に！」「そうですよね！」）から始まり、緊張感・意外性がゼロ。ペルソナに「口調の違い」しか与えておらず、**主張（スタンス）の違い**を与えていなかった。
2. **あらすじの再演**: シーンを順に紹介して解釈を添えるだけ。読んだ人には冗長、未読の人には固有名詞の洪水で、どちらの読者にも刺さらない。
3. **視聴者の不在**: 2 人が内輪で確認し合う体裁で、「画面の向こうの視聴者に向けて話す」という概念がプロンプトに存在しなかった。フック・プレゼン・引きが構造的に生まれない。
4. **脱線素材の不在**: 現行プロンプトは「小説の内容を引用しながら語れ」としか言っておらず、モデルを本の中に閉じ込めている。時事ネタ・類似作品への連想は**素材として明示的に渡さない限り出ない**。

ここから導かれる設計原則（Phase 1 以降の要件の核）:

| 原則 | プロンプト/システムへの落とし込み |
|---|---|
| 面白さは創発しない。素材として渡す | 対立軸・フック・脱線ネタカードを生成前に用意してプロンプトに注入する（「構成作家」の仕事をシステム側が担う） |
| ペルソナ=口調ではなく主張 | 各ペルソナに「今回の推し解釈」を持たせ、意見が割れるテーマを最低 1 つ構成に含める |
| 視聴者ファースト | 「未読の視聴者がいる番組の台本」と定義。全肯定相槌の禁止・あらすじ再演の禁止・固有名詞の初出時一言説明・締めまで総括禁止をルール化 |
| 脱線ネタカード | 類似本（B-19 + `books.summary` / LLM 一般知識）・ジャンルの流行史・設定の系譜などを 2〜3 枚、根拠つきでプロンプトに同梱し「脱線コーナー」セグメントで消費させる |
| リズム | ターン長を可変（20〜300 字）にし、短いツッコミ・疑問形を混ぜる指示を入れる |

この原則を反映した「番組台本型プロンプト」の実証は Phase 0b（§6 実測結果参照）。

### 4.1 台本の構成化・尺のコントロール

- 10 分尺の目安: 日本語の自然な話速は概ね 300〜400 字/分 → 10 分で **概算 3,000〜4,500 字程度の発話量**。
- **分量だけなら現行 API パラメータの範囲内で到達可能**: `POST /api/novel/discussion/generate` は `num_turns` を 2〜20 で受け付け（デフォルト 6）、1 発言は 100〜300 字指示。平均 200 字とすると num_turns=10〜13 で 4,000〜5,200 字に届く。つまり Phase 0 の分量検証は**コード変更ゼロ**で既存 API を叩くだけで開始できる。
- 未解決なのは分量ではなく**構成の制御**（イントロ→本編深掘り→脱線→まとめのセグメント分け）と、長い単発出力の後半で品質・多様性が落ちないかの 2 点。構成指示は `_SYSTEM_TEMPLATE`（`discussion_service.py`）への追記で試せる（ペルソナの `style_description` は max 200 字なのでそこに構成指示を詰め込むのは不適）。
- 生成コスト実測の目安（技術知見 §より）: full-book 投入時 prompt processing ~670 t/s・end-to-end 9.8 t/s（入力 78k tok 時）→ 1 回の生成は**数分オーダー**。Phase 0 の反復検証は現実的な速度で回せる。
- **検討要**: 単発呼び出しのまま構成指示を強化するか、セグメントごとに複数回呼び出して結合するパイプライン化か。後者のレイテンシ懸念は当初想定より小さい — llama-server の KV cache は同一 prefix 再送でヒットする（マルチターン QA で実証済み、検索QA設計 §7）ため、書籍本文を含む system prefix を固定すれば 2 セグメント目以降の prompt processing コストはほぼゼロになる。真の課題はセグメント間の内容重複・話題の一貫性の方。

### 4.2 本を横断した自然な脱線（類似本トーク）

- **コンテキスト上の構造的制約（B-26 の要否とは独立に決まる）**: `MAX_INPUT_TOKENS = 112,000` は主対象本の全文でほぼ使い切る前提の設計。**類似本の全文を同時投入することは不可能**。したがって比較セグメントは必然的に非対称構成になる — 主対象本 = 全文、類似本 = 既存の 1500 字サマリ（`books.summary`）+ 必要ならキャラクター辞典の抜粋。
- **類似本の取得手段は既に存在する**（B-26 は前提にならない）:
  - `find_similar_books`（B-19、実装済み）がサマリ embedding KNN で top-N を返す。対話生成側はこれに `books.summary` の取得を組み合わせるだけでよく、新規の類似度インフラは不要。
  - **実測（2026-07-04、現蔵書 19 冊）**: 「後宮の烏」の類似 top-5 はスコア 0.49〜0.52。B-26 の閾値（合成スコア ≥ 0.7）を適用すると **0 件**になる。対話用途では閾値カットではなく「top-N をそのまま使い、スコアが低い場合は LLM 一般知識へフォールバック」する設計が現実的（§3 のハイブリッド方針と整合）。閾値 0.7 という B-26 の値自体も、フル版実装時に実測ベースで見直しが必要な可能性が高い。
  - B-26（ハイブリッド 3 軸 + 事前計算）は精度向上の後続改善として位置づけ直す。本構想の Phase 2 はB-19 で開始できる。
- 蔵書外の本を LLM 一般知識で語らせる場合、内容の正確性は保証されない（ハルシネーションのリスク）。台本用途であれば許容度は高いと考えられるが、事実として扱う体裁にしないなどのプロンプト設計上の配慮が要る。

### 4.3 時事ネタ・過去の流行の小話

- LLM 学習済み知識のみを使う前提なので新規のインフラは不要。プロンプトエンジニアリングで対応可能な領域だが、「本の内容とどう自然に接続するか」（トリガーとなるキーワード・トピックの抽出）には本のトピック情報が要る。

### 4.4 タグ／トピック管理

- 現行の genre 軸は粗すぎる（source 共通のジャンルタグのみ）。脱線トークの「接続点」を見つけるには、本ごとの**トピック・モチーフ単位のタグ**（例: 「学園もの」「タイムリープ」「異世界転生」等）が必要になりそうだが、これは B-26 のメタ Jaccard 軸とも重複しうる領域。両者を統合的に設計すべきか、脱線トーク専用の軽量な仕組みにするかは要検討。

### 4.5 話者フォーマットの拡張（3 人以上パネル）

- 長期構想として明記されているが、`discussion_service.py` の `[A]:`/`[B]:` マーカー方式は 2 話者決め打ちの実装。3 人以上に拡張する場合はマーカー体系・システムプロンプトの一般化が必要（今回は着手しない）。

## 5. まだ決まっていない・検証が必要な論点

1. **尺のコントロール方法**: 単発生成の指示強化 vs セグメント分割 + 複数回生成のパイプライン化。レイテンシは system prefix 固定による KV cache ヒットでほぼ吸収できる見込み（§4.1）のため、判断軸は**セグメント間の内容重複・一貫性 vs 単発長出力の後半品質劣化**のどちらがマシか、になる。Phase 0 の実測で決める。
2. ~~類似本情報の取得方式~~ → **解決済み（2026-07-04 実機確認）**: `find_similar_books`（B-19、実装済み）+ `books.summary` の組み合わせで足りる。残る論点は「スコアがどの程度低い類似本まで対話に載せるか」の線引きのみ（現蔵書の実測ではスコア帯 0.5 前後が上位、§4.2）。
3. **トピックタグの設計主体**: 自動抽出（LLM にタグ付けさせる）か、手動タグ付けか。自動の場合はどの粒度・語彙で統一するか。
4. **蔵書外の類似本を語らせる際の事実性担保**: プロンプトで「これは会話上の一般的な言及であり事実確認はしていない」旨をどう扱うか（台本上は自然な会話を優先し、視聴者向けの注記は動画編集側の責務とする、等の役割分担が必要かもしれない）。
5. **完成の定義（Definition of Done）**: 「1 冊について 10 分尺の台本が安定して出力できる」をどう検証するか（文字数・構成要素の充足・脱線の自然さは定量評価しにくい）。実機での主観評価を前提にするか。

## 6. 想定される段階的アプローチ（技術検証の叩き台・未確定）

計画書化する際のたたき台として、リスクの低い順に並べる（着手順の確約ではない）:

1. **Phase 0a（技術検証・コード変更ゼロ）**: 既存 API を `num_turns=10〜13` で叩き、10 分尺相当（3,000〜4,500 字）の分量が出るか・後半のターンで品質が落ちないかを実測する。
2. **Phase 0b（技術検証・プロンプトのみ変更）**: `_SYSTEM_TEMPLATE` に「イントロ→本編深掘り→まとめ」程度の構成指示を追記し、単発生成のままで構成が守られるかを検証する。ここでパイプライン化の要否が判断できる。
3. **Phase 1**: Phase 0 の結果を踏まえ、単一書籍内で構成化された長尺台本生成を実装（既存 discussion_service の拡張、または新規サービスとして切り出し）。
4. **Phase 2**: 類似本比較セグメントを追加。必要な部品（`find_similar_books` = B-19 + `books.summary`）は実装済みで、残タスクは「類似本のサマリを対話プロンプトへ差し込む結線」のみ（§4.2）。B-26 フル実装は精度向上の後続改善として切り離す。
5. **Phase 3**: 時事ネタ・過去の流行の小話セグメントをプロンプト側で追加（新規インフラ不要、プロンプト設計とトピックタグ整備が中心）。
6. **Phase 4（長期・別バックログ）**: 3 人以上のパネル形式への拡張。

### Phase 0a 実測結果（2026-07-04 実施済み）

対象: 「後宮の烏」（134 ページ）、`num_turns=12`（12 往復 = 24 ターン要求）、ペルソナは冷静分析派（丁寧語）+ 感情移入派（くだけた口調）の 2 人。

| 計測項目 | 結果 |
|---|---|
| 生成ターン数 | **14 ターン（7 往復）で早期終了** — 要求の 58%。最終ターンで自ら「読書会を終えることができました」と締めに入った |
| 総発話量 | 2,902 字 ≈ **8.3 分**（350 字/分換算）。10 分にわずかに届かず |
| 所要時間 | 202 秒（prompt processing 152 秒 + 生成 50 秒）。反復検証に十分実用的 |
| 後半品質 | **劣化なし**。ターン長はむしろ増加（174→238 字）、固有名詞・シーン引用・ペルソナ書き分けも最終ターンまで維持 |
| 品質上の瑕疵 | ターン #10 に中国語混入 1 箇所（「〜の行為**变成了**」）。Qwen の言語リーク。後処理での検出 or プロンプトでの抑制指示が必要 |

**結論・示唆**:
- ボトルネックは分量上限でも後半品質でもなく、**ターン数指示の遵守**。モデルは自然な談話アーク（導入→深掘り→総括）に沿って早期収束する。皮肉なことに「構成」は既に自然発生しており、問題はそのアークが指定尺より短く閉じること。
- §5 論点 1 の判断軸を更新: 「単発長出力の後半品質劣化」は実測で否定された。次の Phase 0b では「まとめに入るタイミングの制御」（例: セグメント構成の明示 + 「合図があるまで総括しない」指示）で単発生成のまま尺が伸ばせるかを検証し、ダメならセグメント分割パイプラインに進む。
- 副産物: 中国語リーク対策（プロンプト 1 行 or 後処理）を Phase 1 の要件に含めること。
- **ユーザー評価（Phase 0a 出力）**: 「だらだらと内容について話している感じで読む気が起きない」「時事ネタ・脱線が一切ない」→ §4.0 の面白さの設計原則として要件化。

### Phase 0b 実測結果（2026-07-04 実施済み — 番組台本型プロンプト）

§4.0 の設計原則を反映したプロンプト（ペルソナに対立する主張・5 セグメント番組構成・脱線ネタカード 3 枚・全肯定/あらすじ再演/早期総括の禁止・セグメント別ターン数指定）で同一書籍・同一 LLM 設定のまま再生成。製品コードは未変更（テストハーネスでカスタム messages を `stream_discussion_turns` に直接投入）。

| 計測項目 | 結果 |
|---|---|
| 内容品質 | **激変**。OP フック（「また中華風後宮ロマンスかと敬遠していませんか？」）・明確な対立（「それは浅い読み方だと思います」vs「またその理屈の話？」）・脱線コーナー（『薬屋のひとりごと』比較→『十二国記』の系譜→本作へ復帰）・締め（「どんな人に刺さるか」+ 星 5 つ）がすべて指示どおり出現 |
| ターン数 | 実質 約 24 ターン（セグメント別ターン数指定が有効に機能。Phase 0a の全体数指定より遵守率が大幅改善） |
| 総発話量 | 2,681 字 ≈ 7.7 分。目標 10 分にはまだ不足 → セグメント別ターン数の増量で調整可能な見込み |
| 所要時間 | 223 秒（Phase 0a と同等） |
| **新規の問題 1: マーカードリフト** | 出力途中（5 ターン目以降）で話者マーカーが `[A]:` → `[A>:` に崩れ、既存パーサ（`\[([AB])\]:`）が分割に失敗。残り全ターンが 1 つの塊として扱われた。**Phase 1 でパーサの寛容化（`[A>:` 等の揺れ許容）が必須要件** |
| 新規の問題 2: 脱線でのハルシネーション | 『薬屋のひとりごと』の主人公を「ミソギ」と誤称（正: 猫猫）。**脱線ネタカードには作品名だけでなく正確な固有情報（主人公名等）を含めるか、「カードに書かれた事実以上の詳細に踏み込まない」指示が必要** |
| 言語リーク | 中国語混入は 0（禁止指示が有効）。代わりに英語 1 箇所（「琥珀」→「amber の魚」） |

**結論**: 「面白さは素材として渡す」原則は単発生成でも有効に機能する。Phase 1 の実装要件は (1) 番組構成テンプレート + 脱線ネタカードのプロンプト組み込み、(2) マーカーパーサの寛容化、(3) ネタカードへの正確な固有情報の同梱（ハルシネーション抑制）、(4) セグメント別ターン数の増量による 10 分尺到達、(5) 言語リークの後処理検出。

> 実装時の周辺メモ: `save_discussion`（`discussion_service.py`）のファイル名タイムスタンプは JST の `datetime.now(JST)` に UTC を示す `Z` サフィックスを付けており表記が不整合（docstring も「UTCタイムスタンプ」と記載）。実害はないが、本機能でディスカッション保存形式を触る際についでに直すとよい。

## 8. 付録: Phase 0b 実証済みプロンプト（Phase 1 実装のベース）

Phase 0b で品質改善を実証したシステムプロンプトの全文（`{book_name}` / `{book_text}` は既存テンプレートと同じプレースホルダ。ペルソナの主張・テーマの問い・脱線ネタカードは書籍ごとに差し替える可変部）:

```
あなたは本好き向けトーク番組の放送作家兼出演者AIです。課題本について2人のパーソナリティが語り合う動画番組の「台本」を書いてください。画面の向こうには視聴者がいます。視聴者はこの本をまだ読んでいないかもしれません。

## 課題本
{book_name}

## 小説本文（全ページ）
{book_text}

## パーソナリティ（スタンスの対立が番組の生命線）
- **レイ [A]**: 構造・テーマ分析派。今回の主張は「本作は恋愛ものの皮を被った『歴史の隠蔽と沈黙』のミステリーである。ロマンスとして読むのはもったいない」。理屈っぽいが、たまにミオの熱量に押されて本音が漏れる。丁寧語。
- **ミオ [B]**: キャラクター・感情派。今回の主張は「理屈はどうでもいい、寿雪と高峻の不器用な関係性こそ本体。ミステリー要素はおまけ」。レイの分析に「またそういう小難しい話を…」とツッコみつつ、直感で核心を突くタイプ。くだけた口調。

## 番組構成（この順番で進行する。セグメント見出しや区切り記号は出力しない）
1. **OPフック（2〜3ターン）**: 視聴者を掴む。あらすじ紹介から入るのは禁止。「〇〇だと思って敬遠してる人、損してます」のような引きで始める。
2. **テーマ1（6ターン前後）**: 「高峻（皇帝）が寿雪（烏妃）に執着するのは、愛か、利用か、それとも贖罪か」— 2人の解釈がはっきり割れること。決着はつけなくてよい。
3. **テーマ2（6ターン前後）**: 「『後宮にいるのに夜伽をしない妃』という烏妃の設定はなぜ巧いのか」— 設定の面白さを視聴者にプレゼンする。
4. **脱線コーナー（4〜6ターン）**: 下の「脱線ネタ」から1〜2個を使って本作からいったん離れ、また自然に本作へ戻ってくる。脱線こそ番組の華。
5. **締め（3ターン）**: それぞれ「どんな人に刺さる本か」を一言 + 例えや点数など印象に残る評価で終える。このセグメントに入るまで、総括・まとめの空気を出すことを禁止する。

## 脱線ネタ（この材料から選んで使う。無理に全部使わなくてよい）
- 『薬屋のひとりごと』のアニメ化以降、中華後宮ミステリーが一大ジャンルになった流れ。本作はその流れの中でどんな立ち位置か
- 『彩雲国物語』『十二国記』など中華風ファンタジーの系譜と、少女小説の伝統芸「与えられた役割から解放されていく少女」
- 「後宮×幽霊」という組み合わせの妙。閉鎖空間で女たちの愛憎が渦巻く後宮は、そもそもホラーと相性が良すぎる

## 会話のルール
- **安易な同意の禁止**: 「ええ、本当に！」「そうですよね！」のような全肯定で発言を始めない。各テーマで最低1回は反論・別解釈・茶々を入れる
- **あらすじの再演禁止**: シーンの引用は「自分の主張の証拠」として出すときだけ。物語を頭から順になぞらない
- ターンの長さは20〜300字で可変。短いツッコミや疑問形を混ぜて会話にリズムを作る
- 登場人物名は初出時に一言説明を添える
- 出力は日本語のみ。中国語の語彙・簡体字を混ぜない
- レイの発言は `[A]:`、ミオの発言は `[B]:` で始める。それ以外のヘッダー・前置き・後書きは一切出力しない
```

user メッセージ: 「番組台本をお願いします。構成の順番と各セグメントのターン数目安を守り、締めセグメントに入るまで総括しないでください。合計 21〜24 ターンを目安に。」

Phase 1 での改善ポイント（§6 Phase 0b 実測結果より）: マーカードリフト（`[A>:`）へのパーサ寛容化・脱線ネタカードへの正確な固有情報同梱（例: 薬屋の主人公名「猫猫」を明記）・セグメント別ターン数の増量（10 分尺到達）・英語リーク対策。
