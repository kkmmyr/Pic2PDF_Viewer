# ADR-0018: OCR後の公開成果物をSol主生成・選択的独立評価へ段階移行する

- **Status**: Accepted
- **Date**: 2026-08-02
- **決定者**: プロジェクトオーナー
- **関連**: [ADR-0007](0007_llm-extraction-qwen-adoption.md) / [小説RAG Sol主生成・選択的独立評価設計](../../詳細設計/機能別/小説RAG_Sol生成・評価設計.md) / [小説RAG パイプライン設計](../../詳細設計/機能別/小説RAG_パイプライン設計.md) / [バックログ B-36](../../../log/計画/バックログ.md)

## コンテキスト

小説OCR後の事実抽出、詳細あらすじ、一覧用短縮要約、人物辞典をQwen3.6 35B-A3B中心で構築し、
Gemma4 31BとCodex Lunaを補助評価候補として比較した。茉莉花官吏伝10巻では、途中の「牢へ戻る」と
最終的な「最長10年間逃げ続ける」をQwenが混同し、同じQwenによる根拠検証も誤りを支持した。

Gemma4 31Bは固定1件を正しく判定したが、全巻生成は1工程20分を超え、重要事実の省略と意味変更が残った。
Lunaは構造化、外部状態契約、独立ブロック、機械ゲートを追加しても有界再試行後の自動合格が4ブロック中
3ブロックに留まった。Luna事実とQwen執筆を組み合わせた結果は主体を改善したが、期間上限の断定化、
中国字混入、未確定方針の過剰確定が残った。

ローカル推論の電力・時間だけでなく、モデル切替、再試行、Schema調整、相関誤りの独立確認、手動救済を含む
総作業コストが高くなっている。ユーザーはOCR本文の外部送信を許可し、ChatGPT側のモデル改善利用を
オフにしたうえで、品質評価を前提にGPT-5.6 Solを利用する方針を選んだ。

## 検討した選択肢

| 選択肢 | 概要 | 採用しなかった理由 |
|---|---|---|
| A. Qwen中心を継続しローカルゲートを追加 | Qwen生成、Gemma/Luna検証、Codex最終確認 | 同系統誤りと多段運用コストが残り、重大な固定誤りを安定して閉じられない |
| B. Luna抽出 + Qwen生成を本番化 | Lunaを構造化抽出、Qwenを文章生成に限定 | 厳格化後も4ブロック中1ブロックが主体・末尾網羅で不合格。手動救済が必要 |
| C. Solを最終評価だけに使用 | ローカル生成物を巻全体または高リスク箇所だけSolで確認 | 低品質候補を作るローカル多段工程が残り、総作業時間を十分減らせない |
| **D. Sol主生成 + 高リスク主張だけ別Solセッションで独立評価** | 1回の全文読解で全公開候補を生成し、決定的検査はローカル、意味評価は選択実行 | （採用） |
| E. OpenAI APIへ直接統合 | Responses APIをバックエンドから呼び夜間完全自動化 | サブスクリプションと別課金・別データ方針になる。現時点のユーザー許可範囲を超える |

## 決定

1. OCR承認済み本文からの事実表、詳細あらすじ、一覧用短縮要約、人物辞典は、Solによる1冊1回の
   主生成へ段階移行する。
2. Schema、SHA、正規名、文字数、禁止表記、期間・主体の形式整合はローカルで検査し、否定、最終状態、
   拘束主体、期間上限等の高リスク主張だけを別の新規Solセッションで原文照合する。
3. 初期版はMac上のCodex CLIとChatGPTログインを使用する。APIキー課金へ自動切替せず、Linuxサーバーへ
   Codex認証キャッシュを複製しない。
4. 固定パイロット合格までは現行Qwen経路と公開DBを変更しない。Qwenは対話QAとオフライン代替として残す。

## 根拠

- Solは複雑な推論、曖昧な問題、高い判断品質向けのモデルとして位置付けられ、小説の長距離照応、
  主体、時系列、途中状態と最終状態の判定に役割が合う。
- 生成と評価の両方をSolへ寄せても、評価を新規セッション・原文ページ窓・高リスク主張だけに限定すれば、
  巻全文を複数モデルへ繰り返し投入するより利用量と運用工程を減らせる。
- JSON Schema、ハッシュ、表記、文字数等はローカル検査の方が安価で決定的である。
- 1冊1新規セッションと外部状態契約により、Compactの品質や長期会話の過去要約に依存しない。
- `codex exec`は非対話パイプライン、read-only sandbox、ephemeral session、JSONL、JSON Schema出力を
  公式に備え、初期のローカルCLI境界に適合する。

## 結果（Consequences）

### ポジティブ

- Qwen、Gemma、Lunaを順番に切り替える運用を通常経路から外せる。
- 1回の全文読解で全公開候補を生成し、追加利用を高リスク箇所へ集中できる。
- 既存の公開一括確定、旧版差分、fail closedを維持できる。
- ChatGPTログインをMacに留め、サーバーやリポジトリへ認証情報を持ち込まない。

### ネガティブ・受容したコスト

- OCR本文をOpenAIへ送信する。書籍単位の明示的opt-inとデータ最小化が必要になる。
- サブスクリプション利用上限、再ログイン、Codex CLI仕様変更により夜間処理が停止し得る。
- ChatGPT側のモデル改善利用オフはアプリから強制・検証できず、運用前提として管理する。
- 同一モデル系統の独立評価であるため、相関誤りを完全には除去できない。固定コーパスと人手承認を残す。
- API利用のSLA、ZDR、完全自動化は得られない。必要になった場合は別のAPI統合判断が必要になる。

### 影響範囲

- [小説RAG Sol主生成・選択的独立評価設計](../../詳細設計/機能別/小説RAG_Sol生成・評価設計.md)に
  入出力、状態、セキュリティ、段階導入、受入条件を定義する。
- 実装候補は入力export、Codex CLI runner、候補validator、risk selector、結果import、単一書籍CLI。
- 固定パイロット合格後に、DB staging、API、UI、全冊バッチの要否を改めて設計する。
- ADR-0007のQwen採用は対話QA・オフライン代替として維持し、OCR後公開成果物の主生成判断だけを本ADRが追補する。

## 将来の再評価条件

- サブスクリプション利用上限で通常の冊数を処理できない。
- 成功1冊あたり利用量または人手修正時間がQwen中心経路を上回る。
- 固定10〜20件または3冊以上で重大誤り・重大見逃しが残る。
- ZDR、保存期間、SLA、完全自動化が必要になり、Responses API統合の方が妥当になる。
- 64GBローカル環境でSol相当品質のモデルを十分な速度・安定性で運用できる。
- Sol/Terra/Lunaの役割、Codex CLI認証、利用条件が変更される。
