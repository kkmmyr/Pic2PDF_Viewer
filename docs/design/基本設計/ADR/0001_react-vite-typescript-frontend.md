# ADR-0001: フロントエンドに React + Vite + TypeScript を採用

- **Status**: Accepted
- **Date**: 2026-01-12（プロジェクト初期、遡及記録 2026-05-07）
- **決定者**: プロジェクトオーナー
- **関連**: [基本設計書.md](../基本設計書.md)、[詳細設計書_フロントエンド編.md §1.2 ファイル詳細マップ](../../詳細設計/詳細設計書_フロントエンド編.md)

## コンテキスト

WebP 画像・ZIP を PDF 化してブラウザで閲覧する個人向け Web アプリの SPA フロントエンドが必要になった。要件:

- ローカル LAN 専用、シングルユーザー
- PDF ビューア・ライブラリ管理・メタデータ編集 UI
- 開発者は 1 人（プロジェクトオーナー）
- 個人ツールであり「プロダクションでの実績豊富な技術」より「自分が手早く実装できる技術」を重視

## 検討した選択肢

| 選択肢 | 概要 | 採用しなかった理由 |
|---|---|---|
| Vue + Vite | エコシステム成熟、Composition API | プロジェクトオーナーの業務経験が薄く、学習コストが利得を上回る |
| Svelte / Solid | コンパイル時最適化で軽量 | 業務経験なし、トラブル時の独力解決の不安 |
| Next.js (React 上位) | SSR / ファイルベースルーティング | SSR 不要（LAN SPA）、Vite より起動が遅い |
| 素の Webpack | 設定の自由度 | 設定の重さが個人開発の摩擦になる |
| **React + Vite + TypeScript** | 業務で慣れた構成 + 高速 dev server | （採用） |

## 決定

フロントエンドは **React 18 + Vite + TypeScript** で構築する。

## 根拠

- **React**: プロジェクトオーナーが業務で最も多く使う FW で、API・パターン・トラブル対応が手に染みている。「練れている」状態の技術を選ぶことで、個人ツール開発の摩擦を最小化する。
- **Vite**: 直近の業務／個人プロジェクトで最も採用頻度が高く、HMR と起動速度の体験が快適。Next.js は SSR を要件としないため不要なオーバーヘッドになる。
- **TypeScript**: 「型がないと不便」という明確な要望。Hooks の戻り値・コンポーネント Props・API レスポンスの整合性確認に効く。

## 結果

### ポジティブ
- 開発速度が高い（学習コストゼロ）
- React エコシステム（Tailwind / dnd-kit / react-pdf / axios 等）の選定で詰まらない
- TypeScript により API 型整合の崩れが早期に検出される

### ネガティブ・受容したコスト
- React の再レンダリングコスト（`useMemo` / `useCallback` の手動最適化が散在）→ 詳細設計書で規約化済み
- Vite の本番ビルドは Webpack ほど枯れていない（が、現行構成では問題出ていない）

### 影響範囲
- `frontend/` 配下すべて
- `frontend/package.json` の依存ツリー全体

## 将来の再評価条件

- React の代替（Solid 等）が業務でも一般化したとき
- バンドルサイズが許容範囲を超えて遅延ロード戦略では追いつかなくなったとき
- TypeScript ↔ Pydantic の型同期コストが顕著になったとき（ADR-0002 と同時に再考）
