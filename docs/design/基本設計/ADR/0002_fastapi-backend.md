# ADR-0002: バックエンドに FastAPI を採用

- **Status**: Accepted
- **Date**: 2026-01-12（プロジェクト初期、遡及記録 2026-05-07）
- **決定者**: プロジェクトオーナー
- **関連**: [基本設計書.md](../基本設計書.md)、[詳細設計書_バックエンド編.md §1.5 ファイル詳細マップ](../../詳細設計/詳細設計書_バックエンド編.md)

## コンテキスト

WebP / ZIP → PDF 変換 + ライブラリ管理 + OCR 起動を行う Web API バックエンドが必要になった。要件:

- ローカル LAN 専用、シングルユーザー
- 長時間の OCR / PDF 生成ジョブを非同期で実行できること
- メタデータ管理（meta.json）の CRUD API
- フロントエンド (React + TypeScript) と JSON でやりとり

## 検討した選択肢

| 選択肢 | 概要 | 採用しなかった理由 |
|---|---|---|
| Django | フルスタック、ORM・admin 同梱 | ORM 不要（meta.json 使用）、機能過多で個人ツールには重い |
| Flask | 軽量で柔軟 | async サポートが後付けで限定的、型検証は別ライブラリ追加要 |
| Starlette 単体 | FastAPI のベース、より低レベル | DI / Pydantic 統合などのフルスタックが欲しい |
| Bottle | 1 ファイルで動く軽量 FW | コミュニティ・型サポートが弱い |
| **FastAPI** | async ファースト、Pydantic 統合、型ベース | （採用） |

## 決定

バックエンドは **FastAPI** で構築する。

## 根拠

- **慣れている**: プロジェクトオーナーが業務でも採用しており、トラブル対応が手早い。
- **async/await**: OCR や PDF 生成など長時間ジョブを非同期で扱う設計を当初から想定していた（`/api/ocr/run` / `/api/generate` のジョブパターン）。Django/Flask の async は後付けで設計に無理がある。
- **Pydantic**: 現状はリクエスト／レスポンスが小規模だが、機能拡張で大規模化する場合に型検証は必須になる見込み。早めに採用しておけば後付けコストがゼロ。

## 結果

### ポジティブ
- ジョブ系エンドポイント（generate / ocr / hitomi）の async 設計が自然
- Pydantic モデルと TypeScript 型の対応関係が見えやすい
- 起動・記述ともに軽量（個人ツールの開発体験に合う）

### ネガティブ・受容したコスト
- TypeScript 型と Pydantic モデルの**手動同期**が必要（自動生成は採用せず — [リファクタリング計画書 § 対象外](../../../log/計画/リファクタリング計画書.md)）
- FastAPI の DB 統合（SQLAlchemy 等）を使っていないため、ORM 採用時に別 ADR 化する必要あり

### 影響範囲
- `backend/` 配下すべて
- `backend/pyproject.toml` の依存ツリー全体
- API 仕様書 [API仕様書.md](../../詳細設計/API.md) の前提

## 将来の再評価条件

- 大規模化で OpenAPI スキーマ自動配布の要件が出たとき（→ Pydantic 中心の設計が活きる）
- Django Ninja / Litestar 等の後継 FW が業務で一般化したとき
- マルチユーザー化や認証要件が出たとき（FastAPI のセキュリティスキーム再評価）
