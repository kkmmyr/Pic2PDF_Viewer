# セキュリティ設計書

> status: living | last-verified: 2026-07-18

本アプリケーションのセキュリティ設計の根拠・防御範囲・制限をまとめる。

---

## 1. 信頼モデル

本アプリケーションは**ローカルホスト専用のシングルユーザーツール**。

- **想定環境**: `localhost:8766` (API・dev) / `localhost:5176` (UI・dev) / `localhost:8090` (リリース統合) をローカル PC で使用する
- **想定攻撃者**: 外部ネットワークからの不正アクセス、または悪意あるウェブページからの CSRF
- **想定外**: マルチユーザー認証、データの暗号化保存、監査ログ

> 認証・認可機能は実装していない。LAN 外に公開することを想定していないため、必要になった場合は別途設計が必要。

## 2. バックエンド セキュリティ

### 2-1. CORS

**ファイル**: `backend/main.py` / `backend/config/__init__.py`

```python
# デフォルト許可オリジン
_default_origins = "http://localhost:5176,http://127.0.0.1:5176"
CORS_ORIGINS = os.environ.get("ALLOWED_ORIGINS", _default_origins).split(",")
```

- `localhost` / `127.0.0.1` のみ許可（ポート 5176 = フロント開発サーバー）
- 環境変数 `ALLOWED_ORIGINS` で上書き可能（LAN 内共有等の拡張時）
- `allow_methods=["*"]` は CORS ヘッダーの制御用であり、実際の認可ではない

### 2-2. パストラバーサル防止

**ファイル**: `backend/utils/path_utils.py`

全エンドポイントでユーザー入力パスを検証し、データディレクトリ外へのアクセスを防ぐ。

| 関数 | 防御対象 | 拒否する入力例 | 拒否しない入力例（誤検出回避） |
|---|---|---|---|
| `validate_safe_path(path)` | ディレクトリトラバーサル | `..`, `../etc/passwd`, `foo/../bar`, `/etc/passwd`, `\\server\share` | `わたし...変えられちゃいました.pdf` 等、`..` を成分として含まないファイル名 |
| `validate_safe_name(name)` | パスセパレータを含む名前 / 特殊成分名 | `..`, `.`, `folder/file.pdf`, `..\\foo` | `..secret`, `My....pdf` 等、名前自体が `..` / `.` ではない文字列 |

**検証ルール (`validate_safe_path`)**:
- パスを `/` または `\\` で分割し、**いずれかの成分が `".."` と完全一致** → `HTTP 400`
- `"/"` で始まる → `HTTP 400`（Unix 絶対パス）
- `"\\"` で始まる → `HTTP 400`（Windows UNC パス）
- 正規化: バックスラッシュをスラッシュに統一して返す

> **設計判断**: `".."` を部分文字列で検出する単純実装はファイル名中の三点リーダ的な `...`（連続 3 ドット）を誤検出するため採用しない。OS が `..` を特別扱いするのは「パス成分として `..` 単独」のときだけであり、`foo..bar` や `わたし...` は OS にとってただの名前で安全。

**検証ルール (`validate_safe_name`)**:
- 名前が `"."` または `".."` と完全一致 → `HTTP 400`（カレント／親ディレクトリ参照を防止）
- `"/"` または `"\\"` を含む → `HTTP 400`（パスセパレータ混入を防止）

**適用箇所**: `routers/library.py` / `routers/meta/` パッケージ（`core.py` / `novel.py` / `admin.py`） / `routers/pdfs.py` / `routers/thumbnails.py` の全パラメータ受け取り箇所。`routers/genres.py` の `DELETE /genres/{name}` も `validate_safe_name(name)` を呼ぶ（ジャンル名はファイルパスにならない設計だが、設計書整合性のため明示的に検証）。

### 2-3. ファイル種別チェック

**ファイル**: `backend/utils/file_utils.py`

`config.py` で許可する拡張子を一元管理し、直書きチェックを禁止。

```python
is_pdf_file(name)   # .pdf
is_webp_file(name)  # config.SUPPORTED_WEBP_FORMAT
is_zip_file(name)   # config.SUPPORTED_ZIP_FORMAT
is_image_file(name) # config.SUPPORTED_IMAGE_FORMATS
```

任意ファイルを処理対象に混入させる攻撃に対する防御。

### 2-4. meta.json 更新のアトミック性

**ファイル**: `backend/services/meta_store.py`

`update_meta_locked(source, updater)` はファイルロックと updater パターンで実装。
複数リクエストの並行書き込みによるデータ破損を防ぐ。

### 2-5. ZIP 解凍上限（zip bomb 対策）

**ファイル**: `backend/config/__init__.py` / `backend/services/pdf_generator.py`

`generated` ソースの ZIP 入力に対する DoS 対策。`process_zip()` は ZIP を開いた直後・解凍前に `_check_zip_safety(webp_infos, zip_filename)` を呼び、以下の上限を超える場合は ValueError を投げてジョブの `failed_items` に集約する。

| 定数 | 値 | 意味 |
|---|---|---|
| `ZIP_MAX_ENTRIES` | 5000 | ZIP 内 WebP エントリ数の上限 |
| `ZIP_MAX_PER_FILE_BYTES` | 50 MB | 1 エントリあたりの解凍後サイズ上限 |
| `ZIP_MAX_TOTAL_UNCOMPRESSED_BYTES` | 2 GB | 全エントリの解凍後サイズ合計上限 |

値は **個人ツールの想定範囲（〜1000 ページ × 〜500KB WebP ≒ 500MB / 1 冊）に余裕を持たせた**もの。超過は事実上不正な ZIP（zip bomb）か、想定外の大規模入力なので一律拒否する。

拒否時は `logger.warning("Security: ZIP rejected (<filename>) — <reason>", ...)` で**監査用ログ**を残す。一般的な I/O 失敗（`logger.error("Failed to generate PDF for ZIP %s ...", ...)`）と異なる接頭辞 `Security:` で出力するため、ログ走査時に区別できる。ログは [`backend/data/logs/app.log`](../../backend/data/logs/) にファイル永続化されるため（[ADR-0006](../基本設計/ADR/0006_backend-log-file-persistence.md)）、ターミナルを閉じても監査痕跡が残る。

ZipSlip 対策は `os.path.basename(image_name)` で抽出パスを書籍ディレクトリ直下に正規化することで担保（`zf.extract()` は使わない）。

### 2-6. ログへの絶対パス露出抑止

**ファイル**: `backend/services/pdf_generator.py` / `backend/services/ocr_service.py`

`logger.info` / `logs.append` で ZIP パス・出力パス・OCR ランチャーパスをログ出力していた箇所は、Windows ユーザー名 (`C:\Users\<user>\...`) が露出するリスクがあるため、`os.path.basename(...)` ベースに変更。スクショ・配布ログ・Discord 通知連携での個人情報漏洩を予防する。

## 3. フロントエンド セキュリティ

### 3-1. ファイル名バリデーション

**ファイル**: `frontend/src/utils/validation.ts`

```typescript
export const FORBIDDEN_FILENAME_CHARS = /[/\\:*?"<>|]/;
```

Windows / macOS / Linux 共通の禁止文字を除外。各ダイアログで個別に正規表現を再定義しない（`validateFilename(value, kind)` を共有）。

### 3-2. XSS 防止

- React の JSX は文字列をデフォルトでエスケープするため、通常の文字列表示での XSS は発生しない
- `dangerouslySetInnerHTML` は使用していない
- PDF ファイル名・メタデータをそのまま `innerHTML` に渡す箇所はない

### 3-3. ダイアログの標準化

`confirm()` / `alert()` は使用禁止（`coding_conventions.md` 参照）。
共通コンポーネント `ConfirmDialog.tsx` を使用することで、ユーザー操作の一貫性とフィッシング的な悪用を防ぐ。

## 4. 依存関係のセキュリティ

### 自動ゲート

- **シークレット検査**: pre-commit は公式 `gitleaks` フックを固定バージョンで実行し、commit 対象の秘密情報を検出する。GitHub Actions でも `gitleaks/gitleaks-action` を実行し、ローカルフックを迂回した push / PR を検査する。
- **フロントエンド依存監査**: frontend CI の `npm ci` 後に `npm audit` を実行し、既知脆弱性があれば job を失敗させる。
- **Python依存監査**: backend CI の `uv sync` 後に `backend/tools/dependency_audit.py` を実行する。内部では `uv audit --locked` を呼び、`security/uv-audit-allowlist.toml` の期限・理由付き例外だけを許容する。期限切れ例外は監査実行前に失敗させる。

例外は「修正版へ即時更新できない互換性上の理由」がある場合のみ登録し、パッケージ・脆弱性ID・期限・理由を必須とする。期限更新だけで延命せず、期限到来時に実機互換性を再評価する。

### 監査手順

```bash
# /audit コマンドで一括実行
cd frontend && npm audit
cd backend && uv run python -m tools.dependency_audit
```

### 判断基準

| 重大度 | 対応 |
|---|---|
| critical / high | 速やかに対処（`npm audit fix` または手動更新） |
| moderate | dev dependency 由来かを確認し、本番影響なければ放置可 |
| low | 原則放置（次回更新時にまとめて対応） |

## 5. 将来の拡張時の注意

- **LAN 公開**: `ALLOWED_ORIGINS` に加え、認証機能（Basic 認証 or トークン）の追加を検討
- **ファイルアップロード機能追加**: Content-Type 検証とファイルサイズ上限の実装が必要
- **外部 API 連携拡張**: API キーを環境変数で管理し、ソースコードにハードコードしない
