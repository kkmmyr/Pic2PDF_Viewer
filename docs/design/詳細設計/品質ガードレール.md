# 品質ガードレール

> status: living | last-verified: 2026-08-22

<!-- contract-owner: quality-guardrails -->

設計書とソースコードの肥大化・設計ドリフト・契約破壊を継続的に防ぐための
現行ルールを定義する。導入過程と完了Phaseは
[設計書・ソースコード健全性維持計画](../../archive/設計書・ソースコード健全性維持計画.md)
に凍結している。

---

## 1. 正本と文書の寿命

| 情報 | 正本 |
|---|---|
| 現在の要件・設計・運用 | `docs/design/` |
| 進行中の計画・技術知見・既知の問題 | `docs/log/` |
| 完了計画・検証過程・撤去済み仕様 | `docs/archive/` |
| API構造 | FastAPI `/openapi.json` |
| DB構造 | Alembic migration。SQLModelはautogenerate補助 |
| ファイル配置 | 自動生成ファイルマップ |
| 継続必須の開発規約 | `AGENTS.md`とproject skills |

- 同じ一覧やスキーマを複数文書へ手書きしない。
- 設計書には、自動生成物だけでは表せない意図、境界、失敗時挙動を記載する。
- 完了計画は完了を記録する変更で`archive/`へ移す。
- living文書へPhase番号や検証過程を残さず、設計判断の理由はADRへ記録する。
- `last-verified`は、内容を実装または運用実績と照合した場合だけ更新する。

### 1.1 横断事実の所有と競合解決

横断的な事実の所有文書は[ドキュメント案内の正本マップ](../../index.md#canonical-map)
で一意に定める。新しい横断契約を追加するときは、複数文書へ説明を複製する前に正本マップへ
所有文書を追加する。

- 機械可読契約は値と構造の正本、設計書は意味・境界・変更手順の正本とする。
- 計画は未来、技術知見は実測、archiveは過去を所有し、現在の契約を再定義しない。
- MkDocs管理外のモジュール文書は実装内部だけを所有し、横断契約へリンクする。
- 競合時は暗黙に片方へ合わせず、正本マップ、機械可読契約、実装の順で照合する。
- 正本を移す変更では、旧所有文書を同じコミットでリンクへ置き換え、移行途中の二重所有を残さない。

## 2. 設計書ガードレール

`scripts/maintenance/check_docs.py`は次の8項目をすべてblockingとして検査する。

| Rule | 検査 | 合格条件 |
|---:|---|---|
| 1 | living文書の相対リンク | リンク切れ0件 |
| 2 | `docs/log/変更履歴.md`の行数 | 800行以内 |
| 3 | MkDocs nav | dead entry / orphan 0件 |
| 4 | `docs/design/`文書の行数 | 各800行以内 |
| 5 | design文書のstatusヘッダ | 冒頭10行以内に存在 |
| 6 | ファイルマップの主要ファイル補足 | 参照切れ0件 |
| 7 | 横断契約ownerの正本マップリンク | 登録owner全件が正本マップから到達可能 |
| 8 | 横断契約owner marker | 欠落・未登録・別文書への重複0件 |

Rule 7〜8の対象は`scripts/maintenance/docs_contracts.json`へ限定列挙する。各owner文書は
`<!-- contract-owner: <ID> -->`を1個だけ持ち、同じIDを他文書で宣言しない。
意味の近さを曖昧に判定するのではなく、レビュー済みの高リスク横断契約だけを機械検査する。

CIではこれに加えて`mkdocs build --strict`を実行する。ファイルマップは
`scripts/maintenance/generate_file_map.py`で生成し、手編集によるドリフトを許さない。

設計書変更時の確認観点:

- 現在形で読んだときに旧仕様と誤認しないか。
- 実在しないファイル、class、API、設定名がないか。
- API一覧やファイルツリーを手書きで複製していないか。
- 完了済み計画が`log/計画/`に残っていないか。
- 正本でない文書が横断的な事実を再定義していないか。

## 3. ソースコードの規模と複雑度

### 3.1 規模

生成物、migration、凍結・期限付きpilot、テストfixtureを除くproduction codeを対象とする。
`backend/`、`kindle-pdf/`、`frontend/src/`に加え、継続運用する`scripts/`と
`common/llm`のpackage/CLI/MCPも対象に含める。scriptの分類正本は
[保守資産・互換層台帳](../環境構築/保守資産・互換層台帳.md)とし、期限付き除外には
owner、理由、再評価日を必須とする。

| 物理行数 | 扱い |
|---:|---|
| 400行以下 | 通常範囲 |
| 401〜500行 | 変更時に責務数を確認 |
| 501〜800行 | 分割要否を計画書へ記録し、理由なく増加させない |
| 801行以上 | P1調査対象。変更前にcharacterization testを用意する |

`scripts/maintenance/check_code_size.py`は既存超過を
`scripts/maintenance/code_size_baseline.json`へ固定し、新規超過と基準線悪化を
blockingにする。数値だけを理由に分割せず、責務境界と変更理由で判断する。

### 3.2 複雑度

`scripts/maintenance/check_c901_ratchet.py`はRuff C901の既存超過を
`scripts/maintenance/c901_baseline.json`と比較する。

- 新規関数のC901超過を禁止する。
- 既存超過関数を変更する場合は複雑度を増やさない。
- 改善済みentryを基準線へ戻さない。
- baseline変更は専用maintenance変更としてレビューする。

### 3.3 分割判断

次のうち2つ以上を満たす場合を分割候補とする。

- 異なる理由で変更される責務が同居している。
- C901などの複雑度超過がある。
- 直近の変更量が大きく、競合や回帰が繰り返されている。
- テストで外部環境を大量mockしないと検証できない。
- API、DB、ファイルI/O、UI操作など複数の副作用境界をまたぐ。

2箇所の類似だけでは共通化しない。3箇所以上、または同じ不具合修正が
複数箇所へ必要になった時点で検討する。

## 4. 契約と依存方向

### 4.1 外部契約

| 対象 | 比較方法 |
|---|---|
| FastAPI | 正規化した`openapi.json`の差分 |
| DB | migration head、schema、主要query結果 |
| Kindle capture | error code、状態遷移、manifest、画像寸法・枚数 |
| OCR | 固定fixture本文、品質flag、CER |
| Reader | RTL/LTRページ遷移表 |
| ファイル公開 | 障害注入によるrollback結果 |

`scripts/maintenance/check_openapi_contract.py`はFastAPIから生成した正規化schemaを
`scripts/maintenance/openapi_baseline.json`と比較する。意図したAPI変更では
`--update`を使用し、生成型、設計書、差分を同じ変更でレビューする。

### 4.2 依存方向

`scripts/maintenance/check_import_boundaries.py`は次の違反ゼロ境界をblockingにする。

- backend: serviceからrouterをimportしない。
- frontend: page未満の層からpageをimportしない。
- Kindle: controller / capturerからagent transport、backend、routerをimportしない。
- Novel RAG production: `_llm_backend` / `_prompts`互換facadeをimportしない。
- Novel OCR production: `surya_ocr` / `ocr_staging` / `ocr_qa`互換facadeをimportしない。
- frontend production: 撤去済みKindle hook/type、Novel DB SSE集約facadeをimportしない。

設計上の方向は`router → service → utility/config`、
`page → component/hook/feature → apiClient/config/type`、
`agent → controller/capturer`とする。

### 4.3 CIと開発runtimeの再現性

`master`の機能開発は、clean checkoutで全CI jobが成功することを前提とする。
前段の失敗で後段が実行されない場合は、未実行のgateを合格扱いしない。

- Python依存はルート`uv.lock`、frontend依存は`frontend/package-lock.json`を
  再現性の正本とし、通常の初期構築は`uv sync --locked`と`npm ci`を使う。
- frontendの正規runtimeはルート`.node-version`と`frontend/package.json`の
  `packageManager` / `engines`を正本とし、CIも同じNode.js 22 + npm 10を読み込む。
  依存更新時だけこのruntimeでlockfileを再生成し、その後に`npm ci`で
  clean installを再検証する。
- Node.js 22より新しいruntimeでの試験は先行互換診断とし、正規gateの
  代替にしない。新runtime固有のWeb APIとjsdomの競合は製品回帰から分離する。
- 依存監査の例外にはadvisoryの別名を含む識別子、利用経路、露出範囲、
  解消期限を記録する。同一脆弱性の別IDは未記録の新規検出と区別する。
- OS固有のテストは対応runnerを明示する。非対応OSでcollectionできない
  moduleを無条件に除外せず、OS非依存ロジックと実機境界の合格条件を分ける。
- backendの`basedpyright`はAlembic migrationも検査対象とする。autogenerateが
  型stubに無いpackage属性経由の型を出力した場合は、同一の具体型を
  定義moduleから直接importし、migration directory全体を除外しない。
- DBの`lastrowid`などruntime上必須の値はcastだけで隠さず、`None`を
  検出した場合に中断する。TypedDictの既定値も宣言型のconstructorで構築する。

## 5. 例外管理

ガードレールの例外には次を記録する。

```yaml
path: path/to/file
rule: size-over-800
reason: 分割しない具体的理由
owner: 対象機能名
baseline: 917
expires: 2026-10-31
recheck_when: 次の機能追加または50行超の増加時
```

- `reason`、`expires`、`recheck_when`のない例外は禁止する。
- 行単位の無期限`noqa`やディレクトリ全体の除外は使用しない。
- 期限到来時は「分割」「基準線更新」「例外継続」を再判断する。

## 6. 定期監査

月次入口は次のコマンドに統一する。

```bash
uv run python scripts/maintenance/monthly_health_audit.py
```

この監査はdocs、ファイルマップ、production code規模、C901、OpenAPI契約、
import方向、互換・移行・script期限、frontend未使用依存、完了計画の残存を確認する。

- 全項目成功時は結果ファイルや変更履歴を増やさない。
- 単発の候補はその場で起票しない。
- 同じ未解決候補が2回連続した場合だけ計画へ昇格する。
- ユーザー挙動を変えない内部構造はリファクタリング候補、
  依存・インフラ・性能は技術メンテナンス候補へ振り分ける。
- baselineを安易に更新せず、意図した変更か回帰かを確認する。

実行手順と運用上の復旧方法は[運用ガイド](../環境構築/運用ガイド.md)を参照する。
