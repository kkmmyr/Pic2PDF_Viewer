# Codex サブエージェント運用

> status: living | last-verified: 2026-08-01

## 1. 目的

Pic2PDF_Viewer の Codex 作業では、メインエージェントを要件・設計・統合・最終判断へ
集中させ、独立した調査、監査、限定実装をサブエージェントへ委任する。

モデルは単純なコスト差ではなく、失敗時の影響、機械検証の有無、必要な意味判断に
応じて Luna / Terra / Sol を使い分ける。サブエージェントの出力は、担当範囲を越える
変更や公開判断の根拠として単独利用しない。

## 2. 設定の正本

| 設定 | 配置 | 用途 |
|---|---|---|
| プロジェクト共通設定 | `.codex/config.toml` | 同時実行数など、全サブエージェント共通の制約 |
| カスタムエージェント | `.codex/agents/*.toml` | モデル、reasoning、sandbox、担当範囲、禁止事項 |
| 委任ルール | `AGENTS.md` | いつ、何を、どのモデルへ委任するか |
| 設計判断・品質基準 | 本書 | 役割境界、昇格条件、検証・ロールバック |

`~/.codex/` は複数リポジトリに共通する個人設定だけに使い、本プロジェクト固有の
役割はリポジトリ内の `.codex/` で版管理する。

## 3. モデル別の責務

| モデル | 主な役割 | 許可する作業 | 単独で行わない作業 |
|---|---|---|---|
| Luna | 高頻度・定型・読み取り中心の前処理 | コマンド結果の分類、ログ要約、関連ファイル抽出、機械検証可能な監査、構造化草稿 | ソース修正、再試行、DB更新、公開、commit、push、deploy、意味的な最終判断 |
| Terra | 範囲が明確な日常的実装・レビュー | 所有ファイルを限定した小規模実装、テスト追加、設計書と実装の整合性調査、ブラウザー再現 | 要件変更、アーキテクチャ決定、破壊的操作、複数領域の統合判断、最終公開 |
| Sol | 設計・統合・高リスク判断 | 要件確定、設計判断、曖昧な不具合診断、横断レビュー、最終検証、状態変更の採否 | 委任可能な大量ログを理由なくメイン context へ直接取り込むこと |

Terra と Luna は Sol の代替ではなく、Sol へ渡す情報量と反復作業を減らすための
委任先である。メインエージェントはサブエージェントの結果を統合し、ユーザーへの
報告と最終成果物に責任を持つ。

## 4. Luna 完結条件

Luna に作業単位を完結させてよいのは、次をすべて満たす場合に限る。

1. 読み取り専用、または破棄可能な一時成果物だけを扱う。
2. 入出力と対象範囲が明確で、構造化された結果を返せる。
3. exit code、schema、件数、hash、lint、テストなど客観的な判定器がある。
4. 誤判定しても DB、公開データ、外部サービス、Git 履歴を変更しない。
5. 要件解釈、事実認定、複数資料の意味的統合を必要としない。
6. タイムアウト、形式不正、矛盾、判定不能時に fail closed で親へ返せる。

初期運用では Luna を `read-only` に固定する。Luna のレポートが `PASS` でも、元の
検査コマンドが失敗している場合は必ず失敗として扱う。

## 5. Terra 委任条件

Terra へ書き込みを委任する場合は、親が開始前に次を明示する。

- 所有するファイルまたはモジュール。
- 期待する挙動と変更禁止範囲。
- 実行すべきテスト、lint、型検査、ブラウザー確認。
- 完了時に返す差分要約と残存リスク。

仕様が曖昧、複数の正解がある、設計書の変更理由を新たに判断する、または変更が
複数領域へ波及した場合、Terra は実装を継続せず Sol へ返す。初期運用では Terra の
変更を Sol が差分確認してから確定する。

## 6. Sol への必須昇格条件

次のいずれかに該当した時点で Sol へ昇格する。

- 要件、受入条件、API、データ構造、アーキテクチャの判断が必要。
- Kindle 書籍照合、撮影、再試行、OCR 公開、ASIN 確定を伴う。
- DB 移行、バックアップ復元、外部通信、commit、push、deploy を伴う。
- 要約、人物辞典、シリーズ横断分析など、根拠の意味的な統合が必要。
- セキュリティ、権限、個人情報、破壊的操作に関係する。
- 自動検査がなく、画面・原画像・実データを人間相当の判断で確認する必要がある。
- Luna / Terra の出力が矛盾、欠落、形式不正、タイムアウトとなった。

## 7. プロジェクトのエージェント構成

| エージェント | モデル | sandbox | 用途 |
|---|---|---|---|
| `luna-triage` | `gpt-5.6-luna` / medium | read-only | 監査、ログ分類、影響範囲・候補抽出 |
| `terra-focused-worker` | `gpt-5.6-terra` / high | workspace-write | 所有範囲を限定した小規模実装とテスト |
| `docs-cross-checker` | `gpt-5.6-terra` / high | read-only | 設計書と実装の横断整合性確認 |
| `refactor-planner` | `gpt-5.6` / high | read-only | 大規模リファクタの影響分析・段階計画 |

`default_subagent_model` は設定しない。役割ごとにモデルを固定し、レビューや設計調査が
意図せず Luna へ送られることを防ぐ。同時実行数は初期値 3 とし、同じファイルを複数の
書き込みエージェントへ割り当てない。

## 8. 標準フロー

1. メインエージェントが作業を独立単位へ分割する。
2. 各担当について読み取り専用か書き込みか、対象、所有者、検証方法を宣言する。
3. Luna は根拠収集と定型監査、Terra は限定実装、Sol は設計・統合を担当する。
4. サブエージェントは生ログではなく、結論、根拠、未確認事項、実行コマンドを返す。
5. メインエージェントが差分と検証結果を確認し、必要なら Sol で再確認する。
6. commit、push、deploy、公開データ変更はユーザーの依頼範囲を確認してメインが行う。

## 9. 権限と安全性

カスタムエージェントの `sandbox_mode` は安全な既定値であり、単独の強制境界とは
みなさない。サブエージェントは親ターンの権限・ツール・実行時オーバーライドの影響を
受けるため、親の指示、`AGENTS.md`、ファイル所有権、機械検査を併用する。

状態変更を必要とする作業を読み取り専用エージェントへ渡して失敗した場合、権限を広げて
再実行せず、担当を Terra または Sol へ切り替える。

## 10. 段階導入と評価

初期導入は次の順序とする。

1. Luna で docs、コードサイズ、複雑度、OpenAPI、import 境界などの監査結果を要約する。
2. Luna で Kindle / OCR ジョブの読み取り専用状態報告を作る。
3. Terra で純粋関数のテスト追加や単一モジュールの小規模修正を行う。
4. 問題がなければ対象を増やすが、要件・公開・状態変更は Sol に維持する。

評価では、無許可書き込み 0 件、検査失敗の偽 `PASS` 0 件、担当範囲外変更 0 件を必須と
する。重大な見逃しまたは無許可変更が 1 件でも発生した役割は自動委任を停止し、全件 Sol
確認へ戻す。

エージェント定義の追加・変更後は、新しい Codex タスクまたはアプリ再起動で設定を
再読込し、利用可能な agent 一覧とモデル設定を確認する。
