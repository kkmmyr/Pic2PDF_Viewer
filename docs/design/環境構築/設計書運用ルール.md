# 設計書運用ルール

> status: living | last-verified: 2026-09-05

本書は、設計書を「現在の正しい情報」として維持するための運用契約である。
文書の内容をどこへ置くか、いつ更新・移動するか、何を機械検査するかを定義する。

<!-- contract-owner: docs-governance -->

## 1. 読み手が最初に見る場所

1. 現行仕様を知りたい: `docs/design/`
2. 次に行う作業を知りたい: `docs/log/計画/バックログ.md` または
   `docs/log/計画/リファクタリング計画書.md`
3. 現在発生している障害を知りたい: `docs/log/既知の問題.md`
4. 実測値・運用上の注意を知りたい: `docs/log/技術知見/`
5. 過去の判断・完了記録を調べたい: `docs/archive/`

入口と横断契約の所有文書は [docs/index.md](../../index.md) の正本マップを使う。

## 2. 3バケットの責務

| バケット | 記載する内容 | 記載しない内容 |
|---|---|---|
| `design/` | 現在の要件、設計、運用契約、採用済みADR | 実験日誌、完了報告、未承認の将来案 |
| `log/` | 未完了計画、現行の既知問題、再利用する技術知見、直近変更履歴 | 完了済み計画、停止した比較計画 |
| `archive/` | 完了・中止・置換済みの計画、検証履歴、旧仕様 | 現在の契約や未完了作業 |

`archive/` は凍結記録である。誤字以外は原則編集せず、現在の判断はliving文書側へ記載する。

## 3. 文書状態

### design

ADR以外の`design/`文書は冒頭10行以内に次を置く。

```text
> status: living | last-verified: YYYY-MM-DD
```

- `living`: 現在の正本。実装または承認済み契約と一致している。
- `absorption-pending`: 別の正本へ統合してからarchiveへ移す一時状態。新規仕様の保管場所にはしない。

### log/計画

計画書は冒頭10行以内に次を置く。

```text
> status: active | last-verified: YYYY-MM-DD | owner: <担当または判断者>
```

- 許可状態は`active`または`blocked`だけとする。
- 完了、採用見送り、中止になった計画は同じ変更で`archive/`へ移す。
- バックログは優先度・現在地・残作業・完了条件だけを持つ。詳細な実測表や完了工程は
  技術知見、変更履歴、archiveへ置き、リンクで参照する。

## 4. 正本と重複禁止

- 横断的な事実には所有文書を1つだけ決め、[正本マップ](../../index.md#canonical-map)へ登録する。
- API一覧は`/openapi.json`、DB schemaはmigrationと実装、機械判定値はJSON policyを最上位契約とする。
- 別文書では同じ表や設定値を複写せず、所有文書の節へリンクする。
- 要件定義は利用者から見た挙動、基本設計は境界、詳細設計は責務と失敗時挙動を記載する。
- 「Phase Nで実装した」「YYYY-MM-DDに合格した」は現在仕様ではなく履歴へ置く。

### 入口・設計階層・モジュール文書の分担

| 文書 | 所有する説明 |
|---|---|
| ルートREADME | アプリの概要、初回セットアップ、設計書への入口 |
| 起動方法 | 開発・Linux本番・Windowsローカルリリースの選択と手順への案内 |
| docs/index.md | 目的別の入口、横断契約の正本マップ |
| 要件定義 / 基本設計 | 利用者から見た要件 / システム境界と連携 |
| 共通・バックエンド・フロントエンド詳細設計 | 共通規約と各層の責務。機能固有契約は機能別設計へリンク |
| 機能別設計 | 状態遷移、失敗時挙動、保存・公開の境界 |
| 自動生成ファイルマップ | 実ファイルの一覧。手書きの設計書へ複製しない |
| kindle-pdf/docs/、common/llm/docs/ | モジュール内部の実装。docs/design/の横断契約を再定義しない |

正本が競合した場合は、機械可読契約（OpenAPI・migration・schema実装・JSON policy）、
`design/`の所有文書、未完了計画、技術知見、凍結記録の順に照合する。
下位文書を根拠に上位の契約を上書きしない。差異がある場合は実装と所有文書を確認する。

サイドバーは読み手の目的で階層化し、物理ディレクトリは3バケットを維持する。
移動は責務・ライフサイクルが変わる場合に絞り、分類の見せ方だけならnavを変更する。
本文を分割するときは旧入口から新しい正本へリンクし、利用されているアンカーも維持する。
archiveは索引から全記録へ辿れるようにし、既存の凍結本文やURLは配置整理のために書き換えない。

## 5. サイズと分割基準

| 種類 | 上限 | 超える前に行うこと |
|---|---:|---|
| `design/`（ADR以外） | 700行 | 機能責務で分割し、設計過程をarchiveへ移す |
| ADR | 250行 | 決定・理由・影響だけ残し、検証データをarchiveへ移す |
| `log/技術知見/` | 1,000行 | 現行推奨値と時系列の検証履歴を分離する |
| `log/変更履歴.md` | 800行 | 前週分を週次ファイルへローテーションする |

上限未満でも、現在の答えに到達するまで複数の古い結論を読む必要がある場合は分割する。

## 6. 変更手順

設計・挙動・API・データ構造に影響する変更は、次の順序で行う。

1. 正本を特定し、設計書を現在形で更新する。
2. `docs/log/変更履歴.md`の直近週先頭へ変更理由と影響を追記する。
3. 実装・テストを変更する。
4. `check_docs.py`、関連テスト、必要に応じてMkDocs strict buildを実行する。
5. 完了した計画をarchiveへ移し、バックログには未完了事項だけ残す。

複数文書を変更するときは、正本→参照側の順で修正する。実装との相違を発見した場合は、
実装を無条件に正とせず、ADR・機械可読契約・現行運用を照合して判断する。

## 7. 検証コマンド

```bash
uv run python scripts/maintenance/check_docs.py
uv run pytest scripts/maintenance/tests/test_check_docs.py -q
uvx --with mkdocs-material --with mkdocs-mermaid2-plugin mkdocs build --strict
```

`check-docs`はリンク・nav・状態・正本owner・サイズ・計画ライフサイクルをblocking検査する。
MkDocsはHTML生成とアンカー等の表示面を独立検査する。

## 8. レビュー時の確認事項

- 現在仕様と将来案が同じ現在形で書かれていないか。
- 完了済み工程や日次実測がliving設計書へ増え続けていないか。
- バックログと詳細計画の両方に同じ進捗を複写していないか。
- 既知の問題に、撤去済み機能やすでに解消した障害が残っていないか。
- 新しい横断契約にownerが決まっているか。
- 文書移動後にliving文書のリンクと`mkdocs.yml`が追従しているか。

## 9. HTMLビルドとプレビュー


```powershell
# 単発ビルド（→ frontend/public/site/ に出力）
uvx --with mkdocs-material --with mkdocs-mermaid2-plugin mkdocs build --clean

# 開発時プレビュー（→ http://localhost:8000）
uvx --with mkdocs-material --with mkdocs-mermaid2-plugin mkdocs serve
```

出力先は`frontend/public/site/`（Git管理外）。配備スクリプト自体はMkDocsを生成しないため、
設計書変更時はフロントエンドのビルド・配備より先に上記の単発ビルドを行う。
閲覧URLとアプリの静的配信構成は[共通設計](../詳細設計/詳細設計書_共通.md#docs-delivery)を参照する。

ルートREADME、起動方法、`kindle-pdf/docs/`、`common/llm/docs/`、開発ガイドの参照も移管時に確認する。
`check_docs.py`の検査外にあるモジュール文書や見出しアンカーは、実ファイルと生成HTMLで別途照合する。
