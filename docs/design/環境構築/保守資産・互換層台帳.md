> status: living | last-verified: 2026-09-05

互換facade、一回性移行、運用scriptの正本は
`scripts/maintenance/maintenance_assets.json` とする。本書は判断基準と現時点の
監査結果を説明し、`check_maintenance_assets.py` が期限・所有者・対象漏れを検査する。

## 1. 判定規則

互換facadeは次の3状態で管理する。

| 状態 | 意味 |
|---|---|
| `maintain` | 現行production/CLIから到達可能で、公開境界として維持する |
| `timeboxed` | workspace内部のproduction参照はないが、外部利用または移行猶予のため期限付きで残す |
| `removed` | 利用0件を機械確認し、Git履歴をrollback手段として撤去済み |

`timeboxed`にはowner、再評価日、撤去条件、rollbackを必須とする。再評価日を過ぎた
entryは月次監査を失敗させ、無期限延命を許さない。`removed`のpathが復活した場合も
失敗とする。

## 2. 互換facade・legacy移行の再評価

個々の状態・owner・期限・撤去条件は `maintenance_assets.json` が正本。
過去のローカル残存件数は[追加実測履歴](../../archive/検証/環境構築_追加実測履歴_2026-09-05.md)へ分離し、現在の全環境の残存数と混同しない。

撤去は全実行環境・対象ブラウザの残存確認後に行う。移行失敗時は原本を削除せず、Kindle/Hitomiは旧DB・JSONを読み取り専用原本として再実行し、LibraryはlocalStorage keyを残して再読込する。
撤去変更では対象残存数、最終利用日、復旧手順を更新してからコードを削除する。

## 4. script分類

`scripts/`配下の追跡対象は、inventoryのglobで必ず1分類だけに所属する。

| 分類 | 対象 | 運用 |
|---|---|---|
| `continuous` | release/deploy/service、Kindle series、品質check、OCR benchmark本体・比較器 | 月次監査とsize/C901 ratchetの対象 |
| `temporary` | NDL OCR/Parseqの学習pilot・checkpoint復旧・変換、Sol画像OCR、不採用済みOrnithのtuning・holdout・再現用CLI | ownerと2026-11-16再評価日を持つ。成果採用または中止時にarchive/撤去を判断 |
| `frozen` | 現在なし | 新設時は実行禁止理由と復旧参照先を必須にする |

`backend/scripts/`は現行の管理・構築・診断CLI、`common/llm`はpackage/CLI/MCPとして
継続運用する。単体実行時はPythonがscript directoryを`sys.path[0]`へ設定するため、
`ask.py`と`mcp_server.py`自身による同一directoryの再挿入は行わない。workspace内利用は
`qwen-common`依存、外部projectはeditable package依存を正規経路とする。MCP serverの
runtime依存`mcp`も`common/llm/pyproject.toml`で宣言し、import smokeを依存検証に含める。

B-35のformal holdout manifest・一度限り開封ledger・seal CLIは、将来の
OCR候補にも同じfail-closed契約を適用するため`continuous`とする。公開縦書きdatasetを使う
`ocr_benchmark_vertical_screen.py`も、候補変更後に再利用する入力完全性・再現性判定器なので
`continuous`に含める。PaddleOCR-VL、Sarashina2.2-OCR、Unlimited-OCR、Qianfan-OCRの予測CLIは、
不採用候補の固定revision・prompt・入力SHA・checkpointを再現する`temporary`資産とし、
2026-11-16に実行価値を再確認してarchiveまたは撤去する。
Qwen/dots複合OCRで使用する両予測CLI、checkpoint・provenance helper、selectorは `ocr-production-composite-runners` として `continuous` に分類する。
Ornith MLX Gate A〜B4の評価器と専用testは本番不採用の再現資産であり、
`temporary`として2026-11-16にarchiveまたは撤去を判断する。

継続運用scriptと`common/llm`はcode-size/C901 ratchetへ含める。導入時点で閾値を
超えるentryは`maintenance_assets.json`の`ratchet_exceptions`にowner、理由、
2026-11-16再評価日を持たせ、baseline数値だけで無期限固定しない。

OpenAPIはschema baseline、Novel SSEはbackend event順とfrontend frame/parser、OCR workerは
subprocess JSON protocol、Kindle captureはmanifest version/必須field/rollbackを既存testで
比較する。CIはbackendだけでなく`kindle-pdf/tests`と`common/llm/tests`も実行し、frontendは
Vitest・型・Knip・production buildを品質ゲートとする。

## 5. 生成物

`common/llm/qwen_common.egg-info/`はbuild/installで再生成できる成果物であり、sourceではない。
Git追跡から外して`*.egg-info/`をignoreする。必要時は`uv sync`またはpackage buildで再生成する。

## 6. テスト所有

500行を超えたテストは単純な件数分割ではなくproduction責務で分ける。

| 元テスト | 分離する所有責務 |
|---|---|
| Kindle app controller | 書籍照合・window/search と、位置移動・layout/download |
| OCR staging | stage/publication と、QA risk/review |
| Novel discussion | prompt/parser/stream と、repository/router |
| common LLM | config/sync transport と、async transport/factory |
| meta | view/meta更新 と、read-state遷移 |
| Novel summarizer | generation orchestration と、summary repository/index |
| Kindle capture jobs | lifecycle/claim と、publish rollback/compensation |

fixtureやtest doubleを共有する場合は、production APIを再実装せず入力構築だけをhelper化する。
分割前後でpytest収集件数を比較し、テスト消失を許さない。

## 7. 検証

```powershell
uv run python scripts/maintenance/check_maintenance_assets.py
uv run python scripts/maintenance/check_import_boundaries.py
uv run python scripts/maintenance/check_code_size.py
uv run python scripts/maintenance/check_c901_ratchet.py
uv run python common/llm/ask.py --help
uv run --project common/llm --directory common/llm python -c "import mcp_server; print('MCP import: ok')"
```

MCPは通常stdio待機するため、自動検証ではmodule importと登録済みtool/resourceの構築までを
確認し、実サーバー起動は行わない。
