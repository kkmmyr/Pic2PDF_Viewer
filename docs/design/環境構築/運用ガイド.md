## 1. アプリケーション起動・停止

### 起動

```bash
# バックエンド（ポート 8766）
cd backend
uv run uvicorn main:app --reload --port 8766

# フロントエンド（ポート 5176）
cd frontend
npm run dev
```

`--reload` は開発時のみ有効（ファイル変更を自動反映）。本番相当で動かす場合は外す。

### `scripts/start.bat` による一括起動（Windows 開発）

`scripts/start.bat` は Windows Terminal (`wt`) を使い、Backend と Frontend を別タブに自動起動する。Backend が既に LISTENING 中なら再起動のみ実行。

**前提**: Windows Terminal がインストールされていること（Win11 標準・Win10 は要インストール）。`wt` が無い環境では上記コマンドを手動で起動する。

### Windows ローカルリリース（統合配信ポート 8090）

```
scripts\build_release.bat   :: フロントを frontend/dist/ にビルド
scripts\setup_service.bat   :: 初回のみ NSSM サービスを登録
scripts\restart_service.bat :: ビルド後に Pic2PDFViewer サービスを再起動
scripts\open_viewer.bat     :: ブラウザで localhost:8090 を開く
```

Windows ローカルリリースは NSSM サービスが自動起動・クラッシュ時再起動を担う。
旧タスクスケジューラによる起動は二重起動防止のため無効化する。

### Linux 本番（通常運用）

- 公開入口: `http://medaroserver:8090`（nginx）
- アプリ: systemd の `pic2pdf-viewer` が uvicorn を
  `127.0.0.1:8091` で実行
- デプロイ: リポジトリルートから
  `bash scripts/deploy_to_linux.sh`
- docs を変更した場合は、デプロイ前に
  `uv run mkdocs build --clean`

デプロイスクリプトはfrontend build、workspace code / lock転送、writer停止確認、DBの世代backupと
復元試験、新backend世代専用venvのlock同期、import smoke、backend / common symlink切替、サービス再起動までを行う。
active source / venvを直接更新せず、service / HTTP probe不合格時はsourceとvenvを一体で直前世代へ
rollbackする。MkDocsの生成は行わない。

Macから作る転送archiveはACL・extended attribute・AppleDouble metadataを含めず、明示的な
`._*` / `.DS_Store`も除外する。Linux側はbackend / common / staging workspaceに`._*`が1件でも
あれば、writer停止、pre-deploy backup、venv構築、migration、active symlink切替より前に
fail closedとする。これによりFinder metadataをAlembic migration等のアプリファイルとして
誤認しない。

LanceDBの既定pathは`NOVEL_DB_DIR`の親にある`novel.lancedb`とし、version付きbackend世代の外へ
固定する。activation smokeは解決後pathが新backend世代配下なら切替を拒否する。lexical backendが
`shadow` / `lance_icu`の場合は、SQLiteのactive pointerに対応するICU tableを実際に開いて
no-match検索まで通す。SQLiteだけを継承してLance実体を失う世代はactive化しない。

デプロイ完了後は、スクリプトの終了コードだけでなく次の4点を確認する。

1. `http://medaroserver:8090/` と `/site/index.html` が HTTP 200
2. 変更した設計書の固有語句が本番HTMLに存在
3. 実在する軽量API（例: `/api/pdfs?source=doujin`）が HTTP 200
4. `pic2pdf-viewer` が `active` で、再起動後の error ログがない

`/api/health` は本アプリでは定義していないため、死活監視には使用しない。
設計書だけの変更でも配信物は `frontend/dist/site/` に含まれるので、
通常のデプロイスクリプトを最後まで実行する。

Windows と Linux の時計に数秒から数十秒の差があると、tar 転送時に
`time stamp ... is ... in the future` と表示されることがある。終了コード0、
HTTP応答、配信内容、サービス状態がすべて正常なら転送失敗ではない。
警告が大きい、または繰り返し増える場合は両端末の時刻同期を確認する。

`AppleDouble metadata is not allowed`で停止した場合、active backend / common symlinkは
旧世代のままであることと`pic2pdf-viewer=active`を確認する。失敗世代はactive linkの参照先で
ないことを正確な絶対pathで確認してから削除し、修正版のデプロイスクリプトで新しい世代を作る。
汚染した世代は再利用しない。

### 停止

各ターミナルで `Ctrl+C`。

## 2. データディレクトリ構成と保管場所

### `.env` による配置変更

プロジェクトルートの `.env` で各データディレクトリを設定する。

| 環境変数 | 対象 | 推奨場所 | 理由 |
|---|---|---|---|
| `PIC2PDF_DATA_DIR` | doujin / comic / kindle_novel / hitomi | OneDrive 等の共有場所 | 画像・PDF は複数端末で共有したい |
| `META_DB_DIR` | `meta2.db`（閲覧回数・ジャンル・シリーズ） | **ローカル固定** | 頻繁な書き込み + WAL モードで同期競合リスクあり |
| `NOVEL_DB_DIR` | `novel.db`（小説 RAG SQLite） | **ローカル固定** | OneDrive 同期競合で WAL 破損リスクあり |
| `NOVEL_DB_LANCE_PATH` | `novel.lancedb/`（LanceDB） | **ローカル固定** | 多数の Arrow ファイルへの同時書き込みが同期競合で破損するリスクあり |

`.env` 設定例:
```
PIC2PDF_DATA_DIR=C:\Users\<user>\OneDrive\61.tool\Pic2PDF
META_DB_DIR=D:\61.tool\Pic2PDF_Viewer\backend\data
NOVEL_DB_DIR=D:\61.tool\Pic2PDF_Viewer\backend\data\novel_db
NOVEL_DB_LANCE_PATH=C:\Users\<user>\AppData\Local\Pic2PDF\novel.lancedb
```

> `.env` は `.gitignore` 対象。git には保存されない。初回セットアップ時に手動で作成する。

`NOVEL_DB_LANCE_PATH`を省略した場合は`NOVEL_DB_DIR`の兄弟（例:
`NOVEL_DB_DIR=/opt/pic2pdf-viewer/data/novel_db`なら
`/opt/pic2pdf-viewer/data/novel.lancedb`）を使う。version付きrelease directory内を本番の
永続pathにしない。

### バックアップ対象

| パス | 内容 | 復元困難度 |
|---|---|---|
| `$PIC2PDF_DATA_DIR/doujin/` | 生成済み PDF | 高（再生成に時間がかかる） |
| `$PIC2PDF_DATA_DIR/comic/` | 漫画キャプチャ画像・PDF | 高（再キャプチャが必要） |
| `$PIC2PDF_DATA_DIR/kindle_novel/` | 小説キャプチャ画像 | 高（再キャプチャ + 再 OCR が必要） |
| `$META_DB_DIR/meta2.db` | 書誌メタデータ | 高（手動入力データを含む） |
| `$META_DB_DIR/kindle_catalog.db` | Kindle 購入・借用・取り込み・キャプチャジョブ | 高（再取得困難な整理状態を含む） |
| `$NOVEL_DB_DIR/novel.db` | 小説テキスト・チャンク・RAG メタ | 高（全文 OCR + ビルドが必要） |
| `$NOVEL_DB_LANCE_PATH/` | ベクトルインデックス | 中（`novel.db` から再ビルド可） |

> `PIC2PDF_DATA_DIR` を OneDrive に設定した場合、doujin / comic / kindle_novel は OneDrive が自動同期するため別途バックアップ不要。

### 推奨バックアップ方法（自動化スクリプト・ローカルのみ対象）

`tools/backup_data.ps1` を使うと OneDrive への差分バックアップを自動化できる（`NOVEL_DB_DIR` 等ローカル専用データの別バックアップ先として利用）。

```powershell
# 手動実行（PowerShell）
& "D:\61.tool\Pic2PDF_Viewer\tools\backup_data.ps1"

# ドライラン（コピーせず差分のみ確認）
& "D:\61.tool\Pic2PDF_Viewer\tools\backup_data.ps1" -WhatIf
```

- バックアップ先: `C:\Users\<user>\OneDrive\61.tool\Pic2PDF_Viewer_backup\`
- ログ: `%TEMP%\pic2pdf_backup.log`
- robocopy オプション: `/MIR`（ミラーリング）`/FFT`（OneDrive タイムスタンプ対策）`/Z`（大容量ファイル向け再起動可能モード）

### タスクスケジューラへの登録（週次自動実行）

PowerShell で一発登録:

```powershell
$action  = New-ScheduledTaskAction -Execute "powershell.exe" `
    -Argument "-NonInteractive -File `"D:\61.tool\Pic2PDF_Viewer\tools\backup_data.ps1`""
$trigger = New-ScheduledTaskTrigger -Weekly -DaysOfWeek Sunday -At "03:00"
$settings = New-ScheduledTaskSettingsSet -RunOnlyIfIdle:$false -StartWhenAvailable
Register-ScheduledTask -TaskName "Pic2PDF_Backup" `
    -Action $action -Trigger $trigger -Settings $settings `
    -Description "Pic2PDF_Viewer backend/data を OneDrive へ週次バックアップ" `
    -RunLevel Highest -Force
```

確認: `Get-ScheduledTask -TaskName "Pic2PDF_Backup"`
削除: `Unregister-ScheduledTask -TaskName "Pic2PDF_Backup" -Confirm:$false`

### Linux サーバーのDBバックアップ

`backup-meta.timer` は毎日 02:00 に `backend/tools/server_backup.py` を実行する。WAL 使用中の
SQLite をファイルコピーせず Online Backup API で保存し、保存直後に
`PRAGMA integrity_check` を通す。対象は `meta2.db`、`kindle_catalog.db`、`novel.db`、LanceDB で、未作成の
小説DBはマニフェストへ `not_present` と記録する。

- バックアップ先: `SERVER_BACKUP_DIR`（既定は `$PIC2PDF_DATA_DIR` の親の `backups/`）
- 保持期間: `SERVER_BACKUP_RETENTION_DAYS`（既定14日）
- 復元試験先: `SERVER_RESTORE_TEST_DIR`（既定は同じ親の `restore-tests/`）
- 1世代は `YYYY-MM-DD_HHMMSS/` 配下にDB・LanceDB・`manifest.json` をまとめる
- LanceDB はディレクトリコピー後に全テーブルを開いて行数を検査する。不整合時は世代を公開せず失敗する

週次の `backup-restore-test.timer` は最新世代を別ディレクトリへコピーし、SQLiteの
整合性とLanceDBの全テーブルを再検査する。成功結果は
`$SERVER_RESTORE_TEST_DIR/last-success.json` にatomic writeする。

#### medaroserver 導入実績（2026-07-18）

- `backup-meta.timer`: system-wide unitとして`enabled / active`、毎日 02:00 実行
- `backup-restore-test.timer`: system-wide unitとして`enabled / active`、毎週日曜 03:00 実行
- 初回世代`2026-07-18_221951_pre-deploy`を作成し、`meta2.db` / `novel.db`の
  `integrity_check=ok`とLanceDBテーブルの読み取りを確認
- 同じ世代を`restore-tests/`へ復元し、`backup-restore-test.service`が終了コード0で成功
- 検証結果の正本は`/opt/pic2pdf-viewer/restore-tests/last-success.json`
- 配布スクリプトは`590c952`以降、バックアップ実行前に`backend/`へ移動して
  `tools.server_backup`を解決する

```bash
# 初回導入・unit更新時
sudo cp /opt/pic2pdf-viewer/deploy/backup-meta.service \
  /opt/pic2pdf-viewer/deploy/backup-meta.timer \
  /opt/pic2pdf-viewer/deploy/backup-restore-test.service \
  /opt/pic2pdf-viewer/deploy/backup-restore-test.timer \
  /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now backup-meta.timer backup-restore-test.timer

# 手動バックアップ（デプロイ前ラベルの例）
sudo -u amashio /opt/pic2pdf-viewer/backend/.venv/bin/python \
  -m tools.server_backup backup --label manual

# 最新世代の復元試験
sudo -u amashio /opt/pic2pdf-viewer/backend/.venv/bin/python \
  -m tools.server_backup verify-latest

# timer確認
systemctl status backup-meta.timer backup-restore-test.timer
systemctl list-timers --all backup-meta.timer backup-restore-test.timer

# 直近の復元試験結果
systemctl show backup-restore-test.service \
  -p Result -p ExecMainStatus -p ExecMainStartTimestamp -p ExecMainExitTimestamp
cat /opt/pic2pdf-viewer/restore-tests/last-success.json
```

## 3. 定期メンテナンス

### OCR補正後のページ単位索引再構築

原画像との照合後に公開済み`pages`の1画面だけを補正した場合は、書籍全体を再embeddingせず
対象画面だけを再構築できる。`PAGE_NO`はKindleの紙面ページ番号ではなく、
`pages.page_no`と画像ファイル連番に対応するキャプチャ画面番号を指定する。

```bash
cd backend
uv run python scripts/build_novel_db.py \
  --book "<書籍名>" \
  --page <PAGE_NO>
```

前提と確認事項:

1. このコマンドは`pages.full_text`を修正しない。OCR runの承認または画像照合補正を
   先に完了し、公開`pages`が正しいことを確認する。
2. 正常終了時は対象ページのSQLite `chunks`とLanceDB `chunks`のchunk ID集合が一致し、
   `books.indexed_at`が非NULLであることを確認する。他ページのchunk IDは変更しない。
3. embedding計算は対象ページだけだが、古いFTS語を除くため`pages_fts`は全体同期する。
4. 変更前からSQLiteとLanceDBが不一致の場合は、ページ単位処理が変更せずエラー終了するため、
   `indexed_at`の値にかかわらず次の書籍単位再構築を実行する。クロスストア更新開始後の
   失敗では`indexed_at=NULL`が残るため、これを不完全状態として同じ復旧手順へ進む。

```bash
cd backend
uv run python scripts/build_novel_db.py --book "<書籍名>"
```

2026-07-28の本番検証では、茉莉花官吏伝4・5・9・11・12・13巻の補正済み6画面を
ページ単位で再構築し、全件で他ページのchunk件数・ID合計を維持した。対象ページの
SQLite–LanceDB chunk ID集合も一致し、最新承認runだけの再監査は採用本文反復0画面、
未採用primary候補20画面だった。

### 生成済み要約・人物辞典の再生成監査

再生成の前後で公開内容を比較できるよう、書籍単位の監査CLIを使用する。出力先には
Git管理外の作業ディレクトリを指定する。

```bash
cd backend

# 1. 現在の公開版を退避
uv run python scripts/audit_generated_content.py snapshot \
  --book "<書籍名>" \
  --output "data/novel_db/audits/<識別子>-before.json"

# 2. 通常の再生成を実行した後、差分をJSONとMarkdownへ保存
uv run python scripts/audit_generated_content.py diff \
  --before "data/novel_db/audits/<識別子>-before.json" \
  --json-output "data/novel_db/audits/<識別子>-diff.json" \
  --markdown-output "data/novel_db/audits/<識別子>-diff.md"

# 3. QA不合格時だけ旧版へ復元（書名の完全一致を二重確認）
uv run python scripts/audit_generated_content.py restore \
  --snapshot "data/novel_db/audits/<識別子>-before.json" \
  --confirm-book "<書籍名>"
```

- snapshotは書名、要約、人物名、人物説明、初出ページ、登場ページ数、各生成日時を保持する。
- diffは追加・削除・変更人物、文字数、類似度、機械品質ゲート違反、変更前後の全文を保持する。
- 機械品質ゲート合格は公開承認ではない。変更された要約と人物説明はCodex補助QAで、
  読みやすさ、本文根拠、因果・時系列、人物関係、旧版からの情報欠落を確認する。
- restoreはSQLiteを一括復元した後、LanceDBのサマリembeddingを更新する。
  embedding更新失敗時は非ゼロ終了するため、復旧後に再indexする。

## 4. SearXNG レート制限への対処

サークル名自動登録を大量実行（目安: 20 件以上）すると、SearXNG の上流検索エンジンが
レート制限・CAPTCHA ブロックを受け、全件「作者不明」が返るようになる。

### 症状確認

```bash
curl "http://localhost:8080/search?q=test&format=json" | jq .unresponsive_engines
```

`"一時停止"` や `"CAPTCHA"` のエントリがあれば制限中。

### 対処

| 対処 | 詳細 |
|---|---|
| **待機（推奨）** | 数時間〜1 日で自動解除。解除後に「作者不明」エントリは自動再試行される（`overwrite=false` 設定） |
| **待機時間延長** | `backend/routers/meta.py` の `time.sleep(5.0)` を 10〜30 秒に延長 |
| **分割実行** | 一度に全件実行せず、20〜30 件ずつ日を分けて実行 |

> 将来の改善案: 汎用検索エンジンの代わりに DLsite を直接クエリする方式への移行（精度・安定性が向上する見込み）。

## 5. よくあるトラブルシューティング

### バックエンドが起動しない

| 症状 | 原因 | 対処 |
|---|---|---|
| `Address already in use` | 旧プロセスが残っている | `netstat -ano \| findstr :8766` でPID確認後 `taskkill /PID <pid> /F` |
| `ModuleNotFoundError` | venv 未構築または壊れている | `cd backend && uv sync --group dev` |
| `VIRTUAL_ENV` 警告 | 別の Python 環境が有効 | 無視してよい（uv が `.venv/` を優先使用） |

### フロントエンドが起動しない

| 症状 | 原因 | 対処 |
|---|---|---|
| `EADDRINUSE` (port 5176) | 旧プロセスが残っている（`strictPort: true` のため別ポートに自動回避しない） | タスクマネージャーで node.exe を終了 |
| `Cannot find module` | `node_modules` が壊れている | `cd frontend && rm -rf node_modules && npm install` |

### PDF 生成が完了しない

1. ブラウザの「生成中」表示を確認（バックグラウンドジョブは完了まで続く）
2. バックエンドのターミナルログでエラーを確認
3. `backend/data/<source>/` に画像ファイルが存在するか確認

### Discord 通知が届かない（Remote Control 連携）

詳細は [`RemoteControl_Discord通知設定.md`](RemoteControl_Discord通知設定.md) を参照。
`echo $DISCORD_WEBHOOK_URL` で Webhook URL が設定されているか確認する。

### 過去のサーバーログを確認したい

バックエンドログは [backend/utils/logger.py](../../../backend/utils/logger.py) で `RotatingFileHandler` を root logger に登録しており、`backend/data/logs/app.log` に**ファイル永続化される**（[ADR-0006](../基本設計/ADR/0006_backend-log-file-persistence.md)）。

| 項目 | 値 |
|---|---|
| 出力先 | `backend/data/logs/app.log` |
| ローテーション | 10MB × 5 世代（`app.log.1`〜`app.log.5`、最大合計 50MB） |
| エンコーディング | UTF-8 |
| 保持期間 | 出力ペース次第（INFO 中心の通常運用で数日〜数週間分） |

**確認方法**:
- 直近: `app.log` を開く（VSCode / メモ帳など）
- 過去: `app.log.1` 〜 `app.log.5`（数字が大きいほど古い）
- セキュリティ監査ログだけ抽出: `Select-String -Path backend/data/logs/app.log* -Pattern '^.*Security:'`
- 長期保存が必要なら手動で別ディレクトリにコピー（自動アーカイブはしない）

`GET /api/ocr/status` は `rebuild_jobs` の実行状態・現在工程・直近エラーを
フロント互換形式へ変換して返す。詳細な実行履歴は `rebuild_jobs` /
`ocr_runs` / `ocr_page_results` と `app.log` で確認する。

## 6. パフォーマンス指標と容量見積もり

個人 LAN ツールとして「ここまでなら無理なく動く」「これを超えたら検証が必要」のラインを示す。
**実害ベースで設定された hardcode 値**と**運用の経験則による推奨値**を区別して記載。

### 6.1 ハードコードされた上限（コード内固定）

| 指標 | 値 | 場所 | 意味 |
|---|---|---|---|
| 並行ジョブ保持数 | **20** | [backend/config/__init__.py](../../../backend/config/__init__.py) `JOB_MAX_JOBS` | `JobStore` が保持する PDF 生成ジョブの最大数。超過時は最古から自動削除 |
| 閲覧カウント連打抑制 | **300 秒（5 分）** | [backend/routers/meta/core.py](../../../backend/routers/meta/core.py) `VIEW_COUNT_DEBOUNCE_SEC` | `last_viewed_at` から 5 分以内の `view_count +1` をスキップ |
| サムネイル Cache-Control | **3600 秒（1 時間）** | [backend/routers/thumbnails.py](../../../backend/routers/thumbnails.py) `max-age=3600` | ブラウザキャッシュの有効期限 |
| hitomi HTTP タイムアウト | **10 秒** | [backend/services/hitomi/nozomi.py](../../../backend/services/hitomi/nozomi.py) `DEFAULT_TIMEOUT` | NOZOMI / metadata 取得の HTTP タイムアウト |
| API 全体タイムアウト | **30 秒** | [frontend/src/constants.ts](../../../frontend/src/constants.ts) `TIMEOUT_MS` | フロントから axios 経由のリクエスト上限 |
| ジョブポーリング間隔 | **1500 ms** | [frontend/src/constants.ts](../../../frontend/src/constants.ts) `JOB_POLL_INTERVAL_MS` | フロントが PDF 生成・auto-fill ジョブをポーリングする頻度 |
| 検索デバウンス | **300 ms** | [frontend/src/constants.ts](../../../frontend/src/constants.ts) `SEARCH_DEBOUNCE_MS` | PDF 内検索バーの入力遅延 |

### 6.2 経験則による推奨運用値（hardcode ではなく経験則）

「この範囲ならまず問題ない」「超えたら検証が必要」という目安。具体的なベンチマーク測定結果ではなく、**現状運用での体感**ベース。

| 指標 | 快適 | 注意 | 危険 | 根拠・対策 |
|---|---|---|---|---|
| ライブラリ書籍数（1 ソース） | 〜500 冊 | 500〜2000 冊 | 2000 冊超 | サムネイル遅延読み込み (Phase 6 実装) で大半は緩和。`/api/pdfs` レスポンスサイズ・初回 grouping コストが体感に出始める |
| 1 書籍あたりページ数 | 〜200 P | 200〜500 P | 500 P 超 | PDF Reader の page slider サムネイル生成 (`/api/thumbnails/page`) で fitz レンダリングコスト増。Novel Reader は元 PNG を表示する |
| 同時実行 PDF 生成ジョブ | 1（直列） | — | 並列実行 | 設計上は同時実行不可（前ジョブ完了待ち）。`JobStore` 並行制御は履歴保持のみ |
| サークル名自動登録の連続実行件数 | 〜20 件 | 20〜50 件 | 50 件超 | SearXNG レート制限が効き始める。詳細は §4 |
| hitomi 監視対象作者数 | 〜30 人 | 30〜100 人 | 100 人超 | 1 回の監視で `作者数 × NOZOMI 取得` が走り、デフォルト 3 日スキップで負荷を抑える |
| OCR ジョブへの投入 | 1 冊ずつ（推奨） | 複数冊の順次処理 | 大量一括投入 | QA・再実行・障害範囲を 1 冊に閉じる。複数冊は管理ジョブ内でも順次処理される |
| メタデータ DB (`meta2.db`) サイズ | 〜数 MB | 10〜50 MB | 100 MB 超 | SQLite の差分更新を使用。検索 / 集約 hooks の useMemo コストは書籍数 × タグ数で増える |
| ディスク使用量（doujin ソース） | image-only モード前提で WebP のみ | — | — | [ADR-0003](../基本設計/ADR/0003_generated-image-only-mode.md) により PDF 二重保存は廃止済み |

### 6.3 測定が必要なときに実行する確認

- **ライブラリ初回表示時間**: ブラウザ DevTools の Performance タブで `/api/pdfs` レスポンス時間と client-side 処理時間を確認
- **メタデータ DB サイズ**: `Get-Item backend/data/meta2.db | Select Length`
- **書籍数**: `(Get-ChildItem backend/data/<source>/images -Directory).Count`
- **総ディスク使用量**: `(Get-ChildItem backend/data -Recurse | Measure-Object -Property Length -Sum).Sum / 1GB`
- **GPU メモリ使用量**: `nvidia-smi`（OCR 実行中）

### 6.4 限界に近づいたときの対処方針

| 症状 | まず疑う原因 | 一次対応 |
|---|---|---|
| ライブラリ表示が 5 秒超になる | 書籍数増 + サムネイル遅延読み込み未効 | DevTools で `/api/pdfs` レスポンスサイズ確認、grouping 設定を「単純」に切替 |
| サムネイル生成 API が 30 秒超 | `comic` / `novel` の PDF 編集時に fitz が重い + キャッシュミス | ブラウザキャッシュクリア後、再度試行。続くなら fitz レンダリング時間を計測 |
| メタデータ更新が遅い | SQLite の長時間トランザクション / DB 肥大化 | `meta2.db` と WAL のサイズ確認、`PRAGMA integrity_check` を実行 |
| OCR ジョブが進まない | OCR agent 未接続、Surya llama-server 到達不能、モデルパス誤り、GPU メモリ枯渇 | agent の heartbeat、`SURYA_INFERENCE_URL`、または `SURYA_LLAMA_SERVER_PATH` / `SURYA_MODEL_PATH` / `SURYA_MMPROJ_PATH` を確認し、`nvidia-smi` で占有を確認 |
| hitomi 監視が「never」のまま | スクリプト未実行 / 通知失敗 | Task Scheduler 履歴確認、`POST /api/hitomi/run-now` で手動実行 |

### 6.5 シングルユーザー前提の意図的な未対応

以下は「個人 LAN ツール」という前提で**意図的に対応していない**。スケール変化があれば再評価する:

- 認証・認可（LAN 内シングルユーザーのため不要）
- レート制限（クライアント単一のため不要）
- 並行 PDF 生成ジョブ（意図的に直列化、設計簡素化を優先）
- マルチテナント・データ分離
- API バージョニング（[リファクタリング計画書 § 対象外](../../log/計画/リファクタリング計画書.md)）
