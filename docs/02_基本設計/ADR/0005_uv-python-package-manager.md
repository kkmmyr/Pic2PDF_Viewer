# ADR-0005: Python パッケージ管理を `pip` から `uv` に移行

- **Status**: Accepted
- **Date**: 2026-04-26
- **決定者**: プロジェクトオーナー
- **関連**: [変更履歴 W17](../../05_記録/変更履歴/2026-W17.md) `## 2026-04-26: Python パッケージ管理を uv に移行`、[uv環境セットアップ.md](../../04_環境構築/uv環境セットアップ.md)

## コンテキスト

プロジェクト初期は Python 標準の `pip + venv` で依存管理していた。直近の運用で特に致命的な不便は出ていなかったが、以下の懸念が顕在化:

- `requirements.txt` 単独では「直接依存 vs 推移依存」の区別がなく、依存関係のクリーンさを保つのが難しい
- ロックファイル運用（pip-tools 等）は複数ツールの組み合わせで運用が分散する
- Python 仮想環境管理（`venv` 作成・切替）も別ツール
- `uv` は Astral（Ruff の開発元）が提供し、業界での採用が急速に進んでいる

## 検討した選択肢

| 選択肢 | 概要 | 採用しなかった理由 |
|---|---|---|
| 現状維持（pip + venv + requirements.txt） | 標準で枯れている | 将来的に複合ツールチェイン（pip-tools / pipx / venv）を維持する技術負債リスク |
| Poetry | 成熟したパッケージ + 仮想環境マネージャ | 業界の重心が uv に移っている、速度面で uv 優位 |
| pdm | PEP 582 サポート、活発な開発 | 業務での経験少なく、今後のシェア拡大不確実 |
| Rye | Astral 系の前世代ツール | uv に統合される方向 |
| **uv** | Astral 製、Rust 実装で高速、pip 互換 + venv + lockfile を統合 | （採用） |

## 決定

Python パッケージ管理を **uv** に移行する。マニフェストは `backend/pyproject.toml` + `backend/uv.lock`、実行は `uv run`、追加は `uv add`、同期は `uv sync`。

## 根拠

- **将来の技術負債回避が主目的**。現時点で pip に致命的な不便はないが、コミュニティと業務の重心が uv に移っており、後から移行するほどコスト増。
- **再現性**: `uv.lock` で全依存を固定、CI / 別マシンでも同一バージョンが入る。
- **速度**: Rust 実装で `uv sync` が高速。日常運用での待ち時間が減る。
- **統合**: 仮想環境作成・依存追加・ロック・実行が単一 CLI に集約され、覚えるコマンドが少ない。

## 結果

### ポジティブ
- `uv add <pkg>` で「マニフェスト追加 + ロック更新 + 仮想環境同期」が一発
- `pyproject.toml` に統一され、メタ情報（プロジェクト名・Python バージョン要件）も同居
- CI 等で `uv sync --frozen` により厳密再現が可能
- Mac へのポートも uv は同等にサポート

### ネガティブ・受容したコスト
- 開発者は uv のインストールが初期セットアップに必要（[uv環境セットアップ.md](../../04_環境構築/uv環境セットアップ.md) で手順化）
- スキル / hooks が `pip install` を前提にしている場合は書き換え必要（既に対応済み）
- 一部の Windows ネイティブ拡張（pyzbar 等）で uv のインストール挙動を確認する必要があった

### 影響範囲
- `backend/pyproject.toml` / `backend/uv.lock`
- `.claude/CLAUDE.md`（uv 利用ルールの明記）
- `backend/Dockerfile` 相当のセットアップスクリプト（あれば）
- `start.bat` / `start_server.bat` 等の起動スクリプト

## 将来の再評価条件

- uv のメンテナンスが滞ったとき
- pdm / Poetry が業界標準に戻る兆候があるとき
- Linux 環境への対応が必要になり uv の Linux 周りに問題が出たとき（**現時点で Linux 開発予定なし、Mac は将来あり得る**）
