#### Phase 55-4 — `hybrid_search` の `_resolve_book_names` 二重呼び出し解消（P2: 重複ロジック）

**問題**: `backend/services/novel_db/search.py` の `fts_search` / `vec_search` / `search_book_summaries` がそれぞれ独立に `_resolve_book_names(scope)` を呼ぶ。`hybrid_search` は `fts_search` + `vec_search` 両方を呼ぶため、scope=series のとき `load_meta("novel")`（ファイル I/O）が 2 回走る。
**改善案**: 二択。
  1. `hybrid_search` 内で 1 回だけ `_resolve_book_names` を呼び、結果を `book_names: list[str] | None` として内部版関数（`_fts_search_with_book_names` / `_vec_search_with_book_names`）に渡す。
  2. `_resolve_book_names` を `@lru_cache(maxsize=16)`（tuple キー）でキャッシュ。

シグネチャを変えずに済む後者が低リスク。
**変更対象**: `backend/services/novel_db/search.py`
**新規作成**: なし
**完了条件**: `uv run pytest tests/test_novel_db_search.py -v` 通過。外部 API 不変。

#### Phase 55-6 — `post_qa` SSE ブロック内のログ欠落補完（P3: 観測性）

**問題**: `routers/novel_db.py` の `post_qa` は SSE のため `@log_and_raise_500` を付けられないが、`event_stream()` 内の `except Exception as e:` で `logger.exception` を呼ばず、`str(e)` を SSE に流すだけ。本番障害時のデバッグでサーバ側ログが残らない。また「なぜ `@log_and_raise_500` が付いていないか」がコード上どこにも明記されていない。
**改善案**: 2 点。
  1. `except Exception as e:` 直後に `logger.exception("novel_db/qa SSE error: history_id=%s", history_id)` を追加。
  2. `post_qa` の docstring に「SSE のため `@log_and_raise_500` は非適用。ストリーム内で例外を捕捉して SSE event でクライアントへ通知し、サーバ側は `logger.exception` でログ記録する」と明記。

**変更対象**: `backend/routers/novel_db.py`（L320 付近）
**新規作成**: なし
**完了条件**: `uv run pytest tests/test_router_novel_db.py -v` 通過。動作変更なし。

## 対象外（現状維持）

リスク・工数に対してメリットが小さい、または現行設計で十分な項目。

| 項目 | 理由 |
|---|---|
| Pydantic ↔ TS 型自動生成（openapi-typescript 等） | 工数大。手書き同期で運用継続 |
| `pdf_generator.execute_moves` と `file_manager` のロールバック共通化 | 対象（処理ファイル種・タイミング）が異なり、共通化メリット小 |
| `GEMMA_TOOL_DIR` の Windows パス依存デフォルト値 | Phase 8 で `.env` で上書き可能。Linux/Mac 開発予定なし |
| SearXNG → DLsite 直接検索 | 既知の問題として記録済み（Phase 12 時点で対象外維持） |
| `useLibraryManagement` のリネーム | 影響範囲が広い割に効果小 |
| `types/index.ts` の `BookMetaEntry` 拡張 | サークル名のみ管理の現行設計で十分 |
| API バージョニング | 現状シングルクライアント構成のため不要 |
