### Phase 63〜67 — ライブラリ・DB 刷新（2026-05-14 追加）

#### Phase 64 — `meta_store` / `genre_store` → SQLite 移行（P1）

**問題**: 書籍メタデータ（著者・ジャンル・閲覧回数・シリーズ情報等）が `data/meta/{source}/meta.json` と `data/genres/{source}.json` の JSON ファイルで管理されている。  
- `load_meta()` が呼ばれるたびに全件 JSON 読み込み（O(n)）
- `search.py` の `_resolve_book_names()` でシリーズスコープ解決のたびに `load_meta("novel")` 呼び出し
- ソース単位でしかロックできない（書籍単位の並行書き込み不可）
- クエリ・インデックスが使えない

**改善案**: `novel.db`（または独立した `meta.db`）に `books_meta` テーブルを作成し JSON ファイルを廃止。`meta_store.py` / `genre_store.py` のインターフェースを維持したまま内部実装を SQLite に置き換える。  
**変更対象**: `backend/services/meta_store.py`、`backend/services/genre_store.py`、全 router（`meta`・`library`・`genres`・`series`）、`backend/services/novel_db/search.py`  
**完了条件**: pytest 全通過・既存 JSON からのマイグレーションスクリプト完備・dev server で全 CRUD 動作確認  
**注意**: 影響範囲が広いため着手前に詳細設計が必要。

#### Phase 65 — TanStack Query 導入（P2）

**問題**: `usePolling`・`usePdfStatus`・`useGenerateJob`・novel_db 系 hooks でポーリング・キャッシュ・invalidation を自前実装しており重複が多い。  
**改善案**: `@tanstack/react-query` を導入し `usePolling` ベースの hooks を `useQuery`（`refetchInterval`）+ `useMutation`（`invalidateQueries`）パターンに置き換える。フロント hooks 整理（Phase 65-x）と同時着手が効率的。  
**変更対象**: `frontend/src/hooks/usePolling.ts` およびその利用箇所、`frontend/src/hooks/usePdfStatus.ts`、`frontend/src/hooks/useGenerateJob.ts`、`frontend/src/hooks/novel_db/` 配下  
**新規作成**: `frontend/src/lib/queryClient.ts`（`QueryClient` インスタンス）  
**完了条件**: vitest 全通過・`usePolling` の直接利用箇所がゼロになること・dev server でジョブ状態ポーリング動作確認

#### Phase 66 — Alembic 導入（P2）✅

**問題**: `backend/services/novel_db/schema.py` の `_migrate()` が手書きの `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` チェックの連鎖になっており、カラム追加のたびに行数が増える。バージョン管理・ロールバック手順がコード外に存在しない。  
**実装**: `alembic` を本体依存に追加（runtime で upgrade_head() を呼ぶため）。`backend/alembic/` に env.py / script.py.mako / versions/ 配置。`_migrate()` を `0001_initial.py` revision に移管（idempotent）。`_ddl()` は全カラムを含む最新スキーマに更新。`schema.py` から `_migrate()` を削除し `init_schema()` を簡略化。`migrations.py` 新規作成で `upgrade_head()` ヘルパーを提供。`main.py` lifespan に組み込み（失敗で起動中断）。詳細: [履歴.md § Phase 66](../05_記録/変更履歴.md)

#### Phase 67 — React 18 → 19 アップグレード（P3）

**問題**: `react@18.2.0` / `react-dom@18.2.0`。React 19 の `use()` フック・Server Actions・改善された Suspense が使えない。`@types/react` / `@types/react-dom` もバージョンアップが必要。  
**改善案**: `npm install react@19 react-dom@19 @types/react@19 @types/react-dom@19` で更新。破壊的変更（`ref` コールバック型変更・`forwardRef` 廃止推奨・`ReactDOM.render` 削除）を確認しコード修正。  
**変更対象**: `frontend/package.json`、影響を受けるコンポーネント（`forwardRef` 使用箇所など）  
**完了条件**: vitest 全通過・tsc エラーなし・dev server で主要画面動作確認  
**参考**: `react-pdf@10` / `pdfjs-dist@5` が React 19 対応済みかリリースノートで確認してから着手。

#### Phase 62 — ベクトル DB を sqlite-vec → LanceDB に移行（P2）✅

**問題**: sqlite-vec の `vec0` 仮想テーブルは線形スキャン（O(n)）のため、チャンク数増加に比例して検索レイテンシが増大。ANN インデックスを後から追加できない設計制約があった。  
**実装**: `lance_store.py` 新規作成（chunks/summaries テーブル、IVF_PQ 自動構築）。`migrate_to_lancedb.py` で既存データ移行（chunks 2,781 件・summaries 13 件）。D: ドライブが exFAT のため `.env` で `NOVEL_DB_LANCE_PATH` を C: NTFS へリダイレクト。pytest 817 件全通過。

詳細: [履歴.md § Phase 62](リファクタリング履歴.md)

## 対象外（現状維持）

リスク・工数に対してメリットが小さい、または現行設計で十分な項目。

| 項目 | 理由 |
|---|---|
| Pydantic ↔ TS 型自動生成（openapi-typescript 等） | 工数大。手書き同期で運用継続 |
| `pdf_generator.execute_moves` と `file_manager` のロールバック共通化 | 対象（処理ファイル種・タイミング）が異なり、共通化メリット小 |
| `GEMMA_TOOL_DIR` の Windows パス依存デフォルト値 | Phase 8 で `.env` で上書き可能。Linux/Mac 開発予定なし |
| SearXNG → DLsite 直接検索 | 既知の問題として記録済み（Phase 12 時点で対象外維持） |
| `useLibraryManagement` のリネーム | 影響範囲が広い割に効果小 |
| `types/index.ts` の `BookMetaEntry` 拡張 | サークル名のみ管理の現行設計で十分 |
| API バージョニング | 現状シングルクライアント構成のため不要 |
