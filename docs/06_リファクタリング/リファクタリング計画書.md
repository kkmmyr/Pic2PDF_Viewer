# リファクタリング計画書

最終更新: 2026-04-19

---

## 概要

プロジェクト全体の構造整理を段階的に実施する計画。  
影響範囲を最小化するため、Phase 1（定数・ユーティリティ整備）から始め、破壊的変更を後回しにする。

---

## Phase 1 — 定数・ユーティリティ整備（低リスク）

依存関係がなく、他機能への影響がほぼゼロ。最優先で実施する。

### 1-1. バックエンド：定数の一元化

**問題:** マジックナンバー・ハードコード値が各所に散在

| ファイル | 行 | 値 | 対処 |
|---|---|---|---|
| `services/pdf_generator.py` | 24 | `base_height = 500` | `config.py` に `THUMBNAIL_HEIGHT = 500` として移動 |
| `services/ocr_service.py` | 22 | `maxlen=2000` | `config.py` に `OCR_LOG_MAXLEN = 2000` として移動 |
| `routers/pdfs.py` | 67 | `MAX_JOBS = 300` | `config.py` に移動 |

**対応ファイル:** `backend/config.py`

---

### 1-2. バックエンド：サムネイル名生成の共通化

**問題:** `os.path.splitext(name)[0] + ".jpg"` が以下で重複

- `routers/library.py`: 235, 237, 241-242, 277-278, 309-310行
- `routers/pdfs.py`: 43, 248, 370行

**対処:** `backend/utils/file_naming.py` を新規作成

```python
# backend/utils/file_naming.py
def get_thumbnail_name(pdf_name: str) -> str:
    return os.path.splitext(pdf_name)[0] + ".jpg"
```

---

### 1-3. バックエンド：画像拡張子定数の一元化

**問題:** 対応拡張子が複数箇所でバラバラに定義

- `routers/library.py:80` — `.webp, .jpg, .jpeg, .png`
- `services/pdf_generator.py:98, 223` — `.webp` のみ

**対処:** `backend/config.py` に追加

```python
SUPPORTED_IMAGE_FORMATS = ('.webp', '.jpg', '.jpeg', '.png')
SUPPORTED_SOURCE_FORMATS = ('.webp', '.zip')
```

---

### 1-4. フロントエンド：定数ファイルの作成

**問題:** localStorage キー・ポーリング間隔・タイムアウト値が各所でハードコード

| ファイル | 値 |
|---|---|
| `pages/GeneratorPage.tsx:11` | `'generator_active_job'` |
| `components/viewer/LibraryPanel.tsx:9` | `'librarySortOrder'` |
| `config/api_client.ts:25` | `timeout: 30_000` |
| `hooks/usePolling.ts:23` | `interval = 2000` |

**対処:** `frontend/src/constants.ts` を新規作成

```typescript
export const STORAGE_KEYS = {
    GENERATOR_JOB: 'generator_active_job',
    LIBRARY_SORT: 'librarySortOrder',
} as const;

export const API_CONFIG = {
    TIMEOUT_MS: 30_000,
    POLL_INTERVAL_MS: 2000,
} as const;
```

---

### 1-5. フロントエンド：localStorage ラッパーの共通化

**問題:** try-catch を使った JSON の読み書きが3箇所で重複

- `pages/GeneratorPage.tsx:18-33`
- `components/viewer/LibraryPanel.tsx:13-16`
- `hooks/useFavorites.ts:13-20`

**対処:** `frontend/src/utils/storage.ts` を新規作成

```typescript
export function getStorageJson<T>(key: string, fallback: T): T
export function setStorageJson<T>(key: string, value: T): void
export function removeStorage(key: string): void
```

## Phase 2 — バックエンド責務分離（中リスク）

サービス層の整理。既存のルーターは変更するが、APIエンドポイントは変えない。

### 2-1. ファイル操作サービスの作成

**問題:** PDF・サムネイル・画像の3点セット操作が以下で重複

- `routers/library.py:125-178` — move_items
- `routers/library.py:204-257` — rename_item
- `routers/pdfs.py:230-257` — delete_pages

**対処:** `backend/services/file_manager.py` を新規作成

```python
class FileManager:
    @staticmethod
    def move_with_assets(src_pdf, dst_pdf, src_dirs, dst_dirs) -> None: ...
    @staticmethod
    def rename_with_assets(old_name, new_name, dirs) -> None: ...
    @staticmethod
    def delete_with_assets(pdf_name, dirs) -> None: ...
```

---

### 2-2. ジョブ管理の分離

**問題:** `GenerateJob`, `JobStore`, `GenerateState` クラスがルーターファイル `routers/pdfs.py:1-162` に定義されている（ビジネスロジックがルーターに混在）

**対処:** `backend/services/job_manager.py` を新規作成し移動

```python
# backend/services/job_manager.py
class GenerateJob: ...
class JobStore: ...
class GenerateState: ...
```

`routers/pdfs.py` からはインポートに置き換える。

---

### 2-3. エラーハンドリングの統一

**問題:** 例外の種類がファイルごとにバラバラ

- `routers/library.py` — HTTPException + 手動ロールバック
- `routers/pdfs.py` — HTTPException を直接 raise
- `services/ocr_service.py` — RuntimeError

**対処:** `backend/exceptions.py` を新規作成

```python
class FileOperationError(Exception): ...
class OcrProcessError(Exception): ...
```

FastAPI の exception handler で HTTP レスポンスに変換する。

## Phase 3 — フロントエンド責務分離（中リスク）

コンポーネント分割。UIの見た目は変えない。

### 3-1. GeneratorPage のジョブ管理をフックに抽出

**問題:** `GeneratorPage.tsx` (341行) でジョブポーリングを独自実装しており、`usePolling` フックが活用されていない

**対処:** `frontend/src/hooks/useGenerateJob.ts` を新規作成

```typescript
export function useGenerateJob() {
    // job_id の保存・復元・ポーリングを usePolling で統一
    return { currentJob, startJob, isGenerating, isRestoredJob };
}
```

GeneratorPage はフックを呼び出すだけにする。

---

### 3-2. ReaderPanel の分割

**問題:** `ReaderPanel.tsx` (351行) に6つの責務が混在

現在の責務:
1. PDF/画像の取得と描画
2. ページナビゲーション
3. テキスト検索
4. 編集モード（ページ削除）
5. サムネイル管理
6. 見開きモード切り替え

**対処:** 編集モードUIを分離

```
ReaderPanel (統括・現行維持)
├── PageRenderer (既存・変更なし)
├── ReaderHeader (既存・変更なし)
├── PdfSearchBar (既存・変更なし)
└── EditModePanel (新規) ← ページ削除UI を分離
```

`EditModePanel` を `components/reader/EditModePanel.tsx` として切り出す。

---

### 3-3. LibraryPanel の分割

**問題:** `LibraryPanel.tsx` (251行) に5つの責務・20個超のProps

**対処:** ダイアログ群を別コンポーネントに集約

```
LibraryPanel (統括・Props削減)
├── LibraryHeader (既存・変更なし)
├── PdfGrid / FolderGrid (既存・変更なし)
└── LibraryDialogs (新規) ← 各種ダイアログのマウント管理
```

`LibraryDialogs` に Move/Rename/CreateFolder/BulkAuthor/Merge ダイアログをまとめ、Props の数を削減する。

## 対象外（現状維持）

以下はリスクに対してメリットが小さいため対象外とする。

- `useLibraryManagement` → `useLibrary` へのリネーム（影響範囲が広い割に効果小）
- Props ドリリングの Context 化（現状3層で許容範囲内）
- テスト追加（別途計画が必要）
- `services/pdf_generator.py` のクラス分割（動作が安定しており、分割コストが高い）
