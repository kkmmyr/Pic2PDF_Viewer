## 2026-05-10: feat(novel_db) — 書籍サマリを検索インデックスに追加（B-8）

### 内容

- **スキーマ**（[schema.py](../../backend/services/novel_db/schema.py)）
    - `book_summaries_vec USING vec0(embedding FLOAT[1024])` 追加。rowid = books.id。既存 DB は `_migrate()` で自動追加
- **summarizer の embedding upsert**（[summarizer.py](../../backend/services/novel_db/summarizer.py)）
    - `update_book_summary()` がサマリ保存時に bge-m3 で embedding を取って `book_summaries_vec` に upsert（DELETE → INSERT で重複回避）
    - embedder 失敗（タイムアウト等）時はサマリ本文だけ保存し、vec 側は次回 `--redo` を待つ後方互換ガード
- **ベクトル検索**（[search.py](../../backend/services/novel_db/search.py)）
    - 新関数 `search_book_summaries(conn, query, scope, top)` で書籍サマリのベクトル類似度検索
    - FTS5 はサマリ向きでないため使わず、bge-m3 の意味類似度のみ
    - `book_summaries_vec` 未存在の古い DB では空リストを返す後方互換
- **QA 統合**（[routers/novel_db.py](../../backend/routers/novel_db.py)）
    - scope=all / scope=series で **「ページヒット書籍 ∪ サマリヒット書籍」の和集合** を `load_summaries_for_books()` に渡すよう変更
    - ページに引っかからなかった書籍も俯瞰サマリでプロンプトに乗るように
- **設定**: [config.py](../../backend/config.py) に `NOVEL_DB_QA_TOP_SUMMARIES = 11` 追加
- **テスト**: 9 件追加、backend pytest **686 → 695 件 全 PASS**
    - `test_novel_db_search_summary.py`: 5 件（distance 順 / scope フィルタ / vec テーブル欠落時の後方互換 / top 件数制限）
    - `test_novel_db_summarizer.py` に 4 件追加（embed 成功時のインデックス / 失敗時のフォールバック / 重複 INSERT 防止 / 不在書籍エラー）
- **既存 summary のバックフィル**: 既に生成済みだった 2 冊のサマリを再 embedding して vec へ登録
- **設計書反映**: [バックエンド設計 §4 / §6.5 / §7.4](../../design/詳細設計/機能別/小説テキスト検索・RAG機能_バックエンド設計.md) / [機能追加候補 B-8](../計画/バックログ.md) を実装完了に

### 動作確認

「メルディの軍師としての活躍」のような概括質問で、サマリ検索が「10 二人の軍師」を distance 0.97 で 1 位に、「1 巻」を 1.18 で 2 位に置く動作を実機確認（タイトル通り軍師がテーマの巻が圧勝）。

### 影響

- `scope=all` / `scope=series` で、ページ抜粋に引っかからない書籍も俯瞰サマリで Qwen に伝わるため、概括的な質問の回答品質が更に向上
- `summary` 未生成の書籍は何の影響も受けない（後方互換）
- 同 query での bge-m3 呼び出しが page 検索 + サマリ検索の 2 回になり、応答時間が +1〜2 秒程度増える可能性

## 2026-05-10: feat(novel_db) — 書籍俯瞰サマリ事前生成（B-5）を実装

### 内容

- **スキーマ**（[schema.py](../../backend/services/novel_db/schema.py)）
    - `books.summary TEXT` / `books.summary_generated_at TIMESTAMP` を追加。既存 DB は `_migrate()` で ALTER 自動マイグレート（実 DB で確認済み）
- **新規モジュール**: [services/novel_db/summarizer.py](../../backend/services/novel_db/summarizer.py)
    - `summarize_book(conn, book_name)`: Qwen で map-reduce 要約。map（各 ~20000 字チャンクを 400 字に）+ reduce（統合して 1500 字に）。1 冊で完結する短い書籍は 1-shot 経路
    - `update_book_summary` / `load_summaries_for_books` の DB 入出力ヘルパ
    - `_chunk_for_map`: 改行境界優先 + 最大 8 チャンクの安全側分割
- **新規 CLI**: [scripts/build_novel_summaries.py](../../backend/scripts/build_novel_summaries.py)
    - `--all` / `--book NAME` / `--series ID` / `--redo`
    - 進捗表示 + 経過時間 + ETA 出力
- **QA プロンプト統合**（[llm.py](../../backend/services/novel_db/llm.py) / [routers/novel_db.py](../../backend/routers/novel_db.py)）
    - `build_prompt()` に `book_summaries` 引数（keyword-only、後方互換）を追加
    - `scope=all` / `scope=series` のとき、ヒット書籍のサマリを取得してプロンプト先頭の **【書籍俯瞰サマリ】** ブロックに埋め込む
    - `summary IS NULL` の書籍は単にブロックに含めない（後方互換）
    - `scope=book` のときはサマリブロック自体を付与しない（page 抜粋で十分なため）
- **テスト**: 19 件追加 / backend pytest **666 → 686 件 全 PASS**
    - `test_novel_db_summarizer.py`: 10 件（チャンク分割・本文ロード・map-reduce 切替・DB 入出力・空ボディ等の境界）
    - `test_novel_db_llm_prompt.py`: 9 件（scope ごとのヘッダ生成・サマリブロック埋め込み有無・サマリ → page の順序）
- **設計書反映**: [バックエンド設計 §3 / §4 / §5.7 / §5.8 / §7.2 / §14](../../design/詳細設計/機能別/小説テキスト検索・RAG機能_バックエンド設計.md) / [機能追加候補 B-5 を実装完了に](../計画/バックログ.md) / [要件定義 §9](../../design/詳細設計/機能別/小説テキスト検索・RAG機能_バックエンド設計.md)

### 背景

- Qwen 切替で踏み込みは大きく改善したが、`scope=all` / `scope=series` の概括的な質問は依然として「ハイブリッド検索 top_k=16 件のページ抜粋」依存で、全 11 冊・1359 ページを俯瞰しきれない構造
- 当初の品質改善議論で「本命改善」案 B として提示していたが、即時改善（フィルタ + プロンプト + 主要登場人物抽出）+ Qwen 切替で「いったん許容範囲」となり保留していた
- 用件として把握できていなかった気づきの再発掘で再着手判断

### 影響

- 初期サマリ生成は別途 user 任意のタイミングで `uv run python scripts/build_novel_summaries.py --all`（11 冊 × 5〜15 分 ≒ 約 1.5〜2 時間）で実行

### 背景

- Gemma 4:26b では「シリーズ全体テーマは？」のような概括的な質問への回答が浅く、汎用語の羅列で済まされる事象が頻発
- 候補モデル比較（GLM-5.1 / MiniMax M2.7 / Kimi K2.6 / DeepSeek V4）のうちローカル VRAM に乗るのは Qwen3.6:35b-a3b（35B 総 / 活性 3B MoE）。同条件で実測比較した結果、Gemma が `done_reason='length'` で 830 chars 途中切断だったのに対し、Qwen は `done_reason='stop'` で 2246 chars 完走、章ごと対比 + 具体例引用を含む構造的回答を生成
- Qwen3.x は thinking モデルで `stream=True` / `think=False` 必須・`num_predict` を thinking で食い潰される地雷があり、各プロジェクトで再実装したくないので共通化

### 影響

- 応答時間 30〜100 秒 → 80〜130 秒（1.5 倍）。品質向上とのトレードオフとして受容
- VRAM 消費 ~22GB（embedding と LLM は元々直列実行のため運用影響軽微）
- backend regression: pytest 666 件 / 全 PASS
- Pic2PDF backend が外部ディレクトリ（`D:\61.tool\common\Qwen`）に依存。共通モジュール側を破壊的変更しないルールを `CLAUDE.md` に明記

## 2026-05-10: feat(novel_db) — RAG 質問応答の品質改善（検索フィルタ + 主要登場人物抽出 + プロンプト強化）

### 内容

- **検索フィルタを 3 つ追加**（[search.py](../../backend/services/novel_db/search.py) / [config.py](../../backend/config.py)）
    - `min_chars` (`NOVEL_DB_MIN_BODY_CHARS = 300`): 章扉・目次・人物紹介の薄いページ除外
    - `body_page_margin` (`NOVEL_DB_BODY_PAGE_MARGIN = 5`): 各書籍の先頭・末尾 5 ページ除外（表紙・口絵・あとがき・解説・奥付）
    - `max_per_book` (`NOVEL_DB_QA_MAX_PER_BOOK = 2`): `scope=all` / `scope=series` で 1 書籍あたり取得上限。書籍偏り抑制
    - `top_k` を `NOVEL_DB_QA_TOP_K = 16` に拡大（フィルタで弾かれる分を見越して多めに取得）
- **主要登場人物抽出**（新規 [character_extractor.py](../../backend/services/novel_db/character_extractor.py)）
    - `pages.main_characters TEXT` カラム追加、既存 DB は `_migrate()` で ALTER 自動マイグレート
    - `gemma4:e4b` で各ページの主要登場人物を最大 3 名まで抽出（`stream=True` / `think=False` / `num_predict=4096`）
    - 1 ページ 1〜3 秒、1359 ページで 30〜60 分
    - 全 11 冊抽出済み（1,279 / 1,359 ページ = 94%）
- **プロンプト強化**（[llm.py:PROMPT_TEMPLATE](../../backend/services/novel_db/llm.py)）
    - キャラ帰属ルール（誰の発言・行動・心情かを必ず明記、別ページのキャラを安易に統合しない）
    - 概括質問は「具体シーン 3 つ以上 + テーマ・キャラ変化分析 + 巻間対比」を要求
    - 各 page ヘッダに `主要登場人物: A, B, C` ヒントを埋め込み、キャラ帰属の誤統合を抑制
- **設計書反映**: [バックエンド設計 §5.6 / §6.5 / §7.2](../../design/詳細設計/機能別/小説テキスト検索・RAG機能_バックエンド設計.md) を新設・更新

### 背景

- D3-4 リリース直後に動作確認したところ、参照ページに「画像だけのページ」「作者紹介」「目次」が混入。さらに「シリーズ全体テーマ」のような概括質問の回答が浅い
- 即時改善（フィルタ + プロンプト）→ 主要登場人物抽出（誤帰属対策）の 2 段階で品質を引き上げ
- ハルシネーション率は実測 ~18%（11 件中 2 件で別キャラの行動として誤帰属）。許容範囲として運用、本質改善は B-5（書籍ごとサマリ事前生成）として保留

### 影響

- 検索結果の S/N 比が大幅改善（薄いページ・付録ページが除外され、scope=all で全冊から均等にサンプル）

## 2026-05-09: fix(reader) — DnD で着地位置がドラッグ中プレビューと 1 ポジションずれる不具合を修正（B-3 後続）

### 背景

B-3 のリリース後、「移動後にチェックしたページを削除しようとすると、別のページが削除されているように見える」という報告があった。

調査の結果、**`moveMultipleByIndex` のセマンティクスが @dnd-kit のドラッグ中プレビューと一致していなかった**ことが原因。

具体的には:
- @dnd-kit が drag 中に表示するプレビュー（`rectSortingStrategy`）は `arrayMove` 相当の **AT 方式**（active アイテムが `targetIndex` に着地）で計算される
- 一方、`moveMultipleByIndex` は **BEFORE 方式**（移動アイテムを `targetIndex` の直前に挿入）で実装されていた
- 結果、選択ページを単独 drag してドロップした際、視覚プレビューでは「位置 4 に着地」と見せておきながら、実装は **位置 3** に置いていた
- マークの追従や API 呼び出しは内部一貫していて削除は math 的には正しく動作するが、ユーザーから見ると「視覚的にドロップした位置と異なるページが highlighted されて、それが削除される」ように感じる
- 加えて、未選択カードからの drag は `arrayMove` を使っていたため、選択時/未選択時で着地位置がずれる不整合もあった

### 動作仕様

`moveMultipleByIndex` を **AT 方式**に変更:
- 引数に `activeIndex` を追加（ユーザーが実際にドラッグした起点アイテムの index）
- active アイテムが結果配列の `targetIndex` に着地するようグループ全体を配置する
- グループの先頭位置 = `targetIndex - activeOffsetInMoved` を `[0, remaining.length]` でクランプ
- 単独移動 (`movedIndices.length === 1` かつ `movedIndices[0] === activeIndex`) のときは `arrayMove(arr, activeIndex, targetIndex)` と完全に等価

これで:
- 選択時 / 未選択時の DnD 着地位置が一致
- @dnd-kit のドラッグ中プレビューと実際の結果が一致
- ユーザーがドロップした「まさにその位置」にマークが残るので、削除実行時の対象が直感的に正しい

## 2026-05-09: fix(security) — パストラバーサル検証の誤検出修正（`..` を成分単位で判定）

### 背景

タイトルに連続 3 ドット（`...`）を含む書籍（例: `わたし...変えられちゃいました。 ―アラサーOL〜― 総集編.pdf`）が開けない問題が報告された。

原因は `backend/utils/path_utils.py` の `validate_safe_path` / `validate_safe_name` が `".." in path` という **部分文字列マッチ**でディレクトリトラバーサルを検出していたため。`...`（3 ドット）の中に `..`（2 ドット）が含まれてしまい、正規のファイル名まで `HTTP 400 Invalid path` / `Invalid name` で弾かれていた。

実害として、当該書籍は以下の経路で全部落ちる：
- `GET /api/books/<bookname>/images` → 400 Invalid path（image-mode 表示失敗）
- `POST /api/meta/view` → 400 Invalid name（閲覧記録失敗）
- 結果: リーダーが起動できない

OS が `..` を親ディレクトリ参照として特別扱いするのは「パス成分として `..` 単独」のときだけ。`foo..bar` や `わたし...` は OS にとってただの名前で、トラバーサル攻撃には使えない。**部分文字列チェックは over-broad な実装ミス**だった。

### 動作仕様

**`validate_safe_path`**:
- パスを `/` または `\\` で分割した成分（`split`）の **いずれかが `..` と完全一致**したときのみ拒否
- `/` または `\\` で始まる絶対パスは引き続き拒否
- 例: `../etc/passwd` (成分 `..` あり → 拒否), `foo/../bar` (中間に `..` 成分 → 拒否), `わたし...変えられちゃいました.pdf` (`..` 成分なし → 許可)

**`validate_safe_name`**:
- 名前が `.` または `..` と**完全一致**したときのみ拒否（カレント／親ディレクトリ参照防止）
- `/` または `\\` を含む名前は引き続き拒否（パスセパレータ混入防止）
- 例: `..` (拒否), `.` (拒否), `folder/file.pdf` (拒否), `..secret` (許可: ただの隠しファイル名)、`My...pdf` (許可)

### セキュリティ評価

緩和ではなく **誤検出の修正**：

- 攻撃面で `..` 単独成分を要求するため、トラバーサル防御の本質は維持。
- `..secret` のような名前は OS から見れば普通のファイルで、ディレクトリ階層を 1 つ上に登る効果はない（`os.path.join("/data", "..secret")` → `/data/..secret`）。よって誤検出されていただけで、許可しても安全。
- `routers/_deps.py:validate_request_targets` 経由で path/name を二重検証している運用は変えない。

## 2026-05-09: chore(reader) — pdf.js の getHexString 警告を抑止（verbosity = ERRORS）

### 背景

リーダー切替のたびに `Warning: getHexString - ignoring invalid character: <code>` が数十〜百件単位でコンソールに出ていた問題を抑止する。

原因は **OCR 済み Searchable PDF**（`kindle-pdf/searchable_pdf.py` が ReportLab で生成）の構造にある。画像オブジェクトを `/Filter [/ASCII85Decode /FlateDecode]` で埋め込んでおり、ASCII85 のペイロード中に `<` が裸で頻出する（例: `*<p\<j%`, `<n=K;HpCK)d` 等）。pdf.js の lenient parser が初期スキャン中にこれを hex 文字列の開始と誤読し、`<...>` 内の hex 以外の文字（`o`/`t`/`y`/`p`/`h`/`m`/`l` など ASCII85 アルファベットのうち hex として解釈できないもの）について 1 文字ずつ警告を出していた。

機能影響はなく（`getHexString` は警告しつつスキップする lenient 設計）PDF 表示・検索・コピーに支障はないが、kindle ライブラリの 13 冊の Searchable PDF を開くたびにコンソールが汚れデバッグの邪魔だったため抑止する。

### 動作仕様

- `<Document options={PDF_DOCUMENT_OPTIONS}>` で `verbosity: pdfjs.VerbosityLevel.ERRORS` を渡す。これにより WARNINGS / INFOS レベルのログが出なくなり、ERRORS のみコンソールに出力される。
- `PDF_DOCUMENT_OPTIONS` はモジュールスコープで定数化。`<Document>` の `options` プロパティは識別性が変わると react-pdf が再読込を誘発するため、毎レンダー新規オブジェクトを生成しないように固定する。
- グローバルな `setVerbosityLevel` ではなく per-Document option として渡しているため、影響範囲は ReaderPanel の PDF 表示のみ。他の用途（将来的にサムネイル生成等で pdf.js を使う場合）には波及しない。

### 副作用

- **デバッグ時の影響**: pdf.js 由来の他の WARNINGS（破損 PDF、フォント解決失敗など）も同時に黙る。pdf.js の異常を切り分けたいときは一時的に `verbosity: pdfjs.VerbosityLevel.WARNINGS` へ戻す必要がある。
- **未対処の根本原因**: ReportLab の出力フォーマットそのものは変えていない。OCR 出力の filter を `/HexDecode` 等に切り替えるか、別ライブラリで再生成すれば根本解決するが、13 冊の再 OCR 工数とトレードオフのため見送り。

**設計書** (更新):
- `docs/03_詳細設計/詳細設計書_フロントエンド編.md`: `ReaderPanel` の Worker設定節に「verbosity 抑止」項を追記。

## 2026-05-09: fix(reader) — 見開き原稿（センターカラー等）の表示崩れ修正（A-3）

### 背景

機能追加候補.md A-3 の実装。Auto モードで「見開きページと 1 ページ画像が混在すると画面が崩れる」問題が継続していた。同人誌のセンターカラー等で頻繁に遭遇するケース。

原因は 3 点絡み合っていた:
1. `autoIsSpread` が単一 state で「最後にレンダーされたページ」に上書きされ、ページ送りで Auto レイアウトが動的に切り替わる。
2. 判定対象が右ページ or 単独ページのみで、左ページ側の見開き原稿は無視されていた。
3. `width <= height` の単純比較で、1:1 近いページの境界値で判定がバタつく。

### 動作仕様

- **閾値方式**: `width > height * 1.2` で横長判定（センターカラー等の見開き原稿を検出）。
- **片方優先**: 横長検出時は `autoIsSpread` を即 `false` 確定。縦長検出時は何もしない（初期値 `true` を維持）。これにより、現在ペアのいずれか一方でも横長を検出すれば 1 ページ表示になる。
- **左右両通知**: `ReaderPanel` から `PageRenderer` の `onPageSize` を左右両ページで呼ぶよう拡張。

## 2026-05-09: feat(series) — AI 提案（既存シリーズへの紐付け候補）を実装（A-1）

### 背景

### 動作仕様

1. 選択モードで書籍を 1 冊以上選び、ヘッダーから「シリーズに登録」を開く
2. ダイアログに第 3 のラジオ「**AI が提案するシリーズに追加**」を追加
3. ラジオ選択時に `POST /api/series/suggest` を自動呼び出し
4. 上位 5 件までの候補（`series_title` + スコア + 作者一致表示）をラジオで表示
5. ユーザーが 1 件選んで「登録」 → 既存の `POST /api/series/assign` で確定（`existing` モードと同じ書き込み経路）

### マッチング戦略

- 既存シリーズの `series_title` 末尾の巻数表記を除いた本体で比較
- 各選択書籍タイトルとの **共通プレフィックス長 / min(タイトル長, シリーズ本体長)** をスコア化、全書籍の平均
- 全書籍で作者集合が一致したら +0.2 加点（`AUTHOR_MATCH_BONUS`、上限 1.0）
- 閾値 `SUGGEST_MIN_SCORE=0.4` 未満は除外、上位 `SUGGEST_MAX_CANDIDATES=5` 件まで

## 2026-05-07: feat(backend) — バックエンドログを RotatingFileHandler でファイル永続化（A-7 / ADR-0006）

### 背景

`backend/utils/logger.py` の `get_logger()` は `StreamHandler(sys.stdout)` のみでファイル永続化していなかった。`start.bat` から起動した Windows Terminal タブを閉じるとログ履歴が消失し、エラー後の事後調査やセキュリティ監査ログ（`Security: ZIP rejected ...` 等）の追跡が困難だった。[機能追加候補.md A-7](../計画/バックログ.md) として登録されていた項目を実装。

### 設計判断（[ADR-0006](../../design/基本設計/ADR/0006_backend-log-file-persistence.md)）

- **出力先**: `backend/data/logs/app.log`（`backend/data/` は既に gitignore 済み、追加設定不要）
- **ローテーション**: `RotatingFileHandler` で 10MB × 5 世代（最大合計 50MB）、UTF-8 エンコーディング
- **ハンドラ取り付け先**: root logger に 1 度だけ（複数モジュール logger による多重ファイルハンドル取得を回避し、Windows でのローテーション競合を防ぐ）
- **StreamHandler は維持**: 各モジュール logger に従来どおり直接付与し、開発時のターミナル可視性を失わない
- **代替案（TimedRotatingFileHandler / 構造化 JSON / セキュリティイベント別ファイル / 環境変数によるカスタマイズ）は ADR で却下理由を明記**

### 実装内容

- [backend/utils/logger.py](../../backend/utils/logger.py): `_ensure_root_file_handler()` を新設し、`get_logger()` 呼び出し時に root logger へ `RotatingFileHandler` を 1 度だけ追加。重複検知マーカー `_pic2pdf_app_log_handler` で多重登録を防止

  - `force=False`（既定）の場合、ローカルタイムの当日 0:00 を閾値として算出し
