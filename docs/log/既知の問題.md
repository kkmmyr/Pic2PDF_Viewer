# 既知の問題

## Linux週次復元serviceの共通backup lock反映はroot作業待ち

repositoryの`deploy/backup-restore-test.service`は`/opt/pic2pdf-viewer/.backup.lock`を取得する定義へ
更新済みだが、productionでsystemdが読む`/etc/systemd/system/backup-restore-test.service`はroot所有の
旧copyであり、2026-08-22時点ではlockなしの`verify-latest`を実行する。

- **影響**: 日次backupは配置先script経由でlock済み。週次復元試験も単独実行なら安全だが、日曜03:00と
  手動deployを意図的に重ねた場合は共通lockで直列化されない。deploy側はservice activeを二重確認するため、
  残るのは確認直後にtimerが起動する狭いraceである。
- **暫定運用**: 個人利用環境では日曜03:00を避けてdeployし、`backup-restore-test.service=inactive`を確認する。
- **解消条件**: root権限で更新unitを`/etc/systemd/system/`へ配置し、`systemctl daemon-reload`後に
  timerを再確認する。

## 停止中の旧 Windows サービス登録は管理者再登録待ち

`scripts/setup_service.bat` と設計書は uv workspace のルート `.venv` へ統一済み。
一方、現在の `Pic2PDFViewer` Windows サービスは停止・無効化された旧登録で、
`backend/.venv/Scripts/python.exe` を参照している。

- **影響**: Linux 本番と通常開発には影響しない。無効化されたサービスを
  そのまま再有効化した場合だけ旧環境へ依存する。
- **解消条件**: Windows サービスを再利用するとき、管理者として
  `scripts/setup_service.bat` を実行し、登録先がルート `.venv` であることを確認する。

## SearXNG 上流エンジンのレート制限によるサークル名自動登録失敗

> **2026-04-29 更新**: 根本解決策として DLsite / FANZA への直接 HTTP クエリを実装。
> `generated` ソースでは SearXNG より先にこれらを試みるようになった。SearXNG はフォールバックとして残存。

### 概要

サークル名自動登録機能を大量（目安: 20件以上）実行すると、SearXNG の上流検索エンジンが
レート制限・CAPTCHA ブロックを受け、全件「作者不明」が返るようになる。

### 現在の動作（2026-04-29 以降）

`generated` ソースは以下の 4 ステップで解決を試みる:
1. **DLsite 直接検索** — `dlsite.com/maniax` 検索ページを HTTP フェッチ → Gemma で抽出
2. **FANZA 直接検索** — `dmm.co.jp/dc/doujin` 検索ページを HTTP フェッチ → Gemma で抽出
3. **SearXNG site: フィルタ** — `site:dmm.co.jp OR site:dlsite.com` 絞り込み検索
4. **SearXNG 汎用** — `{title} サークル 同人誌` 汎用クエリ

直接検索が成功した場合 SearXNG は呼ばれないため、レート制限の影響を受けにくくなった。

### 症状（SearXNG フォールバックに降りた場合）

- `GET /api/meta/auto-fill/test` の `searxng_hit` が `false` を返す
- `unresponsive_engines` に以下のようなメッセージが並ぶ:

```json
"unresponsive_engines": [
  ["brave",      "一時停止: リクエストが多すぎます"],
  ["duckduckgo", "CAPTCHA"],
  ["karmasearch","一時停止: アクセスが拒否されました"],
  ["startpage",  "解析エラー"]
]
```

SearXNG の確認 URL: `http://localhost:8080/search?q=test&format=json`

### 根本原因

SearXNG は複数の外部検索エンジンに並列リクエストを送る。短時間に大量リクエストを行うと
各エンジン側でボットとみなされ、一時停止・CAPTCHA・アクセス拒否が発生する。

### 対処方法（SearXNG フォールバック使用時）

#### 1. 制限解除を待つ（数時間〜1日）

ブロックは時間経過で解除される。解除後に「作者不明」のエントリは自動的に再試行対象となる
（`overwrite=false` でも「作者不明」エントリは再処理される設計）。

#### 2. 待機時間の設定

`backend/services/auto_fill_service.py` の `AUTOFILL_REQUEST_DELAY_SEC`（現在 5 秒）を調整する。

#### 3. 分割実行

一度に全件処理せず、数十件ずつ日を分けて実行する。
