## 1. この文書の役割

この文書は、Kindle 自動撮影を実機で成立させる過程で判明した、次回の障害調査や
Kindle 更新時の再検証に必要な事実を集約する運用記録である。

- 現在守るべき仕様は要件定義・詳細設計を正本とする。
- Phase ごとの実装経緯と完了判定は実装計画を参照する。
- 本文書には、環境依存の観測値、失敗しやすい操作、切り分け順序、再撮影後の
  品質確認を記録する。
- 画像寸法や UI Automation の矩形は実測例であり、固定値の仕様ではない。

## 2. 実行前提

- Kindle アプリは起動済み、ログイン済みとする。エージェントは自動起動しない。
- Windows は画面ロックなしとし、撮影中はマウス・キーボードを操作しない。
- active capture job 中は、診断スクリプトや別プロセスの
  `KindleAppController.attach_running_app()`を実行しない。状態確認はcapture job APIと
  heartbeatだけを使い、画面キャプチャ・UI Automation診断・目視確認はジョブ完了後に行う。
- 初期版の処理単位は 1 冊で、複数冊の連続処理や並列撮影は行わない。
- 書籍を ASIN で一意に照合できない場合は、安全側に倒して撮影を開始しない。
- Windows は撮影と転送だけを担当し、Linux の正式画像領域へ直接書き込まない。

### 2.1 シリーズ単位で複数冊を取り込む運用

シリーズ全巻を取り込む場合も、capture agent の処理単位と安全境界は 1 冊のままとする。
複数ジョブをまとめて投入せず、次の順序を各冊について直列に繰り返す。

1. 購入カタログをシリーズ名で検索し、所有中の対象 ASIN を確定する。
2. `capture_state=captured` の書籍と active capture job がある書籍を除外する。
3. カタログの `book_type` は誤分類を含むため、書名・レーベルと利用者指定を照合して
   capture job の `source` を確定する。
4. 1 冊だけ capture job を作成し、`succeeded` と正式画像の登録を確認する。
5. 失敗時は次冊へ進まず、エラー原因と既存正式画像が不変であることを確認する。
6. 成功後に次の 1 冊を投入する。

この直列手順は`scripts/capture_kindle_series.py`で自動化する。既定はdry-runで、
`--apply`と期待総冊数を明示した場合だけ実行する。スクリプトはKindle画面へ接続せず、
capture job APIだけを監視するため、active job中のcontroller排他規則に抵触しない。
全対象を先にqueueへ入れる方式は、共通原因の失敗が後続巻へ連鎖し、一時停止も困難に
なるため採用しない。

2026-07-26 の「茉莉花官吏伝」シリーズ取り込みでは、利用者指定に基づき
`ビーズログ文庫`を `novel`、`プリンセス・コミックス`を `comic` とする。
初期棚卸しは小説 18 冊・漫画 12 冊の計 30 冊で、小説 1・2・3・18 巻の 4 冊は
取り込み済み、新規対象は小説 14 冊・漫画 12 冊の計 26 冊である。

2026-07-26 の一時停止時点では、小説 4・5・6・7 巻を追加登録済みで、
既存分と合わせて小説 1〜7・18 巻の 8 冊が取り込み済みである。小説 8 巻は
未ダウンロード状態からの初回試行が `download_failed`、再試行は撮影 10 画面の時点で
利用者指示により停止し、job を `failed / paused_by_user` とした。正式画像と
`meta2.db` は更新されていない。残りは小説 8〜17 巻の 10 冊と漫画 1〜12 巻の
12 冊、計 22 冊である。

シリーズ処理の途中で画面を確認する場合も、現在の1冊が`failed`または`succeeded`に
なってから行う。茉莉花官吏伝5巻では、先頭移動中に別controllerから診断画像を取得した
直後の撮影が3画面で終了した。3画面結果を隔離して、API監視だけで再撮影すると91画面を
完走したため、active job中の別controller接続を禁止する排他規則とした。

### 2.2 連続処理を一時停止する手順

1. 次冊の job を作成するバッチ監視プロセスを先に停止する。
2. capture agent を停止し、新しい job が claim されないことを確認する。
3. 実行中 job は agent 専用 state API で `failed / paused_by_user` とし、
   `captured_screens` を停止時点の値で保持する。
4. active / queued job が 0 件であることと、対象書籍が `not_captured` のままで
   正式画像パスを持たないことを API で確認する。
5. Windows の job 専用一時ディレクトリは正式成果物ではない。再開時は途中画像を
   継ぎ足さず、新しい job で表紙から撮り直す。

再開順序は、停止した小説 8 巻を新規 job で再実行した後、小説 9〜17 巻、
漫画 1〜12 巻とする。停止時の一時画像 10 枚は品質確認・正式登録の対象にしない。

2026-07-27の再開では、小説8〜17巻10冊と漫画1〜12巻12冊の計22冊を正式登録し、
既存8冊と合わせてシリーズ全30冊が`capture_state=captured`となった。完了時点で
`not_captured`、`capture_pending`、`multiple_links`はいずれも0冊である。新規成功jobの
画面数は小説86〜102画面、漫画82〜100画面で、固定枚数ではなく各書籍の終端判定を
完了条件とした。

途中では小説10巻と漫画8巻のKindleダウンロードが一度失敗したが、Kindle画面で
「ダウンロードに失敗しました。もう一度試してください」と正式コンテンツ未作成を
確認後、新規jobによる1回の再試行で回復した。Windowsロック中の漫画4巻は撮影前、
漫画6巻の初回は80画面撮影後のSamba公開renameで停止した。いずれも正式データを
変更せず、原因解消後に新規jobで表紙から再実行して登録した。

事前の効率調査では、直接先頭移動は小説約2.38秒、漫画約2.41秒（安定確認を含む）で、
すでに全体のボトルネックではなかった。ページ描画安定待ちを短縮すると中間フレームや
重複画像の混入リスクが増えるため変更せず、各冊の完了後に人手で次jobを作成していた
待ち時間だけを直列オーケストレーターで削減する。

バックグラウンドでcapture agentを起動した最初の小説8巻では、Windowsが
`SetForegroundWindow`を拒否してChromeが前面に残ったが、旧実装は成功確認をせず
背面にあるKindle書籍カードの座標をクリックした。結果としてKindleはライブラリ画面の
ままで、`kindle_ui_unavailable`により撮影前に安全停止した。以後はforeground threadへ
input queueを一時接続して前面化し、前面handleがKindleと一致した場合だけクリックする。

漫画6巻では80画面撮影後、Samba inbox上のjob専用ディレクトリを
`.partial`から`.ready`へrenameする瞬間だけ`WinError 5`となった。直前の複数jobは同じ
共有先へ正常公開でき、失敗後に`.partial`・`.ready`とも残らなかったため、恒常的な
権限不備ではなくSMBの一時的な共有違反として扱う。画像コピーとmanifest生成後の
renameだけを短いバックオフ付きで有界再試行し、失敗し続ける場合は従来どおり
`transfer_failed`で正式登録せず停止する。

## 3. Kindle 操作で得た知見

### 3.1 接続と UI Automation

- 対象プロセスは `Kindle.exe`、ウィンドウタイトルは `Kindle` として検出できる。
- 検索結果カードの `library-more-menu-<ASIN>` を利用すると、タイトルの表記揺れだけに
  依存せず ASIN 完全一致で本人確認できる。
- 表示倍率が異なるマルチモニター環境では、検索欄のUI Automation矩形と
  pyautoguiのクリック座標が一致せず、検索値が更新されない場合がある。
  2026-07-26の茉莉花官吏伝4巻では、以前の検索値`プリンセス・コミックス`が残ったまま
  18巻の「最後に読んだ本」カードだけを照合でき、4巻は`book_not_found`で安全停止した。
- 検索欄はUI Automationの`SetFocus`だけを使い、通常のキーボード入力後に
  `ValuePattern`を読み戻す。ASIN完全一致を確認できなければ候補探索へ進まない。
  Kindleを不安定化させた`SetValue`や`Click`は使用しない。
- UI Automation tree の全 descendants を約 100 ms 間隔で走査した調査では、
  完了後に Kindle が `ucrtbase.dll / 0xc0000409` で異常終了した。
  因果関係は断定できないが、通常処理では AutomationId を指定した `FindFirst` と
  低頻度ポーリングだけを使う。
- Kindle プロセスの消失は再接続で隠さず、`kindle_app_exited` としてジョブを失敗させる。

### 3.2 未ダウンロード書籍

- ダウンロードボタンの状態だけではなく、Kindle の正式コンテンツフォルダが安定した
  ことも確認してから読書画面へ進む。
- タイムアウトはダウンロード失敗と区別して利用者へ返す。
- 検証書籍 `茉莉花官吏伝 十八　青龍の睛を点ずる` で、未ダウンロード状態から
  ダウンロード完了を待って撮影へ進めることを確認した。

### 3.3 先頭移動とページ送り

- `go_to_start(source, direction)` は「位置に移動」でロケーション `1` を指定し、
  source 別のフッター表示を検証する。直接遷移または結果検証に失敗した場合は
  `positioning_failed` とし、数十画面を逆方向へ送る先頭探索は行わない。
- 漫画ではツールバー非表示時に `FooterLabelText` を取得できない。ツールバーや
  「位置に移動」ダイアログを表示した後は取得できる実測もあるが、常時存在しないため
  フッター文字列を通常の先頭判定の必須条件にできない。
- `ReadingArea` を縮小グレースケール化した画像差分でページ変化と端部を判定する。
  実測では本文ページ遷移の差分が平均 `6.82`、端部 chevron だけの変化が `0.38` で、
  本文変化と装飾変化を分離できた。
- Microsoft Store 版では画面端クリックより矢印キーの方が安定した。右綴じ・左綴じから
  決定した次ページ方向に対応するキーを利用し、撮影ループと先頭移動で同じ規則を使う。
- リフロー小説では、表紙の `Location 1` から本文1ページ目へ進む最初の遷移だけ、
  通常の左送りでは変化せず右キーで進む実機例がある。本文開始後は左キーで進むため、
  撮影ループは2画面目への遷移に限り、通常キーで無変化なら反対キーを1回だけ試す。
  終端では反対キーを試さず、既撮影ページへ戻ることを防ぐ。
- 最終ページでは同じ画像が返ることがあるため、無変化を複数回確認して終了する。
  一時的な描画遅延は直ちに終端とせず、再試行後に判定する。

#### 「位置に移動」による高速化（2026-07-26）

小説・漫画とも、ツールバー右端の `moreMenuButton` から「ページへ移動する」
（旧版は「位置に移動」）を開ける。
限定探索で確認した UI Automation 要素は次のとおり。

| 用途 | AutomationId / Name | 操作方式 |
|---|---|---|
| その他メニュー | `moreMenuButton` / `もっと` | control 矩形を通常クリック |
| メニュー項目 | `btn-popover-menu-item` / `ページへ移動する`（旧版は `位置に移動`） | Name も併用して限定探索し、通常クリック |
| 入力欄 | `go-to-page-input` / `ページ番号入力`（旧版は `ロケーション番号入力`） | `SetFocus` 後、通常のキーボード入力 |
| 確定 | `modal-confirm` / `ページへ移動する`（旧版は `位置に移動`） | control 矩形を通常クリック |
| 結果確認 | `FooterLabelText` | 読み取り専用 |

入力対象は現行版では**ページ番号**、旧版では**ロケーション番号**として
表示される。ただし、どちらも撮影画像の連番とは一致しない。`SetValue` /
UI Automation `Click` はKindleを不安定化させたため使用しない。
2026-07-26時点の実機では、同項目のName変更に加えてpopoverがKindle本体とは別の
UI Automation rootへ公開された。デスクトップからNameとAutomationIdを限定探索し、
control中心がKindleウィンドウ内にあることを確認すれば安全に取得できる。
同版では読書画面の `backButton` が座標クリックを受け付けない実機例もあるため、
本人照合済みcontrolへ `SetFocus` した後、通常のEnterキーでライブラリへ戻る。

実測結果:

| source / 表示 | 移動前 | 入力 | 移動後 | 確認時間 |
|---|---:|---:|---:|---:|
| リフロー小説・単ページ | `Location 2748 of 3304・82%` | `1` | `Location 1 of 3304・0%`、表紙 | 約 0.12 秒 |
| 固定レイアウト漫画・2ページ | `Location 150 of 169・88%` | `1` | `Location 2 of 169・0%`、表紙 | 約 0.17 秒 |

上表はダイアログ確定からフッター更新までの時間である。実装後の
`go_to_start(source, direction)`を、書籍オープン・レイアウト確定後の実機で再試験すると、
読書画面安定待ちと結果検証を含め、小説`2748 → 1`は約2.38秒、
漫画`150 → 2`は約2.41秒で完了した。

漫画は入力値 `1` と移動後の表示値が一致しない。右綴じ・2ページ表示の先頭では
表紙が表示されても `Location 2` となるため、`Location 1` 完全一致を成功条件に
してはならない。小説と漫画の操作部品は共通だが、先頭確認条件を source 別にする。

同じリフロー小説でも、直接遷移後のフッターが
`Location 1 of 2959・0%` または `ページ1/233・0%` となる実機例がある。
実機で後者は表紙ではなく本文側の2画面目であることを確認した。この場合だけ、
ダイアログ確定後に `ReadingArea` 中央へフォーカスを戻してから、利用者が指定した
次ページ方向と逆のキーを1回送り、`Location 1 ...・0%` を再確認して表紙とする。
漫画にはこの補正を適用しない。
ページ本体の切替後も `FooterLabelText.Name` の更新が数秒遅れる実機例があるため、
補正後は追加のページ送りをせず、同じフッター control の更新だけを有界回数待つ。

`go_to_start(source, direction)` は `set_page_layout(source)` の後に、
「位置に移動」で `1` を指定して読書画面の安定を待つ。小説は
`Location 1 ...・0%` を表紙として確認し、`ページ1/N・0%` の場合は上記の
1回だけの補正後に同じ表紙条件を確認する。漫画は表紙表示と `0%`
（実測では `Location 2`）を確認する。メニュー、入力欄、直接遷移結果、
補正後の表紙を取得または検証できない場合は `positioning_failed` として停止する。

## 4. 表示レイアウトと撮影範囲

### 4.1 共通

- Microsoft Store 版 Kindle は F11 中にページ送りすると本文が白画面のままになる
  場合があるため、F11 ではなくウィンドウ最大化を使う。
- 最大化後に `ReadingArea` を取得し、画面座標から Kindle ウィンドウ相対座標へ変換する。
- 最大化により読書領域からキーボードフォーカスが外れる実機例があるため、
  撮影矩形の確定後に `ReadingArea` 中央を通常クリックしてフォーカスを戻す。
  このクリックはページ送り用の端部ではなく、ツールバー表示切替領域で行う。
- 固定クロップ値は controller を使わない手動・互換経路だけのフォールバックとする。
  自動 agent は UI Automation の矩形を取得・検証できなければ撮影を開始しない。
- ジョブ開始時に `source` に対応するレイアウトを毎回選択し、前回読書時の設定を
  引き継がない。

### 4.2 漫画

- `aaMenuButton` から `aaOption-Split` を選択し、`ToggleState` で 2 ページ表示を確認する。
- `ReadingArea` の上下全体を保存する。横幅は先頭の単ページ幅だけに固定せず、
  後続の見開き 2 ページ分を含む安全幅を確保する。
- 表紙や奥付の単ページは安全幅内で中央配置される。単ページの左右に余白があることは
  欠陥ではなく、後続見開きの欠落を防ぐための意図した挙動である。
- 検証漫画は 85 画面、全画像 2936×2064 となり、通常見開きの外側余白中央値は
  左 15 px、右 17 px だった。

### 4.3 小説

- 固定レイアウトで `aaOption-Single` が存在する場合は選択して状態を確認する。
- リフロー型小説ではページ数 option 自体がなく、`フォント-item`、フォントサイズ、
  余白、間隔だけが表示される。この構成を単ページ表示として受け入れる。
- 横方向は `ReadingArea` の左右端を使う。
- 縦方向は `TopChrome.bottom` から `Footer.top` までとし、上部書名と下部の
  `ページ X/Y・進捗 %` を保存画像から除外する。
- `TopChrome` または `Footer` を取得できない、または包含関係が不正な場合は
  `kindle_ui_unavailable` として撮影前に停止する。自動 agent は `ReadingArea`
  全体へ暗黙にフォールバックしない。固定 105 px の下マージンは本文を切るため
  正本にしない。
- 検証小説 2 冊は 91 画面・92 画面、全画像 3516×1940 となり、本文下端を残しながら
  Kindle の上下 UI を除外できた。

## 5. 再撮影後の公開とブラウザーキャッシュ

### 5.1 判明した問題

画像は `Cache-Control: public, immutable, max-age=2592000` で配信される。
同じ書籍ディレクトリ、同じ `009.png` のような名前へ再撮影結果を置換しただけでは、
ブラウザーが最大 30 日間、置換前の画像を表示し続ける。

漫画 P.9 が単ページに見えた事例では、次を確認した。

1. サーバー上の現行 `009.png` は正常な見開きだった。
2. 利用者の画面は、置換前データの単ページ内容と一致した。
3. 現行データを再撮影しても解決せず、画像 URL の世代を変える必要があった。

### 5.2 現在の対策

- `GET /api/books/{path}/images` は各画像の `st_mtime_ns` を `v` クエリへ付与する。
- 小説一覧の `thumbnail_url` は `001.png`、未生成時は書籍ディレクトリの
  `st_mtime_ns` を `v` として返す。
- `NovelReaderPage` は一覧で受け取った `v` を同じ書籍の全ページへ引き継ぐ。
- 小説の世代番号は、正式配置で `001.png` を含む画像列全体を置換することを前提とする。
- 未 OCR 書籍で `page_count=null` の場合も、画像への HEAD 探索でページ数を確定する。

表示不良を報告された場合は、再撮影を始める前に、サーバー上の現行画像、API が返す
`v`、ブラウザーの実際の画像 URL の順で照合する。

## 6. 成果物の転送と置換

1. Windows のジョブ専用一時ディレクトリへ連番 PNG と manifest を作る。
2. Samba inbox へ `.partial` 名で転送する。
3. 転送完了後だけ `.ready` へ原子的に rename する。
4. Linux で manifest、枚数、連番、安全なパスを検証する。
5. 既存正式データを世代バックアップへ退避する。
6. 新しい画像ディレクトリを正式名へ切り替える。
7. 正式配置成功後だけ `meta2.db` の ASIN とジョブ状態を更新する。

Windows 側の転送失敗、Linux 側の検証失敗、正式配置失敗では、既存正式画像と
`meta2.db` を変更しない。2026-07-26 の小説再置換前データは次へ退避した。

`/opt/pic2pdf-viewer/data/.capture-replacement-backup/20260726-092136`

バックアップを削除する時期は自動化せず、一定期間の閲覧・OCR確認後に運用判断する。

## 7. 品質確認手順

### 7.1 画像列の機械確認

- 期待枚数と実ファイル数が一致する。
- `001.png` から最終番号まで連番欠落がない。
- 全画像の寸法が同じである。ただし寸法値そのものは環境依存とする。
- SHA-256 が完全一致する重複画像がない。
- 意図しない全面白画像がない。
- 表紙、本文中盤、最終ページを目視する。

### 7.2 source 別の目視確認

漫画:

- 通常ページが最初から見開きである。
- 左右ページの外側が切れていない。
- 中央の綴じ目が不自然に重複していない。
- 表紙・奥付の単ページが中央に収まる。

小説:

- 本文の最上部と最下部が切れていない。
- 上部に Kindle の書名がない。
- 下部にページ数・進捗率がない。
- 表紙や挿絵を固定クロップで欠損していない。

### 7.3 公開後の確認

- API の画像 URL に `v` が含まれる。
- 同じブラウザーで再読込し、旧ページと新ページが混在しない。
- 漫画はページ数と見開き表示を確認する。
- 小説は OCR 未実施でも画像列探索により総ページ数を表示できる。
- 問題時に戻せるバックアップの枚数を確認する。

### 7.4 OCRへの引継ぎ

- 撮影完了とOCR完了は別の状態として扱う。購入カタログで`captured`でも、
  小説DBの`ocr_done_at=null`なら文字起こしは未完了である。`is_indexed`は
  `indexed_at IS NOT NULL`と同義とし、Embedding構築完了だけを表す。
- シリーズ撮影後は、今回追加した書籍名を固定して1冊ずつOCRへ投入する。
  対象なしの全件OCRは、以前から画像だけ存在する別巻も巻き込むため使用しない。
- 茉莉花官吏伝の2026-07-27撮影分では小説8〜17巻の10冊が対象であり、
  撮影済み全18巻や未OCR書籍全体を対象にしない。
- OCR完了後もQA承認前のrunは正式本文ではない。画像のみ保持する目次・挿絵・
  奥付・広告を分類し、本文ページの必須QAと必要なCodex補正を終えてから公開する。
- 実行結果は10冊914ページ、本文806ページ、画像のみ108ページ、Codexによる
  原画像照合・補助候補採用15ページで、全runを`completed / approved`として公開した。
- 終端位置を使う自動分類だけでは、本文・あとがきを奥付や広告と誤認し得る。
  今回は14巻p79、16巻p95、17巻p97を画像確認で本文へ戻した。終端付近の
  非本文候補に長いOCR結果がある場合は、索引除外前に原画像を確認する。
- 文字起こし公開後、8〜17巻のチャンク・Embeddingを`rebuild`し、10冊すべての
  `indexed_at`更新を確認した。検索は8巻の「赤奏国 コウマツリカ」がp80ほか、
  17巻の「茉莉花」がp12ほかへ命中した。
- Embeddingの実測は、サーバーCPUで8巻が約8分14秒、Windows CPUで9巻が
  約1分32秒、Windows RTX 5070で10巻が約12秒、11〜17巻が各約6〜8秒だった。
  リモートOllamaへ切り替える場合、`NOVEL_DB_OLLAMA_BASE_URL`だけでは
  サーバー既定の`NOVEL_DB_EMBED_NUM_GPU=0`が送信されてCPU実行になる。
  GPU利用時は`NOVEL_DB_EMBED_NUM_GPU=99`も一時設定し、完了後は両設定を戻す。
- 本番Qwen llama-serverが未起動のため、要約・人物抽出を含む`full_build`は実行せず、
  `rebuild`で検索索引だけを構築した。要約・人物抽出は正式本文・検索索引の公開を
  ブロックしない独立工程として扱う。

## 9. Kindle 更新時の再検証

Kindle 更新後は、いきなり正式撮影せず `diagnose_new_kindle.py` と短い書籍で次を確認する。

1. プロセス名、ウィンドウタイトル、主要 AutomationId が取得できる。
2. ASIN 検索と候補一意性を確認できる。
3. ダウンロード済み・未ダウンロードを区別できる。
4. `ReadingArea`、`TopChrome`、`Footer` の矩形が妥当である。
5. 漫画の `aaOption-Split` と小説の表示設定を選択できる。
6. 最大化後にページ送りしても白画面にならない。
7. 直接先頭遷移が source 別のフッター条件を満たし、小説の `ページ1/N・0%` だけは
   1回戻した後に `Location 1・0%` となる。直接遷移を失敗させても連続ページ送りを
   開始せず `positioning_failed` で停止する。
8. 数ページの試験画像で上下・左右の欠落がない。

AutomationId や矩形取得が変わった場合は固定座標を先に増やさず、診断出力と
UI Automation tree の差分を記録してから controller の locator を更新する。
