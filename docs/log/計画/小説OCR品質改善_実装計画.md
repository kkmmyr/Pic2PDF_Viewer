# 小説OCR品質改善 実装計画

> 状態: Phase 1〜5f完了、Phase 5g追加学習は単体不合格、新規2シリーズの合議CER 0.44%・総合ゲート未達
> 作成日: 2026-07-26
> 対象: Kindle小説画像のOCR、品質判定、Windows実行エージェント、Full Build

## 1. 目的

Kindle自動撮影で得た小説画像を、文字列・縦列の欠落を見逃さずにOCRし、
品質確認後だけ `novel.db` と検索インデックスへ公開する。

処理が最後まで動くことと文字が正しいことを別の完了条件として扱う。
OCR失敗またはQA未承認の書籍は、既存の公開本文とインデックスを変更しない。

## 2. 2026-07-26 基準実測

対象:

- `茉莉花官吏伝 十八　青龍の睛を点ずる (ビーズログ文庫)` — 91画面
- `十三歳の誕生日、皇后になりました。10 (ビーズログ文庫)` — 92画面

上下のKindle UIを除外した正式撮影画像と同一SHA-256のローカル複製を使い、
Surya OCR 2 workerを1冊ごとに新規起動して全183画面を処理した。

| 書籍 | 合格 | 失敗 | 失敗率 | 再試行画面 |
|---|---:|---:|---:|---:|
| 茉莉花官吏伝 十八 | 59 | 32 | 35.2% | 42 |
| 十三歳の誕生日、皇后になりました。10 | 47 | 45 | 48.9% | 56 |
| 合計 | 106 | 77 | 42.1% | 98 |

同一画像の単独実行と全冊実行でも文字列が変わった。
茉莉花20画面は単独952文字、全冊860文字で、双方が品質フラグなしの合格だった。
十三歳46画面はSurya合格結果で人物名 `莉杏` を `莉香` と誤認し、
短い縦列 `らなくていいのだ。` を欠落した。
Surya不合格後のyomitoku結果はこの2点を正読したが、
全9block中1blockのconfidenceが0.184だったためページ全体が不合格になった。

この実測を、以下の全Phaseで回帰基準として使う。

## 3. 禁止事項

- 品質未承認のOCR本文を `books` / `pages` / `pages_fts` / LanceDBへ公開しない。
- Windowsから本番SQLiteファイルをネットワーク共有で直接更新しない。
- OCR結果をLLMで原画像照合せず自動修正し、修正後文字列だけを正本にしない。
- キャプチャPNGをOCR前処理や再試行で上書きしない。
- 表紙・挿絵・奥付の低文字量を理由に本文の品質条件を緩和しない。

## 4. Phase 1 — worker安定化

### 実装

1. worker所有のllama-serverを有限ページ数で区切って再起動する。
2. 連続Surya不合格または移動窓の不合格率超過でも早期再起動する。
3. `ocr_page_results` の合格済み画像SHA-256を再利用し、不合格・未処理だけを再開する。
4. 進捗に書籍名、画面番号、総画面数、試行番号、処理段階、server世代を含める。
5. serverの起動・再起動・終了理由を監査ログへ残す。

### 受入条件

- 模擬workerテストで、ページ上限と連続不合格の双方から再起動される。
- 再起動後も各入力画面の結果が1件だけ出力され、欠番・重複がない。
- worker異常終了後、合格済みSHA-256を再利用して残りだけ再実行できる。
- 外部管理serverへ接続した場合は、workerが無断停止しない。

## 5. Phase 2 — 品質ゲートと無料OCR候補

### 5.1 判定改善

- yomitokuは全blockの最小confidenceだけで棄却せず、中央値、低位分位、
  低confidence blockの文字比率、構造検査、Suryaとの一致率を併用する。
- 原画像の縦列候補とOCR bboxの対応から、短い独立縦列の欠落を検出する。
- 同一画像の再読結果が大きく異なる場合は `unstable_text` として不合格にする。
- 人物名・書名辞書は誤り検出とQA対象抽出に利用するが、辞書だけで本文を自動置換しない。

### 5.2 無料・ローカル候補の同一画像ベンチマーク

候補はそれぞれ隔離環境へ導入し、同じ20画面以上を処理する。

| 候補 | 採用候補の役割 | 一次資料 |
|---|---|---|
| PaddleOCR PP-OCRv5 / PaddleOCR-VL | 縦書き対応の主系または第三判定 | [公式文書](https://paddlepaddle.github.io/PaddleOCR/main/en/index.html) |
| NDLOCR-Lite | 日本語図書向けCPU補助系 | [NDL公式](https://github.com/ndl-lab/ndlocr-lite) |
| manga-ocr | 列・小領域単位の日本語再読 | [公式リポジトリ](https://github.com/kha-white/manga-ocr) |
| Tesseract `jpn_vert` | 独立した軽量比較基準 | [公式学習データ](https://github.com/tesseract-ocr/tessdata) |

VLM系は文脈補完による幻覚を生じ得るため、単独結果を無条件採用しない。
各エンジンのlicense、モデルサイズ、RTX 5070 12GBでの速度、文字誤り率、
列欠落、固有名詞精度、再現性を記録する。

### Phase 5a進捗（2026-07-26）

- ページ種別の保管・安全側の自動提案・QA手動確定と、本文以外の索引除外を実装済み。
- 正解コーパスの`draft` / `verified`管理、画像SHA確認、ページ別・加重CER評価を実装済み。
- 2冊から20画面を下書き登録する。OCR本文は比較用であり、原画像から人手転記して
  `verified`にするまでは品質指標へ含めない。
- 20画面の人手正解確定後、同一SHA画像で無料OCR候補を再比較し、Phase 5公開可否を判断する。

### 2026-07-26 予備比較（6画面）

本番依存へ追加せず、`%LOCALAPPDATA%\Temp\pic2pdf-ocr-free-benchmark-20260726`
以下の隔離venvで、前付け・通常本文・挿絵混在・既知欠落画面を処理した。
この段階は正解文字列を固定する前の候補絞り込みであり、CER受入試験ではない。

| 候補 | 実測 | 判定 |
|---|---|---|
| NDLOCR-Lite 1.2系 | CPUで0.5〜3.6秒/画面。既知46画面の短い列は取得したが、人物名誤読、文字混入、重複がyomitokuより多い | 軽量な第三判定候補。主系にはしない |
| manga-ocr 0.1.16 | ページ全体・本文領域とも原文にない自然文を生成 | 全ページOCR用途では不採用 |
| PaddleOCR PP-OCRv5 | 短い列を検出。小書き「っ」の連続脱落と句読点欠落があり、Windows CPUで約4分/画面 | 列存在確認の診断候補。主系にはしない |
| Tesseract 5.4 + `tessdata_best/jpn_vert` | 既知46画面を約1秒で全列取得。数文字の誤読はあるが文章生成型の幻覚は見られない | 無料の軽量第三判定として有望 |

現段階の主候補はSurya + yomitokuの相互照合であり、
Tesseract `jpn_vert`を列欠落・文字数差の第三検査へ追加する方向で20画面評価を続ける。

2026-07-26の正式画像による追加確認では、通常本文8画面目に対する
Tesseract `jpn_vert`も「天庚国」「覇権」「采青国」「優娜」等を複数誤読した。
Suryaより精度が低く、第三エンジンの一致だけで本文を自動確定する用途には採用しない。
文字領域・列数・文字数差を安価に検出する補助判定に用途を限定する。

### 受入条件

- 本文標本20画面以上で文字誤り率（CER）0.5%以下。
- 縦列の全欠落0件。
- 指定した書名・著者名・主要人物名は完全一致。
- 同一画像3回の正規化文字列一致率99.5%以上、文字数差1%以下。
- 不一致時に原画像、各エンジン本文、信頼度、bboxを追跡できる。

## 6. Phase 3 — QA承認

OCR完了とQA承認を別状態として管理する。

- 前付け全画面
- 品質フラグ付き全画面
- 各書籍の先頭・中盤・終盤本文
- 挿絵と本文が混在する画面
- 固有名詞を含む画面

を原画像と照合する。QA未承認ではFull Buildを投入できない。

受入結果には、対象画像SHA-256、OCR/model revision、engine構成、
サンプル正解文字列、CER、列欠落数、承認者・日時を保存する。

## 7. Phase 4 — Windows OCRエージェント

本番Linuxをジョブ・DB・画像の正本、Windows GPU端末を推論実行者とする。
Kindle capture agentと同様に共有トークンで認証するが、SQLiteを共有しない。

1. Windows agentが本番APIから1ジョブをclaimする。
2. APIからmanifestと画像を取得し、画像SHA-256を検証する。
3. 画面単位のOCR結果とheartbeatをAPIへ返す。
4. 本番側が `ocr_page_results` へ保存し、全画面合格後もQA承認待ちにする。
5. 再claim時は合格済みSHA-256を除いたmanifestを返す。

APIはディレクトリ任意指定を受けず、job IDと登録済みmanifestだけを扱う。
トークンをログ、レスポンス、ジョブ詳細へ出力しない。

## 8. Phase 5 — 2冊の正式登録

1. 正式画像のSHA-256と基準実測画像の一致を確認する。
2. 改善workerで2冊を再OCRする。
3. Phase 2の機械受入とPhase 3の目視QAを完了する。
4. OCR本文をトランザクションで公開する。
5. `full_build` でchunks、embedding、検索索引を生成する。
6. 書名・人物名・本文引用の検索と、検索結果から原画像を開く導線を確認する。

### 最終完了条件

- 両書籍で未解決の本文失敗0件、列欠落0件。
- `ocr_done_at` と `indexed_at` が設定される。
- `莉杏` 等の指定人物名と5件以上の本文引用を検索できる。
- 検索結果の画面番号と原画像が一致する。
- 失敗時に旧公開本文・索引が保持される。

### 2026-07-26 本番実行結果

Windows OCRエージェントから本番APIを利用して全画面を処理し、
失敗ページだけを最大3回再実行した。ページ結果は本番DBへチェックポイント保存したが、
品質条件未達のため本文公開とFull Buildは実行していない。

| 書籍 | 最終状態 | 合格 | 未解決 | 主な結果 |
|---|---|---:|---:|---|
| 茉莉花官吏伝 十八 | `awaiting_qa` | 91/91 | 機械失敗0 | 69画面で`external_crosscheck_unavailable`。QA必須73画面 |
| 十三歳の誕生日、皇后になりました。10 | `failed` | 88/92 | 4 | 4・5・86・88画面が3回とも`cross_engine_disagreement` |

再試行の推移:

- 茉莉花官吏伝: 初回86/91、2回目90/91、3回目91/91。
- 十三歳: 初回86/92、2回目88/92、3回目も88/92。

原画像照合で次を確認した。

- 茉莉花官吏伝8画面目は、Suryaが「茉莉花」を「暗菜莉花」と誤読した。
  yomitokuも人物名を複数誤読し、中央値confidence 0.770、
  文字数加重平均0.559、低confidence文字比率43.7%、
  Suryaとの正規化一致率0.820であった。現行閾値による停止は妥当である。

- `external_crosscheck_unavailable`は単なる監査ノイズではない。
  通常本文でもyomitokuの固有名詞誤読・列断片化・低confidenceが発生しており、
  これをQA対象外へ緩和してはならない。

### Phase 5の初回判定と残作業（改善前）

Phase 5は**未完了**とする。run 1はQA待ち、run 2は失敗状態に保持し、
`books` / `pages` / `pages_fts` / LanceDBへ公開しない。

次の順で改善する。

1. 通常本文、目次、表紙・挿絵、漢文、販促を含む20画面以上の正解コーパスを固定し、
   全エンジンのCER、固有名詞再現率、列欠落を同一条件で測定する。
2. ページ種別を`narrative` / `toc` / `illustration` / `colophon_or_ad`へ分類し、
   非本文ページは閲覧用に保持しつつ検索索引対象から除外できるようにする。
3. 固有名詞辞書は自動置換ではなく、原画像との不一致検出とQA優先度付けに使う。
4. 無料候補は、Tesseractを列・文字数検出、NDLOCR-Liteを独立比較に限定する。
   GLM-OCR、PaddleOCR-VL等の新しい小型VLMは隔離環境で正解コーパスへ評価し、
   既存主系を上回った場合のみ採用を検討する。
5. 受入条件を満たした構成でrun 1・2を再処理し、目視QA後に初めて公開・Full Build・
   検索確認を行う。

### Phase 5a — 正解コーパスとページ種別

1. 正式2冊から本文・前後付け・既知不一致を含む20画面を画像SHA付きで登録する。
2. OCR本文を初期表示用draftとして保持し、人手正解と混同しない。
3. QAでページ種別を確定し、`narrative`だけを検索・RAG派生データへ流す。
4. verified標本のページ別CERと加重CERを継続表示する。
5. 初期20件の登録、既知4種別の確認、索引除外テストを完了する。

#### 2026-07-26 完了結果

正式画像とSHA-256が一致する20画面を原画像から照合し、20/20件を`verified`にした。
全体の加重CERは16.42%だったが、ページ種別・レイアウト難度による差が大きく、
全体値だけを通常本文の品質指標には使えない。

| 評価範囲 | 画面数 | 加重CER | 主な課題 |
|---|---:|---:|---|
| 本文（序章の全幅要約・挿絵混在を除く、漢文を含む） | 7 | 2.24% | 固有名詞、似た漢字、約物、漢文の読み順 |
| 通常散文（全幅要約・挿絵混在・漢文を除く） | 4 | 1.82% | 固有名詞、似た漢字、約物 |
| 本文全体 | 9 | 14.38% | 序章の列欠落、挿絵混在画面の本文全落とし |
| 目次 | 4 | 70.00% | 読み順、重複、装飾罫線の文字化 |
| 挿絵・表紙 | 4 | 61.24% | 文字領域の見落とし、装飾文字 |
| 奥付・広告 | 3 | 0.87% | 記号差 |

特に茉莉花38画面は挿絵と本文の混在によりCER 94.40%、
十三歳86画面は漢文・書き下し・ルビの読み順によりCER 22.64%だった。

### Phase 5b — ページ種別別ベンチマーク

1. 正解コーパスAPI/UIで、全体値に加えてページ種別別の件数・文字数・加重CERを表示する。
2. Surya、yomitoku、Tesseract等の候補を同一SHA画像・同一正解文字列で比較する。
3. 通常本文、挿絵混在、目次、漢文、広告を別集計し、用途ごとの採否を決める。
4. 全体CERの改善だけで候補を採用せず、通常本文の列欠落0と固有名詞再現を必須にする。
5. 挿絵混在・構造化ページは、文字領域検出と読み順の改善を通常本文モデル変更から分離して評価する。

比較の再現には `scripts/maintenance/benchmark_ocr_ground_truth.py` を使用する。
同スクリプトはAPIからverified標本と画像を取得し、取得時SHA-256を検証したうえで、
現行OCR本文、Tesseract `jpn_vert`、または既存yomitoku workerを同じCER定義で集計する。

| 評価範囲 | 画面数 | 現行Surya系 | yomitoku | Tesseract `jpn_vert` |
|---|---:|---:|---:|---:|
| 全体 | 20 | 16.42% | **11.51%** | 57.20% |
| 通常散文 | 4 | **1.82%** | 4.55% | 8.46% |
| 全幅要約 | 1 | 19.19% | 11.22% | **8.03%** |
| 本文＋挿絵の混在 | 3 | 38.28% | **10.71%** | 151.74% |
| 漢文・書き下し | 1 | **22.64%** | 57.23% | 67.30% |
| 目次 | 4 | 70.00% | **50.00%** | 141.54% |
| 挿絵・表紙 | 4 | **61.24%** | 64.61% | 340.45% |
| 奥付・広告 | 3 | **0.87%** | 21.68% | 65.32% |

全体値だけならyomitokuが最良だが、通常散文と漢文は現行Surya系が優位であり、
主エンジンを一律に置換しない。yomitokuの改善効果は本文＋挿絵の混在ページに集中する。
Tesseractは挿絵の網点・輪郭を大量の文字として誤認するため、全画面OCRには採用せず、
文字領域を限定した後の列欠落・文字数確認にのみ利用候補として残す。

次の実装対象は、意味上のページ種別とは別にレイアウト特性
（通常散文／全幅要約／本文＋挿絵／漢文）を判定し、
本文＋挿絵ではyomitoku結果を比較候補へ必ず含めることである。

### Phase 5c — レイアウト別選択とCodex補助QA

1. `layout_type`を`unknown` / `normal_prose` / `full_width` /
   `mixed_illustration` / `structured` / `image_only`で保存し、
   意味上の`page_type`と分離する。
2. Surya・yomitoku両候補を保持する。本文＋挿絵はyomitokuを優先候補にし、
   通常散文はSuryaを優先するが、自動選択だけで公開確定しない。
3. QA画面で両候補の選択と原画像照合済み補正文を保存できるようにする。
   現時点の無料・ローカルOCRで基準未達のページはCodexが画像を確認し、
   補正文を作成する。機械OCR原文は監査用に保持する。
4. 目次・表紙・挿絵・奥付・広告は、明示的に非本文へ分類・承認した場合、
   OCR失敗でも画像のみ公開できるようにする。本文は機械合格または
   非空の画像照合済み補正文を必須とする。
5. 固定20画面はレイアウト別CERを再集計し、機械OCR値とCodex補正後の
   公開正本品質を区別して報告する。2冊のQA完了後にのみ正式公開、
   Full Build、索引除外、検索と画像参照を確認する。
