## 1. 管理先

| 判定 | 管理先 |
|---|---|
| ユーザーから見た振る舞いが増える・変わる | [バックログ](バックログ.md) |
| 外部挙動を変えない内部構造改善 | 本計画 |
| 依存・インフラ・性能特性を変更する | 本計画の「技術メンテナンス」 |
| 完了・スキップ・撤回済み | [リファクタリング履歴](../../archive/リファクタリング履歴.md) |

新機能、API・DBスキーマ・品質基準の仕様変更は本計画へ混在させない。
行数だけを理由にした分割、2箇所の類似だけを理由にした先回り共通化も行わない。

## 2. 技術メンテナンス

### 現在の実行順

本表は管理先を統合しない。機能追加は[バックログ](バックログ.md)、内部改善と
技術メンテナンスは本書を正本としたまま、依存関係だけを横断して示す。

| 順位 | 正本 | 作業 | 次へ進む条件 |
|---|---|---|---|
| P0 | TM-3 | CI・依存監査・開発runtimeの再現性を回復する | clean checkoutの全CI jobがgreen |
| P1 | バックログ B-37 | LanceDB ICUのshadow観測・未調整holdout・本番切替判断を閉じる | rollbackを含む本番受入完了 |
| P2 | TM-4 | 設計ドリフトとバックログ状態を解消する | 設計・実装・計画の再監査で差分0 |
| P3 | バックログ B-32 | キャプチャ品質holdoutと警告運用を完了する | 人手label付きprecision / recallと運用判断を記録 |
| P4 | バックログ B-35 / B-36 | OCR・生成文QAを停止条件付きで再評価する | 固定gate合格、またはtimebox終了を明示 |

P0〜P2の間は、新しいLLM checkpointの導入、長文一括生成の拡大、新規大型機能へ
着手しない。現状の失敗要因はメモリ容量よりも主体・時系列・根拠帰属とdelivery
gateの再現性にあるため、モデル探索を先行させない。

### TM-3. CI・依存監査・開発runtimeの再現性回復 — P0

**起票理由**: 2026-08-22の`master`監査で、GitHub Actionsはfrontendの
`npm ci` lock不整合とbackend dependency auditで停止した。後段をローカルで
再現すると、保守script未分類9件、Python format差分1件、basedpyright 82件、
Windows COM依存Kindle testの非Windows collectionを確認した。MacのNode 26では
Node組込みWeb Storageとjsdomが競合してVitest 61件が一括失敗した一方、Node側の
experimental Web Storageを無効化すると1,083件が合格したため、製品回帰ではなく
未固定runtimeの問題として扱う。

**作業単位**:

1. Node 22を開発・CIの正規versionとしてrepositoryに固定し、Node 22 + npm 10の
   clean checkoutで`npm ci`可能なlockfileを生成する。依存変更以外では
   `npm install`によるlockfileの暗黙更新を行わない。
2. `npm audit`の修正版があるtransitive依存とdirect依存を、`--force`なしで更新する。
   PythonはONNXの修正版互換性を確認し、PyTorch / CUDA固定を一括更新しない。
   例外を維持する場合はadvisory alias、用途、露出、期限を監査正本へ記録する。
3. Ornith評価器とOCR holdout scriptを`maintenance_assets.json`へ一意に分類し、
   owner・用途・再評価日を持たない一時資産を残さない。
4. format差分を解消する。basedpyrightは生成migrationを含めて原因別に直し、
   repository全体を無期限excludeすることでgreen化しない。
5. Kindle testをOS非依存ロジックとWindows COM実機境界へ分ける。Ubuntu jobで
   Windows専用moduleをcollectionせず、Windows側の契約を削除して通過させない。
6. backend coverage、common LLM、frontend type / Vitest / build、docs、gitleaksを含む
   GitHub Actions全jobをclean commitでgreenにする。

**完了条件**:

- clean checkoutで`uv sync`と`npm ci`が成功する。
- `npm audit`とproject dependency auditが、未記録の脆弱性0件で成功する。
- C901、code size、OpenAPI、import boundary、maintenance asset、format、basedpyrightが成功する。
- backend、platformに応じたKindle、common LLM、frontend、docsの全CI jobが成功する。
- Node 22でローカル手順とCI手順が一致し、新しいNodeでの既知非互換を運用書へ記録する。

**中止・分割条件**: PyTorch / CUDAのmajor更新、OCR model再変換、公開API・DB・SSE変更が
必要になった場合はTM-3から分離し、現行CIを回復できる最小変更を先に完了する。

### TM-4. 設計ドリフトとバックログ状態の解消 — P2

**起票理由**: 横断監査でP1不整合はなかったが、frontend componentからのHTTP直接呼出し2件と、
旧source名・Tailwind v4設定位置の設計差2件を確認した。またC-8はPlaywright 8 scenarioが
実装済みなのに未着手欄へ残り、B-28は技術実装済みで主観受入だけが残る。

**対象**:

- `AmazonImportButton.tsx`と`ToolsMenu.tsx`のHTTP処理をfeature / hook境界へ移し、
  OpenAPI生成型を正本にする。
- OCR設計書の旧`generated` sourceを現行3値へ直す。
- z-index tokenの正本を存在しない`tailwind.config.js`からTailwind v4の`index.css`へ直す。
- C-8を実装済み履歴へ移し、B-28を「技術実装済み・主観受入待ち」として残作業を限定する。

**完了条件**: docs-cross-check、OpenAPI型、import boundary、frontend test / build、
`check_docs.py`、ファイルマップcheckが成功し、ユーザー向け挙動を変えない。

TM-2の契約、実測、migration/rollback確認は
[リファクタリング履歴](../../archive/リファクタリング履歴.md)へ移動済みである。

## 4. 共通の完了条件

1. 変更前にcharacterization testまたは比較fixtureを用意する。
2. 公開import、API、DB、SSE、保存ファイル、error codeの不変条件を明記する。
3. 設計書、変更履歴、ソース、テストの順で変更する。
4. 対象テストの後に全体テスト、月次監査、静的検査を行う。
5. UI影響がある場合はdesktop/mobile、keyboard、console、修正後再実行を確認する。
6. rollback可能な単位でcommitし、仕様変更・依存更新・性能改善を混在させない。
7. 完了実績は同じ変更で履歴へ移し、本書には未完了事項だけを残す。
8. 例外や保留にはowner、理由、期限、再評価条件を記録する。

### 中止・再計画条件

- OpenAPI、DB migration、SSE、manifest、OCR判定に意図しない差分が出た。
- 現行挙動を固定できない副作用が見つかった。
- 新機能またはデータ移行が不可避になった。
- 独立したgreen状態を作れないまま変更範囲が拡大した。
