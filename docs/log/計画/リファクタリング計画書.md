# リファクタリング計画書

最終更新: 2026-08-16（全体再計画 R0〜R7、R3完了）

> 状態: R0〜R3・D1〜D5完了（R1 Windows実機確認のみ保留）。次はR4

外部挙動を変えずに、責務境界、変更容易性、障害時の復旧可能性、設計書の正本性を
改善するための全体計画。過去に完了した Phase 1〜99、再計画 Phase 0〜6、D0 の実績は
[リファクタリング履歴.md](../../archive/リファクタリング履歴.md)と本書の D0 基準線を参照する。

長期的な肥大化・設計ドリフトの予防策は
[品質ガードレール](../../design/詳細設計/品質ガードレール.md)を正本とする。

## 1. 目的と範囲

### 1.1 目的

1. Windows Kindle 操作、Linux カタログ、OCR、RAG、Web UI の境界を明示する。
2. 副作用の多い処理を「判断」「I/O」「状態遷移」「公開」に分け、単体検証可能にする。
3. API、DB、SSE、保存ファイル、エラーコード、OCR 品質判定を変更せずに内部構造を改善する。
4. 互換 facade と一回性移行コードを、利用実績に基づき安全に縮小する。
5. 行数を減らすこと自体ではなく、変更理由と障害範囲が一致する構造へ寄せる。

### 1.2 管理先の判定

| 判定 | 管理先 |
|---|---|
| ユーザーから見た振る舞いが新しく増える・変わる | [バックログ.md](バックログ.md) |
| 外部挙動を変えない内部構造改善 | 本計画 |
| 依存・インフラ・性能特性を変更する | 本計画の「技術メンテナンス」 |
| 完了・スキップ・撤回済み | [リファクタリング履歴.md](../../archive/リファクタリング履歴.md) |

### 1.3 対象外

- API、DB スキーマ、取込ロジック、OCR 品質基準そのものの仕様変更
- Kindle の撮影範囲、ページ送り、先頭移動方式、復旧回数上限の変更
- 新しい画面、検索方式、LLM 機能、対応ソースの追加
- 行数だけを理由にした機械的分割
- 2 箇所の類似だけを理由にした先回り共通化
- 依存更新、性能改善、データ移行を構造変更と同じ Phase へ混在させること

仕様変更が必要と判明した場合は、その部分をバックログまたは技術メンテナンスへ分離し、
本計画の Phase を一度止めて契約を再確定する。

## 3. 全体方針と依存順序

### 3.1 実施順

| 順序 | Phase | 依存 | 理由 |
|---:|---|---|---|
| 1 | R0 基準線・契約固定 | なし | 以後の比較器と rollback 点を作る |
| 2 | D1〜D5 正本整理を領域別に先行 | D0 | 各コード Phase に必要な文書 Phase だけを直前までに完了する |
| 3 | R0-B OCR 比較器の分割 | D1〜D2 | OCR 本体より先に回帰判定器を信頼できる構造にする |
| 4 | R1 Kindle 操作・一括実行境界 | D3〜D4 | Windows 内部実装と横断 job 契約を混同しない |
| 5 | R2 Kindle カタログ境界 | R0、D3 | job 完了とファイル公開の契約を固定してから分ける |
| 6 | R3 OCR パイプライン | R0-B、D1〜D2 | 品質基準と公開条件を先に正本化する |
| 7 | R4 RAG・LLM 境界 | R0、D5 | OCR 実測知見を分離して RAG の責務を明確にする |
| 8 | R5 フロントエンド | R2〜R4 の対象 API 契約確定 | backend と同時に型・SSE 所有を動かさない |
| 9 | R6 互換層・テスト・ツール整理 | R1〜R5 | 移行中に必要な facade を早期撤去しない |
| 10 | D6〜D7、R7 | R1〜R6 | 完了実績を archive し、確定境界を機械検査へ昇格する |

R1 と R3 は担当ファイルが重ならないため、R0 と各文書前提の完了後は並行可能。
R2 は capture job 契約を共有するため R1 と設計判断を同期し、同じファイルを同時編集しない。

### 3.2 変更単位

- 1 Phase を 1〜3 個の独立 PR に分け、各 PR を常に green で閉じる。
- 「新しい境界を追加」「呼び出しを移行」「旧 facade を撤去」を別コミットにできる形にする。
- rename とロジック変更、依存更新と責務分割、性能改善とデータ構造変更を同じコミットにしない。
- 公開 import がある場合は facade を先に残し、全利用箇所移行と reachability 確認後に撤去する。

### R4. Novel RAG・LLM の orchestration、parser、repository を分離 — P2

**対象:** `backend/services/novel_db/` の search、summary、discussion、character、prompt、
`common/llm/` の利用境界、対応 router/test。

目標境界:

- provider: `local_llm.Backend` の構築と lifecycle
- prompt: domain ごとの prompt template と version
- parser/validator: LLM 応答を純粋関数で正規化・検証
- repository: SQLite/LanceDB の read/write
- application service: QA、summary、discussion、character generation の orchestration

実施内容:

1. module global の `_llm_backend` を provider 経由の明示依存へ寄せ、テストの patch 点を境界へ集約する。
2. `_prompts.py` を利用 domain ごとの所有先へ移し、共通化は真に共有する断片だけに限定する。
3. `summarizer.py` の text load、map-reduce、persist、index を分ける。
4. `generated_content_audit.py` の snapshot codec、diff、renderer、restore transaction を分ける。
5. `summary_grounding`、`query_expander`、relation extraction の parser を純粋関数として隔離する。
6. discussion の LLM stream、品質検査、history、SSE event 生成を分ける。
7. `common/llm` の公開 API は維持し、Pic2PDF 固有設定を共通 package へ逆流させない。

不変条件:

- prompt 内容・既定 option・model 選択・SSE event 順序・履歴 schema を意図なく変更しない。
- 検索 ranking、grounding 判定、summary/character restore の transaction を維持する。
- Qwen/Gemma/Verifier の役割を統合しない。

完了条件:

- `parse_grounding_response`、`stream_discussion_turns`、`_parse_expansions` の C901 超過を解消する。
- LLM を module global へ patch せず fake provider で主要 application service をテストできる。
- prompt snapshot、固定 retrieval fixture、SSE transcript が構造変更前後で一致する。

完了条件:

## 6. 技術メンテナンス

### TM-2. OCR ground truth API の全件 CER 再計算を増分化 — P2

`GET /api/ocr/ground-truth` と単件更新応答は、登録済み全本文の Levenshtein 距離を
都度再計算する。B-35 corpus 追加後、全件応答が 60 秒を超える事例がある。

- R3 とは別 Phase とし、先に D2 と R3 の ground truth 所有境界を確定する。
- R0-B の benchmark CER は NFKC 等を含む別の正規化契約なので、TM-2 の同値比較には流用しない。
- API 実装の空白除去だけを行う `character_error_rate` に対し、ページ別・集計別の
  characterization fixture とレスポンス比較器を別途用意する。
- API 契約、CER 正規化規則、DB 正本を変更せず、ページ単位の編集距離と文字数を更新時に再計算する。
- 一覧・更新応答は保存済み集計を合算し、本文または候補変更時だけ対象ページを無効化する。
- 現行の全件再計算結果と固定 corpus で完全一致させ、失敗時は古い集計を返さない。
- 完了条件は一覧・更新応答 10 秒以内、全指標一致、migration/rollback 手順確認とする。

## 7. Phase 共通の完了条件

1. 変更前に characterization test または比較 fixture を用意する。
2. 公開 import、API、DB、SSE、保存ファイル、error code の不変条件を明記する。
3. 設計書、変更履歴、ソース、テストの順で変更する。
4. 対象テストの後に全体テスト、月次監査、静的検査を行う。
5. UI 影響がある場合は desktop/mobile、keyboard、console、修正後再実行を確認する。
6. rollback 可能な単位で commit し、複数 Phase を同一 commit へ混在させない。
7. 完了実績を本書から履歴へ移し、未完了事項だけを残す。
8. 例外や保留には owner、理由、期限、再評価条件を記録する。

### 中止・再計画条件

- OpenAPI、DB migration、SSE、manifest、OCR 判定の意図しない差分が出た。
- characterization test では現行挙動を固定できない副作用が見つかった。
- 新機能またはデータ移行が不可避になった。
- 1 Phase が 3 PR を超えても独立した green 状態を作れない。

この場合は無理に分割を継続せず、Phase の境界か要件を再定義する。
