## 1. 管理先

| 判定 | 管理先 |
|---|---|
| ユーザーから見た振る舞いが増える・変わる | [バックログ](バックログ.md) |
| 外部挙動を変えない内部構造改善 | 本計画 |
| 依存・インフラ・性能特性を変更する | 本計画の「技術メンテナンス」 |
| 完了・スキップ・撤回済み | [リファクタリング履歴](../../archive/リファクタリング履歴.md) |

新機能、API・DBスキーマ・品質基準の仕様変更は本計画へ混在させない。
行数だけを理由にした分割、2箇所の類似だけを理由にした先回り共通化も行わない。

## 2. 技術メンテナンス

### TM-2. OCR ground truth API の全件 CER 再計算を増分化 — P2

`GET /api/ocr/ground-truth` と単件更新応答は、登録済み全本文の Levenshtein 距離を
都度再計算する。B-35 corpus 追加後、全件応答が60秒を超える事例がある。

- API実装の空白除去だけを行う `character_error_rate` に対し、ページ別・集計別の
  characterization fixtureとレスポンス比較器を先に用意する。
- API契約、CER正規化規則、DB正本を変更せず、ページ単位の編集距離と文字数を更新時に再計算する。
- 一覧・更新応答は保存済み集計を合算し、本文または候補変更時だけ対象ページを無効化する。
- 現行の全件再計算結果と固定corpusで完全一致させ、失敗時は古い集計を返さない。
- 完了条件は一覧・更新応答10秒以内、全指標一致、migration/rollback手順確認とする。

R0-Bのbenchmark CERはNFKC等を含む別の正規化契約なので、TM-2の同値比較には流用しない。

2026-08-16の本番実測では`GET /api/ocr/ground-truth`が120秒でタイムアウトした。
追加の画面仕様指定は不要で、現行本番DBをcharacterization corpusとし、レスポンス完全一致、
10秒以内、migration前バックアップ、rollback確認を既定の受入条件として着手できる。

## 4. 共通の完了条件

1. 変更前にcharacterization testまたは比較fixtureを用意する。
2. 公開import、API、DB、SSE、保存ファイル、error codeの不変条件を明記する。
3. 設計書、変更履歴、ソース、テストの順で変更する。
4. 対象テストの後に全体テスト、月次監査、静的検査を行う。
5. UI影響がある場合はdesktop/mobile、keyboard、console、修正後再実行を確認する。
6. rollback可能な単位でcommitし、仕様変更・依存更新・性能改善を混在させない。
7. 完了実績は同じ変更で履歴へ移し、本書には未完了事項だけを残す。
8. 例外や保留にはowner、理由、期限、再評価条件を記録する。

### 中止・再計画条件

- OpenAPI、DB migration、SSE、manifest、OCR判定に意図しない差分が出た。
- 現行挙動を固定できない副作用が見つかった。
- 新機能またはデータ移行が不可避になった。
- 独立したgreen状態を作れないまま変更範囲が拡大した。
