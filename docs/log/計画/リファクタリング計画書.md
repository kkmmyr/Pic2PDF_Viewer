## 4. Phase 2 — APIスキーマのドメイン分割（P1）

**問題**

`backend/routers/api_schemas.py`にライブラリ、小説、OCR、Kindleの型が集中し、
別機能の変更が同じファイルで競合する。

**変更**

- `backend/routers/schemas/`を作り、common/library、novel_db、ocr、
  kindle_catalogへ分割する。
- 移行中は`schemas/__init__.py`から再exportし、router側の変更を段階化する。

**完了条件**

- 分割前後の`openapi.json`を正規化比較し、外部契約差分が0件。
- `openapi-typescript`再生成で意図しない型差分がない。
- backend全テスト、frontend型チェックが通る。

---

## 5. Phase 3 — Kindle自動撮影境界の分割（P1）

### Phase 3A — Kindleアプリ操作

`KindleAppController`を次の責務へ分割する。

- 書籍identity照合
- ウィンドウ・control探索と通常入力
- ライブラリ検索・ダウンロード待機
- reader設定・撮影矩形・先頭移動

既存の`KindleAppController`は互換facadeとして維持する。

### Phase 3B — 撮影処理

`capturer.py`から撮影ループ、漫画crop、小説crop、手動互換UIを分離する。
撮影画像の座標・終了判定・保存形式は変更しない。

### Phase 3C — Windows agent

`capture_agent.py`をAPI/heartbeat、package作成・転送、工程制御へ分割する。

### Phase 3D — Linux側の正式登録

`capture_jobs.py`を状態リポジトリ、ready package検証、正式配置・補償処理へ分割する。
配置後、meta更新後、package移動後、DB更新前の失敗を注入するテストを追加する。

**完了条件**

- Kindle 50テストと追加した障害注入テストが通る。
- 公開エラーコード、状態遷移、manifest、保存先、画像内容が変わらない。
- 最終段階でユーザー承認のうえ、小説・漫画を各1冊実機確認する。

## 7. Phase 5 — フロントエンド共通ロジック整理（P2）

**変更**

1. `PageSlider`と`useReaderNavigation`のRTL/LTR・単ページ/見開き計算を
   純関数へ統一する。
2. Kindle一覧のURL query解析を純粋なquery-stateモジュールへ移す。
3. OCR QA画面は状態管理と表示部品を分ける。

SSE transportはすでに`features/novel_db/sse.ts`へ集約済みのため、
利用側の抽象化は重複障害を確認できた場合だけ行う。

**完了条件**

- RTL/LTRの先頭、末尾、奇数ページ、表紙単独を表形式テストで網羅する。
- URL検索条件、ブラウザー戻る・進む、表示結果が変わらない。
- frontend全テスト、型チェック、E2Eが通る。

## 8. Phase 6 — 小規模負債と品質ゲート（P2/P3）

個別に実害を確認できる項目だけを、1項目1コミットで扱う。

- `routers/library.py:delete_pdfs`の`update_meta_locked`反復を1回のロックへ集約。
- `tools/migrate_flatten.py`の利用実態を確認し、使用不能ならarchiveまたは撤去。
- `routers/hitomi.py`を共通loggerへ統一。
- C901の既存超過を基準線化し、新規超過・悪化を防ぐラチェットを導入。

次は構造変更ではないため、同じPhaseへ混在させない。

- RAGゴールデンQA: 品質評価基盤として別途要件と採点方式を確定する。
- `maybe_create_index()`: 実データ件数と検索性能を測定してから性能施策として判断する。
- hitomi同期HTTPの非同期化: 呼び出し元を含めた性能要求が出るまで保留する。

## 9. 実施規則

各Phaseは次を満たしてから完了とする。

1. 変更前に既存挙動を固定するテストまたは比較手順を用意する。
2. 公開import、API、DB、保存ファイル、エラーコードの不変条件を明記する。
3. 設計書、変更履歴、ソース、テストの順で変更する。
4. 対象テストの後に全体テストと静的検査を行う。
5. 完了実績を本書から削除し、リファクタリング履歴へ移す。
6. 例外や保留は理由と再評価条件を記録し、無期限のignoreを作らない。
