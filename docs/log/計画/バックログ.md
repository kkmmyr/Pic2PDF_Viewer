## A. 対応決定（高優先）

### A-4. Kindle 購入カタログと画像取り込みの統合

**動機**: 購入済み Kindle 書籍の確認、Amazon データの取り込み、既存画像との対応付け、キャプチャ開始が別アプリ・手入力・タイトル推測に分散している。新 Kindle アプリのウィンドウタイトルから書籍を識別できないため、キャプチャ前に購入カタログから ASIN を確定する必要がある。

**方針**:

- `kindle購入履歴` の必要領域を Pic2PDF_Viewer へ移し、通常運用時の外部アプリ依存をなくす
- Linux サーバーを正本とし、購入カタログと画像ライブラリを分離して ASIN で接続する
- カタログ DB は SQLite / PostgreSQL を負荷試験で比較し、Phase 0 の ADR で採否を確定する
- Amazon 注文 CSV / Kindle Info / 自動購入 JSON の差分取り込みを画面から実行する
- `kindle購入履歴` 側の表紙・画像キャッシュ・画像パスは移行しない
- 既存 comic / novel は候補提示 + 人の確認で ASIN を設定する
- 購入一覧から Windows キャプチャエージェントへジョブを渡し、Samba inbox 経由で Linux が成果物を検証・正式配置する
- 感想・レビュー・レビュースクレイピングは対象外とする

**完了記録**: [Kindle購入カタログ統合_実装計画.md](../../archive/Kindle購入カタログ統合_実装計画.md)

**工数**: 大。専用 DB・移行・複数形式インポーター・API・新規画面・Windows キャプチャエージェント・既存機能切替を段階実装する。

**状態**: 実装完了（2026-07-25）。実測 11,419 冊・単一利用者の条件から専用 SQLite を採用し、PostgreSQL への移行トリガーを ADR-0016 に記録。購入一覧、旧 DB 移行、Amazon/Kindle Info/自動購入差分取込、既存 comic / novel の手動 ASIN 紐付け、Windows キャプチャエージェント、Linux inbox 検証・正式配置、バックアップまで実装済み。

### B-34. Kindle 自動撮影取込

**動機**: 現行 capture agent は、ジョブ取得後にユーザーが対象書籍を Kindle アプリで開いて確認する必要がある。購入カタログで選んだ書籍を起点に、対象書籍の特定から Pic2PDFViewer 登録までを安全に無人化したい。

**方針**:

- 初期版は 1 冊ずつ処理する。
- 起動・ログイン済み、画面ロックなしの Windows を前提とし、Kindle アプリ自体は自動起動しない。
- Kindle の購入済みライブラリで ASIN を最優先に照合し、取得できない場合はタイトル、著者、シリーズ・巻を組み合わせる。
- 候補複数または本人照合不足では撮影せず失敗させる。
- 未ダウンロード書籍は完了を待ち、表紙または先頭位置へ戻してから最終ページまで撮影する。
- 既存 capturer、Samba inbox、Linux 側検証・原子的配置を再利用する。
- 本実装前に対象 Kindle アプリの UI Automation 成立性を実機確認する。

**詳細要件**: [Kindle自動撮影取込_要件.md](../../design/要件定義/Kindle自動撮影取込_要件.md)

**完了記録**: [Kindle自動撮影取込_実装計画.md](../../archive/Kindle自動撮影取込_実装計画.md)

**工数**: 大。Windows UI Automation、本人照合、ダウンロード待機、ジョブ状態・heartbeat、UI、実機回帰試験が必要。

**状態**: Phase 5 実装・実機受入完了（2026-07-26）。ASIN本人照合、未ダウンロード待機、
直接先頭移動、全画面撮影、Samba成果物公開、Linux側の原子的登録・置換、失敗時補償、
状態監視UIまで実装した。小説10巻は92画面、漫画1巻は85画面を同一ASIN置換で再登録し、
連番欠落・SHA-256重複・全面白が0件であることを確認した。先頭移動は数十画面戻る
フォールバックを持たず、直接遷移の検証失敗時は撮影前に`positioning_failed`で停止する。

### B-26. 書籍類似度推薦（novel 専用）

**動機**: 読書会で「この本に似ている」という表現を自然に使えるようにしたい。書籍詳細ページから直接「次に読む本」を探せる体験を作る。

**詳細要件**: [書籍類似度推薦_要件.md](../../design/要件定義/書籍類似度推薦_要件.md)

**概要**:
- 類似度: bge-m3 全文 embedding + サマリ embedding + タグ/著者メタ情報の 3 軸ハイブリッド（均等重み、調整可）
- 表示: 書籍詳細ページ下部パネル、閾値 cos ≥ 0.7 の最大 5 件
- 永続化: `book_similarities` テーブルにプリコンピュート
- トリガー: 管理画面から手動バッチ実行
- 対象: novel のみ（comic / doujin は対象外）

**工数**: 中〜大。DB スキーマ変更・バッチ処理・新規 API 2 本・フロントエンドコンポーネント追加

### B-28. 読書会ロングフォーム化 Phase 1（構成化台本 + 固定ホストキャラ永続化）

**動機**: 既存の読書会ディスカッション生成（B-20）は本の内容をだらだら話すだけで「読む気が起きない」というユーザー評価だった。10 分尺相当の構成化された番組台本にし、固定の司会キャラ（レイ＆ミオ）を本を跨いで使い回せるようにしたい。「やる夫スレ／ゆっくり解説」的な、キャラクターが本について語る動画コンテンツの土台を作る。

**詳細要件**: [読書会ロングフォーム拡張_要件.md](../../design/要件定義/読書会ロングフォーム拡張_要件.md)（Phase 0a/0b 技術検証済み、ホストキャラ設定・関係性・境界線確定済み）

**概要**:
- 番組構成テンプレート（OP フック → テーマ 2 本 → 脱線コーナー → 締め）をプロンプトに導入し、セグメント別ターン数指定で 10 分尺（3,000〜4,500 字）に到達させる
- ホストキャラ（レイ＆ミオ）の人格核（属性・得意分野・口調ベース）を永続データ化し、本ごとの推し解釈・スタンスのみ都度生成する設計に分離
- ボケ・ツッコミ役割をテーマごとに入れ替える会話ルールを追加
- マーカーパーサの寛容化（`[A>:` 等のドリフト許容）、中国語/英語リーク対策
- 生成バックエンドはローカル LLM（Qwen）を既定としつつ、有償 LLM API への切替も可能な設計にしておく（品質比較は別途実施）
- **UI（要件メモ §4.10 確定）**: 読書会ページを番組台本生成に置き換え（自由ペルソナ UI・往復数スライダーは廃止、旧履歴は閲覧可能のまま）。セグメント見出し付き区切り表示・クリップボードコピー + Markdown ダウンロード・機械チェック合否バッジ + 不合格理由 + 再生成ボタン
- **保存スキーマ / API 契約（要件メモ §4.11 確定）**: 保存 JSON v2（turn 単位 `segment` フィールド + キャラ設定スナップショット埋め込み + `checks` + `format_version`）。generate API は `{book_name}` のみの破壊的変更、SSE に `segment` / `checks` イベント追加、履歴は v1/v2 互換読み、DELETE API 新設（パストラバーサル対策必須）。全保存 + 削除ボタン方式

**DoD**: 要件メモ §10 に確定済み。機械チェック 5 項目（字数 3,000〜4,500 / 5 セグメント出現 / 話者分割 100% / 言語リーク 0 / ネタカード言及）を恒常的な合否ゲートとして実装し、「後宮の烏」1 冊で層1 全合格 + ユーザー主観合格（笑える・へえ箇所 3+ / キャラのブレなし）の台本が 1 本生成できれば完了

**着手時に決める残論点**: 有償 LLM コスト試算（要件メモ §5 論点7）のみ。要件レベルでは着手可能

**工数**: 中〜大。プロンプト設計 + パーサ改修 + キャラ永続データ構造の追加 + セグメント境界の機械可読出力 + 検証スクリプト

### B-31. 重複作品検出（doujin）— 検討段階

**動機**: フォルダ監視自動取り込み（2026-07-04 導入）は同一 ZIP の二重投入を防げない。重複に気づくのは閲覧時で、削除の手間と閲覧メタの分散が起きる

**工数**: 中

**状態**: 検討（2026-07-07 起票。閾値・警告 UI の要件は未確定）

### B-17. 漫画ソースへの画像キャプション検索（パイロット先行）

**案**:

| gemma4:e4b | △ | ◯ | × | ×（30%） | △ |
| **qwen3-vl:8b** | **◯** | **◯** | **△** | **◯（4/5）** | **△** |

**採用モデル**: `qwen3-vl:8b`（OCR 精度が 30% → 80%+ に改善）

**技術的注意点**:

**規模試算**: 1 冊平均 25 頁仮定で約 12,100 頁。qwen3-vl:8b の速度は実測次第。許容できなければサンプル頁（表紙 + 中扉 + 数頁）モードに切替

**工数**: Step 3 本実装 中

**判断**: **保留**（2026-06-12）: 現状の qwen3-vl:8b の品質が期待を下回るため現状は対応しない。ローカル VLM の精度向上（新モデル等）を確認した段階で再判断する。

### B-18. 小説 RAG: リーダー統合「ここまでのあらすじ」生成（優先度低）

**動機**: 続巻を読み始める前や、間が空いたときに「ここまで何があったっけ」を即座に思い出したい。Qwen 131k ctx で 1 冊丸ごと読めるので、任意ページまでの本文を input に「現時点までのあらすじ」を生成できる。

**案**:
- 小説リーダーに「ここまでのあらすじを生成」ボタン
- `GET /api/novel_db/books/{name}/recap?up_to_page=N` 新設、1〜N ページの本文を Qwen に投入し 800〜1500 字で要約
- 結果は `book_recaps(book_id, up_to_page, text, generated_at)` にキャッシュ（同じ `up_to_page` での再要求はキャッシュ返却）
- 既存 `summarizer.py`（B-5）が骨格としてほぼ流用可能

**工数**: 小〜中

### B-25. meta.db クラウド同期（SQLite Online Backup API + ファイルストレージ）

**動機**: 閲覧回数・ジャンル・シリーズ等の書誌メタを複数端末で共有したい。SQLite は WAL モードで頻繁に書き込みが発生するため、ライブファイルを OneDrive に置くと同期競合でDB破損リスクがある。

**方針**: `sqlite3.backup()`（SQLite Online Backup API）でスナップショットを安全に作成し、そのファイルだけを OneDrive / S3 等に配置する。ライブDB は常にローカルのまま。

**案**:
- `GET /api/meta/backup` — `sqlite3.backup()` でスナップショット（`meta.backup.db`）を作成し、指定ディレクトリに保存
- `POST /api/meta/restore` — 指定パスの `meta.backup.db` を取り込んで現在の DB に upsert マージ（衝突時は `last_viewed_at` が新しい方を優先）
- バックアップ先は env `META_BACKUP_DIR` で設定（OneDrive の共有パスを指定）
- Windows タスクスケジューラで定期実行（例: 1 日 1 回 `POST /api/meta/backup`）

**なぜ DynamoDB でなく SQLite backup か**:
- データモデルの移行が不要（SQLite のままファイルコピー）
- 追加クラウド費用ゼロ（OneDrive / ローカル NAS に置くだけ）
- `sqlite3.backup()` は API 標準なのでロック競合なし

**工数**: 小。`sqlite3.backup()` の呼び出し 1 関数 + API エンドポイント 2 本 + タスクスケジューラ登録手順

**関連**: 前段となるローカル自動バックアップ（クラウド同期なし・日次 N 世代 + integrity_check）を [リファクタリング計画書 § 未着手候補 — 技術メンテナンス](リファクタリング計画書.md#未着手候補--技術メンテナンス) に検討として起票済み（2026-07-07）。先にそちらを実装すれば本項の土台になる

### B-27. Kindle 新アプリ（Microsoft Store 版）キャプチャ完全対応

**状態**: 実装・実機受入完了（2026-07-26）。最大化ウィンドウと本文領域フォーカスを
共通基盤へ反映し、小説の上下UI除外と漫画の見開き安全幅を実装した。漫画1巻を85画面で

## 対象外（信頼モデル / 同人誌特化方針との非整合）

以下は **個人 LAN シングルユーザー × 同人誌特化** の前提と整合しないため意図的に作らない。

| 項目 | 理由 |
|---|---|
| ユーザーアカウント / 認証 / 認可 | LAN 内シングルユーザー前提 |
| マルチテナント・データ分離 | 同上 |
| API レート制限 | 単一クライアント前提 |
| WebSocket / SSE による進捗通知 | ポーリングで十分 |
| GraphQL API | REST で要件を満たす |
| API バージョニング | クライアント単一 |
| マイクロサービス分割 | 規模に対し過剰 |
| Kubernetes / Docker Compose 化 | LAN ローカル起動で十分 |
| 公開 PR テンプレート / Issue テンプレート | ソロ開発 |
| Storybook | コンポーネント数が爆発しない範囲 |
| サークル名 Web 検索による自動取得 | 撤去済み（精度が実用に達しない） |
| シリーズの自動発見（新規シリーズ生成） | 撤去済み（命名揺れに対し精度不足）。代替: AI による既存シリーズへの紐付け提案（A-1） |
| 多言語 OCR 対応 | OCR 機能自体が保留領域。現状日本語のみで十分 |
| ePub サポート | スコープ外（同人誌は ZIP / 画像が主） |
| AI タグ自動生成（表紙画像 + LLM） | タグ機能自体を撤去。復活時に再検討 |
| レーティング（★1〜5） | 旧バックログで実装候補だったがコード化されたことはなく、利用習慣もないため恒久的に対象外 |
| 小説 RAG: クラウド LLM 移行（B-7） | B-13/B-14 完了でローカル QA 品質・速度が要件を充足（llama-server で応答 5× 短縮、全文読み込み実現）。「性的描写を含む可能性があるためクラウド AI を使用しない」方針とも整合するため恒久的に対象外（2026-06-12 判断） |
| 小説 RAG: ページ単位シーン要約（B-10） | B-9（Contextual Retrieval / gemma4:e4b）で当初 19 時間想定 → 実機 100 分に短縮され存在意義消失。B-9 で品質充足（2026-06-12 判断） |
| 大規模 Panel の presentation/container 分割 | hook 抽出済みで本体ロジック層は既に薄く、JSX 主体の分割では行数は減っても認知負荷は下がらない。テスト容易性の利得は hook 単体テスト（744 件）と将来の E2E（C-8）で充足見込みのため対応しない |
| 小説 RAG: LLM 補助チャンキング（Qwen でシーン境界検出 → 再チャンク） | 文献的に確定的な評価が薄く、B-9（Contextual Retrieval）のほうが ROI 高い。再チャンク + 再 embedding のコストも大きい。B-9 で十分な改善が得られると見込み、本項目は対応しない |
| PDF 分割（B-1） | merge の逆処理は工数に対して利用頻度が低く、手動ツールで代替可能 |
| モバイル UI 最適化（C-4） | 個人 LAN PC 専用ツールのためモバイル対応は不要 |
| a11y 強化（C-6） | LAN 内シングルユーザー前提のため不要。LAN 外公開の予定もなし |
| 小説 RAG: 横断検索（C-9） | スキーマ変更コストが大きく、ソース別閲覧で利用実態として不要 |

## 運用方針

- **新規候補の振り分け**: ユーザーから見た新機能・新体験 → 本ファイル（A/B/C 階層）。内部改善・依存更新 → [リファクタリング計画書](リファクタリング計画書.md)。
- 候補が **A-N → 対応決定** になったら新機能として `feat:` プレフィックスのコミットで実装
- 実装後は本ファイルから対応済み項目を削除し、上部「実装済み機能の履歴」テーブルに 1 行追加 + 詳細は変更履歴 / 設計書側に記録
- 棚上げ判断（C → 対象外）になった項目は対象外テーブルに移動

候補追加時のフォーマット:

````markdown
### {Tier}-{N}. {タイトル}

**動機**: {現在の不便 / 欲しい価値}
**案**: {具体的な実装方針}
**工数**: 小 / 中 / 大
````
