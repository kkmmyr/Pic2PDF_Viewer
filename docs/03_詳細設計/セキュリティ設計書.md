# セキュリティ設計書

本アプリケーションのセキュリティ設計の根拠・防御範囲・制限をまとめる。

---

## 1. 信頼モデル

本アプリケーションは**ローカルホスト専用のシングルユーザーツール**。

- **想定環境**: `localhost:8766` (API・dev) / `localhost:5176` (UI・dev) / `localhost:8090` (リリース統合) をローカル PC で使用する
- **想定攻撃者**: 外部ネットワークからの不正アクセス、または悪意あるウェブページからの CSRF
- **想定外**: マルチユーザー認証、データの暗号化保存、監査ログ

> 認証・認可機能は実装していない。LAN 外に公開することを想定していないため、必要になった場合は別途設計が必要。

## 2. バックエンド セキュリティ

### 2-1. CORS

**ファイル**: `backend/main.py` / `backend/config.py`

```python
# デフォルト許可オリジン
_default_origins = "http://localhost:5176,http://127.0.0.1:5176"
CORS_ORIGINS = os.environ.get("ALLOWED_ORIGINS", _default_origins).split(",")
```

- `localhost` / `127.0.0.1` のみ許可（ポート 5176 = フロント開発サーバー）
- 環境変数 `ALLOWED_ORIGINS` で上書き可能（LAN 内共有等の拡張時）
- `allow_methods=["*"]` は CORS ヘッダーの制御用であり、実際の認可ではない

### 2-2. パストラバーサル防止

**ファイル**: `backend/utils/path_utils.py`

全エンドポイントでユーザー入力パスを検証し、データディレクトリ外へのアクセスを防ぐ。

| 関数 | 防御対象 | 拒否する入力例 |
|---|---|---|
| `validate_safe_path(path)` | ディレクトリトラバーサル | `../etc/passwd`, `/etc/passwd`, `\\server\share` |
| `validate_safe_name(name)` | パスセパレータを含む名前 | `../secret.pdf`, `folder/file.pdf` |

**検証ルール (`validate_safe_path`)**:
- `".."` を含む → `HTTP 400`
- `"/"` で始まる → `HTTP 400`（Unix 絶対パス）
- `"\\"` で始まる → `HTTP 400`（Windows UNC パス）
- 正規化: バックスラッシュをスラッシュに統一して返す

**適用箇所**: `routers/library.py` / `routers/meta.py` / `routers/pdfs.py` の全パラメータ受け取り箇所。

### 2-3. ファイル種別チェック

**ファイル**: `backend/utils/file_utils.py`

`config.py` で許可する拡張子を一元管理し、直書きチェックを禁止。

```python
is_pdf_file(name)   # .pdf
is_webp_file(name)  # config.SUPPORTED_WEBP_FORMAT
is_zip_file(name)   # config.SUPPORTED_ZIP_FORMAT
is_image_file(name) # config.SUPPORTED_IMAGE_FORMATS
```

任意ファイルを処理対象に混入させる攻撃に対する防御。

### 2-4. meta.json 更新のアトミック性

**ファイル**: `backend/services/meta_store.py`

`update_meta_locked(source, updater)` はファイルロックと updater パターンで実装。
複数リクエストの並行書き込みによるデータ破損を防ぐ。

## 3. フロントエンド セキュリティ

### 3-1. ファイル名バリデーション

**ファイル**: `frontend/src/utils/validation.ts`

```typescript
export const FORBIDDEN_FILENAME_CHARS = /[/\\:*?"<>|]/;
```

Windows / macOS / Linux 共通の禁止文字を除外。各ダイアログで個別に正規表現を再定義しない（`validateFilename(value, kind)` を共有）。

### 3-2. XSS 防止

- React の JSX は文字列をデフォルトでエスケープするため、通常の文字列表示での XSS は発生しない
- `dangerouslySetInnerHTML` は使用していない
- PDF ファイル名・メタデータをそのまま `innerHTML` に渡す箇所はない

### 3-3. ダイアログの標準化

`confirm()` / `alert()` は使用禁止（`coding_conventions.md` 参照）。
共通コンポーネント `ConfirmDialog.tsx` を使用することで、ユーザー操作の一貫性とフィッシング的な悪用を防ぐ。

## 4. 依存関係のセキュリティ

### 監査手順

```bash
# /audit コマンドで一括実行
cd frontend && npm audit
cd backend && uv audit
```

### 判断基準

| 重大度 | 対応 |
|---|---|
| critical / high | 速やかに対処（`npm audit fix` または手動更新） |
| moderate | dev dependency 由来かを確認し、本番影響なければ放置可 |
| low | 原則放置（次回更新時にまとめて対応） |

### 既知の処置済み脆弱性

| 日付 | パッケージ | 脆弱性 | 対処 |
|---|---|---|---|
| 2026-04-29 | postcss < 8.5.10 | XSS (GHSA-qx2v-qp2m-jg93) | `npm audit fix` で 8.5.10 以上に更新 |

## 5. 将来の拡張時の注意

- **LAN 公開**: `ALLOWED_ORIGINS` に加え、認証機能（Basic 認証 or トークン）の追加を検討
- **ファイルアップロード機能追加**: Content-Type 検証とファイルサイズ上限の実装が必要
- **外部 API 連携拡張**: API キーを環境変数で管理し、ソースコードにハードコードしない
