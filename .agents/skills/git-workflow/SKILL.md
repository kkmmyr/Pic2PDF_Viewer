# Git 運用ルール

このプロジェクトの git 操作は以下のルールに従う。

## コミットの粒度

- **1 コミット = 1 つの論理単位**。複数のリファクタリング・機能追加・無関係な事前変更を 1 コミットに混ぜない。
- 大きな作業（Phase 13〜17 のような）でも、ファイル間の依存で分割不能な場合のみ 1 コミットにまとめる。それ以外は論理単位で分ける。
- **会話開始時から既に変更されていた無関係なファイル**（リリース関連・設定変更等）は、リファクタリングのコミットには含めない。別コミットに切り出す。

## コミットメッセージ

- **Conventional Commits** プレフィックスを使う:
    - `feat:` 新機能 / `fix:` バグ修正 / `refactor:` リファクタ
    - `docs:` ドキュメント / `test:` テスト追加 / `chore:` 設定・依存等
    - スコープ付きで `feat(library):` のように書ける
- **HEREDOC** で渡す（改行・引用符の崩れを防ぐ）:
    ```bash
    git commit -m "$(cat <<'EOF'
    refactor: foo を bar に変更

    詳細...

    Co-Authored-By: Codex <現在のセッションのモデル名> <noreply@anthropic.com>
    EOF
    )"
    ```
- 末尾には常に `Co-Authored-By: Codex <現在のセッションのモデル名> <noreply@anthropic.com>` を入れる。モデル名は**そのコミットを作成している現在のセッションのもの**を使う（特定バージョンを固定で書かない — 固定すると陳腐化する）。
- タイトルは 70 文字以内。詳細は本文で書く。

## ファイル操作

- **リネーム / 移動は `git mv`** を使う。`mv` してから `git add` だと履歴が切れる。
- 削除は `git rm`。

## 危険な操作

- 以下はユーザーの明示許可がない限り **禁止**:
    - `git reset --hard`
    - `git checkout -- <file>`（未保存の変更を破棄）
    - `git commit --amend`（公開済みコミットの書き換え）
    - `--no-verify`（pre-commit hook のスキップ）
- 変更を「なかったことにしたい」場合は、まず `git stash` を提案する。

## 「事前変更が混ざっている」状況の扱い

セッション開始時点で `git status` に M / ?? のファイルがある場合：
1. 自分が触ったファイルを判別する。
2. **触ったファイルだけ `git add <file>` で個別追加**する（`git add .` / `git add -A` は使わない）。
3. 残った事前変更は別コミットに切り出すか、ユーザーの判断に委ねる。

## コミット直前の確認

- `git status --short` でステージ状況を最終確認する。
- `git log --oneline -5` で過去のコミットスタイルを参照し、揃える。
- HEREDOC 内に `$variable` や バックティック・ドル記号が含まれる場合はシングルクォート (`<<'EOF'`) を使う（変数展開を防ぐ）。
