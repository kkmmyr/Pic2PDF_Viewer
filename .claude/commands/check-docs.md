設計書と実装の整合性チェックを実行してください。Phase 完了直後・大きな機能追加後・リファクタリング後の検証用。

## チェック対象

| 設計書 | 実装との対応 |
|---|---|
| `docs/01_要件定義/要件定義書.md` | 機能の存在 |
| `docs/02_基本設計/基本設計書.md` | アーキテクチャ・技術スタック |
| `docs/02_基本設計/アーキテクチャ詳細_バックエンド編.md` | バックエンド／Kindle／データディレクトリのファイルマップ（最重要）|
| `docs/02_基本設計/アーキテクチャ詳細_フロントエンド編.md` | フロントエンドのファイルマップ（最重要）|
| `docs/03_詳細設計/詳細設計書_バックエンド編.md` | バックエンド／Kindle／OCRエンジンのクラス設計 |
| `docs/03_詳細設計/詳細設計書_フロントエンド編.md` | Context／フック／UI／コンポーネント設計 |
| `docs/03_詳細設計/詳細設計書_共通.md` | 全体ディレクトリ構成・運用・リリースビルド |
| `docs/03_詳細設計/API仕様書.md` | エンドポイント・レスポンス形式 |
| `docs/03_詳細設計/OCR設計書.md` | OCR/Kindle 領域（変更があるときのみ）|

## 進め方

1. **アーキテクチャ詳細_バックエンド編.md** と **アーキテクチャ詳細_フロントエンド編.md** を Read で読み込む（最初の1ステップ）。
2. 実装側の **新規ファイル / 削除ファイル** を `git log --stat` または `git diff --stat HEAD~10` で確認。
3. 各設計書のディレクトリ構成・ファイル一覧と実装を**対応表**で突き合わせる:
    - 設計書にあって実装にないもの → デッドコード or 削除漏れ
    - 実装にあって設計書にないもの → 追記漏れ
4. **API 仕様書** の対応:
    - `backend/routers/` 配下の `@router.<method>` をすべて列挙し、API 仕様書に記載があるか確認
    - レスポンス例の構造（`return` / `BaseModel` / dict 構築箇所）を実装と照合
5. **詳細設計書（バックエンド編・フロントエンド編）** のクラス・関数説明の更新漏れ:
    - 主要クラス・関数のシグネチャ変更があったか
    - 新規フック / コンポーネントが追記されているか

## 報告フォーマット

```markdown
## 整合性チェック結果

### ✅ 整合済み
- 〇〇〇

### ⚠️ 不整合（要修正）

#### 詳細設計書（バックエンド編／フロントエンド編）
- [ ] AAA — 実装にあるが設計書に未記載: ファイルパス
- [ ] BBB — 設計書にあるが実装にない: ファイルパス

#### API仕様書
- [ ] CCC — エンドポイント未記載: `POST /api/xxx`
- [ ] DDD — レスポンス例の不一致

### 📝 参考指摘（リファクタリング範囲外）
- 要件定義書に未反映の機能: ...
```

## 修正方針

不整合が見つかった場合：
- **修正してもよいか確認**してから着手する（勝手に大規模 docs 編集をしない）
- 1 設計書 = 1 コミット で分割するか、まとめて 1 コミットにするかをユーザーに聞く
- 修正後は `docs/05_記録/変更履歴.md` にも記録する
